# `tide_add_game` and the generated header

`EMBED` (2026-10-20): `tide_add_game(... EMBED)` passes `--embed` (which
implies the layout) and defines `TIDE_HAS_EMBED` for the target, so
`tide/run.h`'s table has `tide_game_embed` and `tide_game_layout` for
`tide/embed.h`. It keeps all assets, as LAYOUT does. `notes/standard-host.md`.

Managed deployment (2026-10-15): the installed CLI's internal managed target
builds a wasm32-wasip1 reactor with imported bounded memory and `managed_run.h`;
it is distinct from CMake's native SERVER target and the threaded web player.
Generated headers expose `TIDE_SIMULATION_ID` outside the layout hash; the game
API carries its 32 bytes. Header session ABI marker is 15. Platform installation
now also supplies single-threaded WASI headers/libc/libm/crt1-reactor. Full
contracts, source-toolchain fingerprint and validation: managed-hosting.md.

Dedicated service targets (2026-10-15): tide_add_game(... SERVER) generates a
server_run.h launcher on native targets, preserving the client game identity.
It omits client-only assets automatically without custom C; STRIP_SERVER_ASSETS
is the explicit C opt-in and requires SERVER. SERVER rejects HOST, WINDOW,
LAYOUT, web and Android. Header/source installation uses the existing paths.
Both debug/release collect unreachable client code. Contracts/tests are in
dedicated-servers.md.

Docs playground (2026-10-14): opt-in TIDE_DOC_PLAYGROUND builds its shared Tide
example with LAYOUT and a portable HOST (ordinary tide_run for native captures,
tide_host_run_web for the browser). On web it also builds tidec_browser from the
existing compiler sources, engine and importers, and explicitly stages the
compiler/static runtime bundle through docs_playground. TIDE_DOC_EXAMPLES
defaults this option on; docs_examples collects the web staging target. Normal
native/web builds retain their host tidec and existing program generation.
There is no generated-C/runtime API change. Contracts, downloads and validation
are in notes/docs-site.md.

Games outside this repo (2026-10-21, replacing `TIDE_PRIVATE_PROTOTYPES` and `prototypes/`): `TIDE_EXTERNAL_DIRS` adds folders from other checkouts, each `add_subdirectory`'d into `external/<folder name>`, after this repo's games. Their games and tests use `tide_add_game` normally on native and web, with the engine's targets and `PROJECT_SOURCE_DIR`; the owner's prototypes (`Tide-Engine/tide-prototypes`) are built that way, and their `private_games` stages each catalog game's page at `docs/static/prototypes/<id>/index.html` and the catalog beside the docs site. Nothing installs them into the package. Contract: `notes/repository.md`, Other repositories.

Build notes, moved here from `AGENTS.md` as they were: what's built, what code relies on, the tests and the measurements. `AGENTS.md` has the rules every session needs and the index of these files. The headings below are that file's sections as they were, and "see <Section>" names one of them: the index says which files each is in. What a note calls "below" or "above" may be in another of these files now: search `notes/` for its name.

## Building

### Tide programs

`tide_add_game(<target> [SOURCES <file.tide|file.c|file.cpp>...] [HOST <file.c>...] [WINDOW] [NAME <name>] [TITLE <title>] [STATS] [LAYOUT] [WARNINGS <text>...] [PACKAGES <Name> <file.tide>...] [DEFINES <SYMBOL>...] [SHELL <page.html>])` builds a game as the program `<target>` (see `cmake/Tide.cmake`):

- The game is every `.tide` file in the current source folder and its subfolders; the next build picks up new files. `SOURCES` lists the files instead, for tests and folders that hold several games.
- The game's C (its `extern` functions') is every `.c` file there but the `HOST` ones and those in hidden folders or `build/`, or the `.c` files in `SOURCES`. Its C++ files (`.cpp`, `.cc`, `.cxx`) go the same way, with tide's flags for them (`TIDE_CPP_FLAGS`): the project stays C, so the C compiler compiles them and programs link as C. `compiler/tests/e2e/cpp` runs C++ with no runtime on every target. Unlike `tide`, it doesn't pick up prebuilt libraries.
- Without `HOST`, the game is the whole program and needs no C: a generated `main` runs it in a window through `tide/run.h`. On the web it's `<target>.html`, around the canvas `SHELL` makes (`tide_web_page`'s, `platform/web/shell.html` without one): Earth's (`examples/earth/page.html`) gives the program `Tide.arguments`, its regions.
- It doesn't read `tide.packages`: games with packages build with `tide`. `PACKAGES` is for tests of what packages do to a game: the files after each package's name are that package's, and compile before the game's (tidec's `--package`).
- With `HOST`, those C files are the program (tests, the demo's smoke test, custom hosts). They include `<name>.h`, where `NAME` defaults to `<target>`. `WINDOW` says the host opens a window, so on Android it's an app (see Android builds). They link the engine and `tide_font_bold`, the bold weight's file as a library of one object, which a linker only takes for a game that says `Font.Bold` (see Rendering and platform).
- `tidec` compiles all the files together, in order of their paths. The generated files regenerate whenever a `.tide` file or `tidec` changes. `tide_add_game` gives tidec the files as a list in a file (`@<file>`, a path a line; `tide/<target>.sources` in the target's build folder), since a big game's are more than a command line holds (32,767 characters on Windows), and tidec takes as many files as there are.
- tidec has to stay fast on big games (thousands of files, declarations and systems): with `TIDEC_TIMES` set in the environment, it says on stderr how long each phase of a compile took. Names are looked up through an index of the declarations by namespace and name, and by name in generated C (`decls_by` in `compiler/src/check.c`), never by going through them all.
- `node bench/compile.mjs --tide <installed tide> --save <label>` measures cold game caches, unchanged builds, a Tide body edit, a C body edit and a header edit, keeping repeated wall times, object reuse and machine/compiler/revision metadata in `bench/results/compile.jsonl`. `bench/README.md` lists native/web, debug/release and source-size options. Cold means an empty game cache, with the installed tools and filesystem caches still warm.
- A warning from `tidec` fails the build, unless part of its text is listed after `WARNINGS`; each of those has to be there (see Building).
- The game's assets go with it (see Assets, under Tech stack): `<name>.pack` beside the generated C, which a game with a window gets as `<target>.pack` beside its program, in its page and in its APK, and a `HOST` program as `<name>_pack.c` (`tide_game_pack`), to hand `tide_assets_load`. The files assets name are in the generated files' dependencies, found as the game is configured (globs through their folders).
- Standalone optimized `tide_add_game` targets omit assets with no references in checked Tide code through explicit `--strip-unused-assets` generation. Debug, `HOST`, `LAYOUT` and custom-C targets retain all declarations because external hosts or C code can find them by name. Release, RelWithDebInfo and MinSizeRel standalone links collect unreachable code sections; only Release/MinSizeRel strip symbol/debug tables, retaining the everyday release preset's profiling information. The compiler still validates unused asset declarations, and references in emitted helpers/defaults remain conservative roots. A RelWithDebInfo integration fixture verified that an all-unused standalone pack disappears, custom C retains its pack, and the profiling PDB remains.
- `<target>_schedule` is a build target that prints the game's schedule: which systems can run at the same time, and why the others wait.
- Every game's files are listed in `build/tools/games.txt`, one `<game>\t<path>` per line. A path ending in `/` is a folder: every `.tide` file in it and its subfolders, so editors see new files before the next build. A file of a package (`PACKAGES`) has the package's name after it, `<game>\t<path>\t<package>`. `tidels` reads it, and the one in `build/tools/` of any folder open in the editor, to analyze a game's files together, in `tidec`'s order. A file in no game belongs to the open folder it's in, as `tide run` would build that folder, unless a manifest lists games in that folder: then it's analyzed alone.

The generated header is the API between the game and the host. Namespaced declarations have their namespace in their C name: `Combat.Health` is `Combat_Health`, read with `tide_get_Combat_Health`.

Assets read by skinned vertex defaults contribute their named content fingerprints to this header, including defaults used by runtime `Decode`. The compiler follows constants, omitted defaults, operators and their helpers, and referenced mesh defaults to collect these dependencies. A private helper shared by tidec and its generated C checks the actual dependency entries before replacing the loaded pack; rejection keeps the current assets intact. Unrelated assets stay outside these fingerprints, so their updates retain the game's identity. `tidec_skinned_default_identity`, `tidec_e2e_skinned_defaults` and `tidec_pack_fingerprint` cover the dependency closure, reload boundary and raw pack validation; see `notes/assets-and-files.md` for their cases.

- `tide_world`: the whole simulation state. Its data is in pages it shares with its snapshots (see ECS and simulation state), so a world starts zeroed (`{0}`, static or `calloc`), copying the struct isn't a snapshot (`tide_world_copy` is), and `tide_world_free(w)` lets it go. When fields hold text or lists, it has a `heap` they're kept in; hosts read a text field with `tide_text_read(&w->heap, field)`.
- `tide_world_init(w, dt)`: clears the world, sets `Time.dt` and singleton defaults, and loads the `Main` scene if it's the match's. `Time` is a singleton like the game's, in the world: `t` (`tick * dt`, which the tick sets from the tick, never by adding) and `tickRate` (1 / `dt` to the nearest, set here; 0 for a `dt` no rate fits) are stored fields, so views blend `t` and shaders get it as any float they read.
- `TIDE_MAIN_IS_LOCAL` is defined when `Main` is a local scene: the program starts outside any match.
- `tide_world_tick(w)`: runs every system once, then applies structural changes. With no scene left, it loads `Main` again if it's the match's; `tide_frame` does the same for a local `Main`. `tide_world_tick_events(w, jobs, events)` is the same tick, recording into a `tide_event_log` what it sent that the game's local handlers hear (see Networking); the world comes out the same.
- `tide_world_ended(w)`: whether the match is over: its last scene unloaded and `Main` is local, so it can't come back. The server stops ticking there and tells every player, who go offline with `TIDE_DISCONNECT_ENDED` (`Ended` in Tide).
- `tide_local`: this machine's local state, outside every world. `tide_local_init(local)` clears it and sets its singletons' defaults.
- `tide_frame(w, previous, alpha, verified, verified_previous, verified_alpha, local, draw, gui)`: runs every view once, adding their Draw calls to a `tide_draw_list` and their widgets to a `tide_gui`, then applies the local changes they made. Views see the match's floats blended from `previous`, the tick before `w`, by `alpha` (0 to 1), so they're smooth at any tick rate; `tide_session_view` supplies both predicted and confirmed intervals. Verified values blend between `verified_previous` and `verified` by `verified_alpha`, holding at the latest confirmation; local fields are kept by the upper endpoint (see ECS and simulation state). Pass NULL and 1 to draw `w` as it is, and NULL for `verified` where `w` is all there is. Call it once per frame, after `tide_draw_reset(draw)` and `tide_gui_begin(gui, devices, tide_platform_screen_size(), tide_platform_measure_text)`, then `tide_gui_end(gui, draw)` and render the list with `tide_platform_draw(draw)`. Outside a match `w` is NULL, and views that read the match don't run. A zeroed `tide_gui` is ready to use. Before it, `tide_local_events(local, events)` hands over what the match sent since the last frame (a session's `tide_session_events`, or the log a host gave `tide_world_tick_events`): the frame runs the local handlers of the match's events first, then lets go of local fields, then runs the views. `verified` parameters read `verified`, or `w` where it's NULL.
- Components are values, as a world keeps them in lanes (see ECS and simulation state): `tide_has_<Component>(w, entity)` says whether an entity has one, `tide_get_<Component>(w, entity)` gives a copy (zeros when it has none), and `tide_set_<Component>(w, entity, value)` puts one back (false when it has none, changing nothing), as its bytes: text and lists in it stay where they are in the heap. A local component's take the `tide_local`. A match component's local fields are a struct of their own, `<Component>_local`, with `tide_has_<Component>_local(local, entity)` (whether anything was written for it), `tide_get_<Component>_local` (the defaults when nothing was) and `tide_set_<Component>_local`; a singleton's are `local-><Singleton>_local`. The component's own struct and accessors are the match's part. `TIDE_AT(w, arch0_Body, Body, row)` (a copy too) and `TIDE_ENTITY_AT(w, arch0_Body, row)` read an archetype's rows, for tests and tools.
- `tide_world_player_joined(w, player)` and `tide_world_player_left(w, player)`: send `PlayerJoined` and `PlayerLeft`, handled at the end of the next tick. Every machine calls them before the same tick.
- `tide_world_entity_count(w)` and `tide_world_print(w)`: for debugging.
- `tide_world_copy(to, from)` and `tide_world_hash(w)`: snapshots and state hashes between ticks. `tide_game_api.hash_world_on(w, jobs)` is that hash with what changed of the world hashed on a few of `jobs`' threads first, where it's megabytes (see ECS and simulation state): what sessions call, and only in the game's table, not the header. `tide_world_pack(w, out, capacity)` and `tide_world_unpack(w, data, size)`: the world as bytes, which hot reloading carries over; the same for the local state (`tide_local_pack`, `tide_local_unpack`, `tide_local_free`).
- `tide_world_pack_delta(w, base, need, need_size, &size)` and `tide_world_unpack_delta(w, base, data, size)`: the world as a delta (`tide/delta.h`), which sessions send: page by page, what differs from `base` (a world the receiver has too: changed pages go XOR'd with the base's), or from the receiver's own world, which lacks the pages `need` says, or the whole world. `tide_world_hash_pages(w, &size)` lists the pages' hashes, and `tide_world_need_pages(base, hashes, size, out, capacity)` says which of them a world lacks. Unpacking shares the base's pages that are the same and checks the world's hash. Storage a world gains (like the tables of tasks) goes in all of these as it does in packing, copying and hashing: what's left out stays in the struct's bytes, pointers and all.
- `tide_world_start(w, dt, start)`: `tide_world_init`, starting the match in the scene `start` names (`tide_start`, from `Session.Start`), or `Main` for NULL.
- `tide_world_start_seeded(w, dt, start, seed)`: the same with the match's seed, `Random.seed` (its low 31 bits, kept as `w->Time.seed`), only in a game that has one (see Random numbers, under Language). The two above start with seed 0. `tide_game.start` always takes the seed, and a game without one ignores it; `tide_game.seeded` says which.
- `tide_game_api`: the game as sessions run it (`tide_game` in `tide/session.h`): the world's size and functions, the input packed for the network, and its settings (`settings { ... }`): `tick_rate`, `title` and `stats` among them, 0, NULL and false where it sets none. They're in the generated `.c`, so they don't change `tide_game`'s hash, but for `max_players`, which is in the header too (`TIDE_GAME_PLAYERS`), as the world keeps an input for each. A session whose desc leaves `tick_rate` at 0 starts its matches at the game's rate, or 60; `tide_run_desc`'s `title` (`TITLE`, `--title`) goes over the game's, and `game_name` stands in when neither says.
- Local code's requests of the session (`Session.Start` and the like) wait in the local state: `tide_local_take_request(local, &request, &start)` takes them, in order. `Clipboard.Copy` goes the same way, as `TIDE_REQUEST_COPY`, after them, and hosts put its text on the clipboard (`tide_platform_copy`). Pasting is the platform's: Ctrl+V (Cmd+V) types the clipboard's text into `tide_devices.keyboard.text`, from the system's clipboard on desktop (GLFW's) and Android (Java's), and the browser's `paste` event on the web. Hosts tell local code where it stands with `tide_local_set_session(local, state, player, ping, server, open, room)` (`open` from `tide_session_status`, the room from `tide_platform_room_code`, `""` while the match is closed), `tide_local_connected(local)` and `tide_local_disconnected(local, reason, message)` (a kick's message, from `tide_session_event`). `tide_local_set_session` makes `Session.invite` the room; `tide_local_set_invite(local, invite)` after it replaces it (2026-10-21: `tide/host.h` passes `tide_platform_room_invite`'s, a page's link on the web; see `notes/webrtc-and-rooms.md`). Before each `tide_frame`, hosts give the frame's length with `tide_local_frame_time(local, seconds)` (`tide_host_game.frame_time`), which local tasks' `Wait.Seconds` counts down and `Frame.dt` reads (`tide_local.tide_frame_seconds`, in every game's local state, 0 until a host gives one). `Frame.dt` is local code's: views, local handlers and tasks, and the functions they call, which are handed the local state as those that reach files are (`decl.frame_time`, `check_frame_time_use` in `compiler/src/check.c`, `takes_local` in `codegen.c`); the match is told to read `Time.dt`. Its name is a pick the owner hasn't confirmed (`docs/spec.md`, Local state), and there's no clock of seconds beside it on purpose: a float of seconds loses precision after hours. Code that asks `Frame` for one is told what to write (the owner's card, 2026-10-08; `refuse_frame_clock` in `check.c`, before `resolve_builtin_member` and `resolve_builtin_call`): a member or a call by a clock's name in any case (`builtin_frame_clock` in `compiler/src/builtins.c` has the list: `time`, `t`, `now`, `elapsed`, `seconds`, Unity's `realtimeSinceStartup` and the like) keeps the error's first line, "Frame has no member 'time'", and gets two notes, the clock in local state added to with `Frame.dt` and wrapped, and `time.t` of `Time time`; in a system or a match handler, the second alone, as the match reads neither `Frame.dt` nor local state. Such a name gets no "did you mean 'dt'" (`Frame.t` did), so editors offer no change to `dt` for it. Any other name keeps the note it had, and a call of one still has none. The list, the call form and the match's own note are Claude's picks. Tests: `compiler/tests/errors/frame_clock`, `frame_clock_called`, `frame_clock_in_system` and `frame_unknown_member` (another name), and `lsp_gui` for the editor's side. `gone.message`, like `Session.room`, is kept beside the local state rather than in a field, so neither costs a game a heap.
- If the game has an input (it declares one, or systems take `Devices`), `TIDE_HAS_INPUT` is defined and `tide_input` names its type. `TIDE_GAME_PLAYERS` is how many players the game's matches take (its `maxPlayers` setting), and `TIDE_SERVER_INPUT` the server's slot in `tide_world`'s `inputs`, after theirs. `tide_input_sample(devices, local)` runs the input's `Sample` on the client, with this machine's local state: give it a copy of the devices that `tide_gui_hide(gui, &copy)` took what the GUI is using and what views claimed out of, then call `tide_devices_consume(devices)` on the real ones. The input holds what match code reads of the devices (`tide_dev`), everything else zero. `tide_world_set_input(w, player, input)` sets a player's input for the next tick, and `tide_world_set_server_input(w, input)` the server's, which entities without an owner read. Both repair NaN and infinite floats, apply the fields' `[Clamp]`, `[Min]` and `[Max]`, then run the input's `Sanitize`, if it has one.

## Confirmed frame/physics completion ABI (2026-10-11)

Generated tide_frame takes `(w, previous, alpha, verified, verified_previous, verified_alpha, local, draw, gui)`. Host API callbacks, standard hosts and every repository caller migrate together. Single-world callers use NULL/1 for confirmed previous/fraction. tide_game adds optional view-time input accessors and max_rewind; enabled inputs gain the engine-owned timestamp. Extern-system ticks carry deterministic transient completion slots and call the approved rows completion hook after queued changes. Collider history is ordinary match state, while slots and readonly query contexts contribute no live-world mutation.
Merge integration: the incoming LOD and Rooms page test hosts also pass NULL/1 for the confirmed interval; their single-world frame behavior is unchanged.

## Prefab source sets (2026-10-12)

The default tide_add_game source glob includes .tprefab. Explicit SOURCES already
accepts it as a Tide compiler input, and PACKAGES now classifies both extensions
as source paths rather than treating a .tprefab path as a package name. Registered
manifest lists/folders retain the existing game context used by tidels. The prefab
e2e target compiles separate .tide and .tprefab sources on native and web.
