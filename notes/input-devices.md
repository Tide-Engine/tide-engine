## Layout

### Runtime written by Claude for now

- `platform/` (the platform layer), `demo/`, `bench/`, `relay/`, `builds/` and `packages/` are Claude's too, on the same terms.
  - The platform layer reads keys by physical position everywhere. On the web, the page reads the DOM's `code`, never the typed character, which follows the keyboard layout. `platform/tests/web_keys.c` guards this with AZERTY-style events. Hosts and views should read input from `Devices` too, never the window's own (GLFW's key functions).
  - The characters typed, which do follow the layout, are a separate channel (`tide_devices.keyboard.text`, since the last poll) that the GUI and views read (`devices.keyboard.text`), and samples never. A poll takes up to `TIDE_TEXT_MAX` (32) of them, and the platform keeps the rest for the next polls, so a long paste comes over a few frames.
  - A key or mouse button pressed and released between two frames reads as held for one, on every platform, so taps aren't lost when frames are slow: each window keeps what's held and what was pressed since it was last asked (not GLFW's sticky keys, which also hold every key a frame past its release). A finger that touches and lifts between two polls does too (`engine/src/devices.c`).
  - A finger is the touchscreen's, never the mouse's, as in Unity's Input System. Platforms report fingers as events (`tide_touch_event`), and the engine keeps their slots and ids. On the web, the page reads the canvas's pointer events and cancels its touch events' defaults, so the browser makes no mouse of them (`platform/tests/web_touch.c`); a game in a page that scrolls leaves that page a finger's swipes until a tap (`embedded`, see Web builds). On Windows, the window's `WM_POINTER` messages for touch are handled before GLFW's (`platform/src/touch_win32.c`), so the system makes no mouse of them either. GLFW has no touch, so other desktops have none yet.
  - A finger keeps its slot while it touches, and once it lifted, until a sample cleared it (`tide_devices_consume`), so the next sample reads a tap that came and went between two. No finger is left out for that: one that touches with no slot free takes the slot of the finger that lifted longest ago (`free_slot` in `engine/src/devices.c`, by `tide_touch.rested`, the polls since it lifted, so a finger that lifted in the same poll is the last to go), whose lift the next sample then doesn't see. That's every touch past the tenth in a host that never consumes: a touchscreen stopped answering after ten taps in a game with no input and outside a match, before the standard host cleared the devices there itself. A finger is only left out while ten still touch. `devices_fingers_keep_coming_where_nothing_samples` and its neighbors in `tests/test_devices.c` check the slots, `gui_buttons_answer_every_tap_where_nothing_samples` in `tests/test_gui.c` the GUI's buttons, and `platform/tests/web_touch.c` ends with 25 taps that nothing samples.
  - The pointer (`tide_pointer_poll`) follows the mouse or the primary touch, whichever was used last, as Unity's `Pointer.current`, and the GUI follows the pointer. A host that fills the devices itself calls it, or the GUI sees no mouse. On a machine with both, the pointer goes from where the mouse rests to where a finger lands with nothing between, and presses in the frame it arrives: the GUI finds the widget under it by where it is now (`on_top`, see `notes/gui.md`).
  - A finger that lifted leaves the pointer where it lifted: the primary touch is empty once a sample saw the lift, which is no place, so the pointer keeps its own until another finger touches or the mouse is used (`devices_pointer_stays_where_a_finger_lifted`). It read (0, 0) from then on, and a view that followed `devices.pointer.position` jumped to the screen's corner.
  - A view reads a finger's `press.up` in the frame it lifts, with its id and where it was, whether a sample emptied its slot before the frame's GUI began (a tick every frame) or none did (`frame_touch` in `engine/src/gui.c`; `gui_views_see_a_finger_lift_whenever_the_game_samples`). With a sample between, the lift was never true for a view: at 60 ticks a second, never at all.
  - The cursor's lock (`Cursor.Lock()`, `Cursor.locked`) is asked for frame by frame and read back, never assumed (agreed). The GUI collects the frame's ask (`tide_gui_lock_cursor`, as `GUI.ShowKeyboard`'s), a host passes it on every frame (`tide_platform_cursor_lock(tide_gui_cursor_lock(gui))`), and the next poll says whether the window holds the cursor: `tide_devices.mouse.locked`, platform state like `poll_delta`, which `Cursor.locked` reads (the match never: `tide_keep_devices` leaves it zero). There's no unlock: a frame that doesn't ask lets the cursor go. While it's locked, the window says the position it had when it was locked, and what the mouse itself moved (`tide_window_mouse.moved_x`, `moved_y`), which is the delta; a mouse whose cursor is locked is on no widget (`cursor_hidden` in `engine/src/gui.c`), so nothing hovers, a click is the game's, and a button still held as the cursor comes back presses nothing. A finger isn't the mouse, and still presses what it touches. What each system does is its own, and none of it is worked around with a timer:
    - The web (`platform/web/tide.js`): a browser only gives the lock when it's asked from a click or a key press, so the page asks at the next one on the canvas while the game wants it, and at once when the game starts wanting it if one still counts (`navigator.userActivation`), as after a Resume button's click. The browser takes the lock back when the player presses Escape, which the page can't prevent and may never see the key of (so Escape never asks, nor a held key's repeats), and when the page loses the focus or is hidden, and for a moment after Escape it refuses. The page says what the browser says (`pointerlockchange`, `pointerlockerror`) and never asks again on its own: a lock refused or taken back waits for the next click or key press. It asks for the mouse's own movement (`unadjustedMovement`), and for the usual kind where the system has none. Locked, movement is the events' `movementX` and `movementY`, as positions stop changing. A hot reload keeps the canvas and the page's state, so the new build reads it. `tide_platform_web_cursor` stands in for the browser, which gives a script's events no lock, and checks all of this.
    - Desktop (`platform/desktop/glfw.c`): GLFW's disabled cursor, with raw motion where the system supports it. Only a window with the focus holds the cursor: Alt+Tab lets it go (`Cursor.locked` is false meanwhile), and coming back takes it again while the game still asks (`follow_lock`, at every poll and every ask). Escape gives the cursor back to the player, as a browser does (agreed), though the game still asks and still gets the key: the player's next click on the window, or press of another key (not one still held, repeating), takes it again, and Escape never does. A game that stops asking starts over, so one whose Escape is its pause menu holds the cursor at once when it asks again (Resume, or Escape once more): a browser's wait for a click isn't copied. When the window holds the cursor is `platform/desktop/cursor.h`, apart from GLFW, so `tide_platform_cursor_rules` checks it with no window. A test's window is hidden and never has the focus, so `tide_platform_cursor` (label `gpu`) only checks that side; nothing checks GLFW's part of a held lock without taking the screen and the mouse.
    - Android never locks it, yet: NativeActivity has no view to capture the pointer with.
  - Phones show their keyboard while the player types into the GUI, or into what a view said shows it, `GUI.ShowKeyboard()` (`tide_platform_typing(tide_gui_typing(gui))`, once a frame). On the web, the page focuses a hidden field of its own, whose input comes as characters typed and its deletions as Backspace, as phones' keyboards say no key positions (`platform/tests/web_keys.c`). On Android, NativeActivity's view can't take the focus, so the window's view takes it, on Android's main thread, which the program reaches through a pipe on that thread's looper; the keyboard's keys still come to the input queue, and Java's `KeyEvent` says the character each types.
  - Pixels (the window's size, the mouse, what's drawn) are the display's logical pixels, as a browser's CSS pixels are, and rendering is at the display's full resolution: on desktop the window's framebuffer, as many times its logical size as GLFW says its contents are scaled (`GLFW_SCALE_TO_MONITOR`), and on the web a canvas `devicePixelRatio` times its CSS size. Render targets are the same: sized in logical pixels, with the display's pixels in each unless they say otherwise (see Rendering and platform).
  - `tide_platform_run` never returns (on the web, the browser drives the frames), so hosts do all their work in the frame function.
