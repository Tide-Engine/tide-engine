# Code the GPU runs: frags and verts

## SPIR-V, for Vulkan (2026-10-14)

tidec writes SPIR-V by translating the WGSL it already writes, rather than with a third emitter over the tree. The WGSL has WebGPU's bindings and its depth conversion already. The same translator takes the renderer's hand-written WGSL too (`notes/rendering.md`, Vulkan). The translator is `compiler/src/spirv.c` (`spirv.h`: `tide_wgsl_to_spirv`), about 3,700 lines of C with no dependency.

- **What it does:** it reads WGSL into a tree and writes SPIR-V 1.3 (Vulkan 1.1 rules) as it works the types out, in one module whose entry points are `vertex` and `fragment`.
  - It writes no `OpName`s.
  - It takes what tidec and the renderer write, and WGSL generally as far as frags and verts go:
    - structs, uniform blocks laid out by WGSL's rules, `var<private>`, textures and samplers;
    - functions with `ptr<function, T>` parameters;
    - abstract numbers, folded where both sides are;
    - constructors, conversions and `bitcast`;
    - every built-in tidec and the renderer call, and more of GLSL.std.450's;
    - `textureSample`, `...Level`, `...Grad`, `...Bias`, `...Compare(Level)`, `textureLoad`, `textureDimensions`, levels and samples;
    - `if`, `for`, `while`, `loop`/`continuing`/`break if`, `switch` with several selectors and `default` among them, `break`, `continue`, `discard` (`OpKill`) and `return`.
  - It doesn't take storage buffers, atomics, workgroups or compute, `alias`, `override`, or f16.
- **What's out of range is made safe the way WebGPU (Tint) makes it, so a shader reads the same on both:**
  - integer `/` and `%` by zero, or the least i32 by -1, go by 1;
  - shift counts are masked to 5 bits;
  - float to int saturates (`FClamp` before `OpConvertFToS`/`U`);
  - an index into a vector, matrix or array that isn't a constant is clamped to the last element (`UMin`), and a constant one is clamped as it's written.
  - Reads past a buffer's or image's end are the device's robustness features' job (`robustImageAccess`, `robustBufferAccess`, enabled where present).
- **Structured control flow:** the patterns are glslang's.
  - A loop is its header (`OpLoopMerge`), a block for its condition (`OpBranchConditional` to the body or the merge), the body, and its continue block, which does a `for`'s step or a `continuing` and branches back.
  - `&&` and `||` whose right side calls a function of the module's become a selection with an `OpPhi`; otherwise they're `OpLogicalAnd`/`Or`.
  - Code after a `return`, `break`, `continue` or `discard` is dropped as dead.
  - A construct whose merge nothing reaches ends in `OpUnreachable`. A `switch`'s merge is reached by any case that falls off its end and by any `break` to it. A first version missed the `break`s; that dropped the code after such a switch, and the `Rest` and `ListSum` probes of `tide_platform_shaders` caught it on Vulkan.
- **Codegen:**
  - Each shader's words go in the generated C as `tide_shader_<n>_spirv`, with `.spirv` and `.spirv_words` set in its `tide_shader`, all under `#ifdef TIDE_SPIRV` (`tide/draw.h`: defined off the web and Android).
  - The shader's id is still the hash of its GLSL and WGSL, which the SPIR-V is made of.
  - A translation that fails is tidec's bug. It's an error naming the shader, and the build stops: codegen returns false after `gen_shaders`.
  - `tide_shader` grew two fields, so hosts, libraries and generated games rebuild together.
- **`tidec --spirv <dir>`** writes each shader's module as `<n>.spv`, in `--shaders`' order. `tidec_spirv_<name>` (`compiler/tests/expect_spirv.cmake`) runs it on every `compiler/tests/shaders/*.tide` and has the SDK's `spirv-val --target-env vulkan1.1` check each module. `tide_spirv_shaders_valid` (`platform/tests/spirv_shaders.cmake`) does the same for the renderer's seven. Both exist where CMake finds `spirv-val` (`cmake/VulkanTests.cmake`).
- **Tested:** all 81 golden shaders and the 7 built-ins pass `spirv-val`. Every game in the repo builds, so tidec translated every shader it has. The validation layer checks each module again as the GPU tests make their pipelines. `tide_platform_shaders` compares the CPU's and the GPU's results through the SPIR-V on this machine's NVIDIA driver.
- **Not done:** `OpName`s for debuggers (RenderDoc shows ids); `OpDemoteToHelperInvocation` for `discard`. That would matter only for derivatives taken after a discard in the same quad, which tidec's frags don't do: they ask for theirs as they start.

## Delayed locals and switch values, 2026-10-11

The CPU's definite-assignment rules also check delayed locals in frags, verts
and their helpers. Switch expressions lower to a captured selector and a
result variable assigned by one GLSL/WGSL switch arm. Each arm declares its
own out locals and emits its own effect prelude. Surrounding operands are
captured in source order; conditional and short-circuit branches retain their
laziness. Mutable/out arguments remain writable places. Statements declare
outer out locals before their preludes.

Loop headers containing switch expressions lower to a loop that reevaluates
the selector each iteration, with a for's step at the next iteration's start
so continue still reaches it. Existing GPU type, increment and for-header
out-declaration restrictions remain. No runtime or shader binding changed.
`compiler/tests/shaders/switch_values` pins GLSL and WGSL. `SwitchProbe` in
`platform/tests/shaders.tide` checks delayed branch initialization, single
selection and source-order effects, skipped/nested branches, arm-local out
variables and for/while/continue behavior against CPU results in both stages.
Final native OpenGL, web WebGL and WebGPU results are recorded with language
validation in `notes/language.md`; other platforms require CI.

Contextual enum shorthand (2026-10-11): owner-approved `.Member` resolves to
the ordinary checked enum member before GPU lowering. The `lit` and `maps`
fixtures use it in comparisons and helper arguments; `declared` and `cubemaps`
use it in fixed Sample filter/wrap arguments. Their existing GLSL/WGSL goldens
remain byte-for-byte unchanged. No shader writer or backend change is needed;
language and editor contracts are in `notes/language.md` and `notes/editors.md`.

Build notes, moved here from `AGENTS.md` as they were: what's built, what code relies on, the tests and the measurements. `AGENTS.md` has the rules every session needs and the index of these files. The headings below are that file's sections as they were, and "see <Section>" names one of them: the index says which files each is in. What a note calls "below" or "above" may be in another of these files now: search `notes/` for its name.

## Rendering and platform

- Enum counts (2026-10-11): `CALL_ENUM_COUNT` emits the checked declaration
  count as an integer literal in GLSL and WGSL, matching generated C and
  compile-time folding. No uniforms, runtime functions or enum layout changes.
  `compiler/tests/shaders/enum_count` pins both stages/languages with plain and
  qualified enum types, byte-backed sparse values and aliases, constants and

  through the same code in a frag and a vert. Golden checks and the CPU/GPU
  probe pass in the full native/web debug suites on OpenGL, WebGL and WebGPU.

- **Degree literals on the GPU** (2026-10-10): lowercase `deg` on a decimal
  literal is an ordinary float in radians. GLSL and WGSL emit the parser's
  converted binary32 value, shared with generated C, instead of converting

  leading-point, exponent, separator and unary-minus forms in both stages.
  The quaternion probes in `platform/tests/shaders.tide` compare degree
  constants exactly with the CPU's and check their angles and rotations
  against `Math.Radians` within the existing GPU math tolerance.

- **Scalar quaternion Euler arguments** (2026-10-10): `quaternion.Euler(x, y, z)`
  packs its three checked float arguments into the existing `H_EULER_Q` helper
  in both GLSL and WGSL. It retains the vector overload's radians and ZXY
  rotation order; integer arguments widen normally and named arguments use
  the checker's settled x/y/z order. The vector overload and helper formula
  are unchanged. `compiler/tests/shaders/math` pins scalar float, integer and
  reordered named calls in both stages. `platform/tests/shaders.tide` adds
  these forms to the existing CPU-versus-frag/vert quaternion probes, including
  comparisons with vector Euler results to check argument placement.
  Validation: GLSL/WGSL golden pins and the quaternion probes pass on OpenGL,
  WebGL 2 and WebGPU; all 2,016 native debug tests pass.

### Skinned vertex stage

- `Draw.SkinnedMesh` plans `shader.skinned` (2026-10-08), including plain Vertex3 draws without a user stage. Two existing integer data textures carry the palette and hidden influence ranges/pairs (`shader_texture.skin` 1 and 2; 0 is an ordinary texture), using three draw-uniform ints for their counts. They consume normal texture slots and add no vertex fields. The compiler reserves one hidden instance int word for a palette atlas's matrix base, after the user's int words; an existing int4's spare lane is used first. If another int4 would exceed the portable 16-attribute limit, the shader keeps an individual palette with an implicit zero base. Valid user layouts stay valid.
- Atlas-capable wrappers call `tide_draw_skinned_atlas(..., textures[2], info[4])`: `info[0..2]` keep the palette, vertex and influence counts, and `info[3]` fills `shader.skin_base_at` in the packed instance ints. Saturated wrappers keep `tide_draw_skinned_data(..., info[3])`. The vertex stage first bounds a joint against the current pose's palette count, then reads matrix `(base + joint)`; the atlas's other poses do not widen those bounds. GLSL and WGSL use the same integer arithmetic and word packing. The renderer calls `tide_draw_prepare` before consuming deferred palette pixels; a C host that inspects them directly must prepare too. No sampling, operand evaluation or custom-vert placement order changes.
- GLSL indexes the hidden stream with `gl_VertexID`, WGSL with `vertex_index`. Both sum every supplied influence, divide by total weight and deform position before calling the user's vert. If V has `float3 normal`, it uses the cofactor normal matrix of the blended skin matrix, determinant-sign corrected and normalized. A float3/float4 tangent follows the blended linear matrix, is orthogonalized against the normal and normalized; float4 handedness changes when the bone deformation mirrors. Existing zero-length normalization and singular-matrix behavior apply. The draw transform and camera follow, and `instance.Normal` still only applies the outer draw transform.
- Explicit vertex placement uses that same posed vertex: `this.clip` projects its current position through the outer transform and camera, and a vert's `out float4` replaces automatic projection. Later changes to the vertex still feed the frag's `this.world`; they do not replace the captured clip output. Skinning runs once before user code for both placement forms. The skinned shader golden puts a handed struct before the clip parameter to pin parameter order, and the GPU fixture distinguishes posed clip placement, later world changes and accidental automatic placement.
- Model handles (Pose, Skeleton, Animation, Bone and catalogs) are CPU-only, also through ordinary functions a shader reaches and through wrapper structs. Shader type analysis rejects their opaque hidden state; `BoneTransform` remains its ordinary ten-float numeric struct. Hidden model fields cannot be supplied in a source literal. `gpu_skinned_helper` and `gpu_skinned_wrapped` pin the GPU restrictions.
- Numeric `BoneTransform { }` and `default` work in shaders: zero position, identity rotation and unit scale, represented by ordinary typed default expressions rather than C-only placeholders. `compiler/tests/shaders/bone_transform_defaults` pins GLSL/WGSL, and the custom vert in `platform/tests/skinned.tide` checks their values on all three backends.
- `compiler/tests/shaders/skinned` pins both languages for plain, textured, custom-vert/frag, explicit clip placement and render-target draws, beside an ordinary Mesh using the same V. `skinned_attribute_limit` pins a base in the last spare int lane at 16 attributes and a fully occupied layout's zero-base fallback; its E2E also checks user int words, distinct instance bases, automatic batching and individual fallback captures. The rest and borrow E2Es prepare before inspecting captured matrices, including independent poses merged into one run. `tide_platform_skinned` checks twelve pixels for eight influences per vertex, normals/tangents/default vertex fields visible in a custom vert, independent pose captures, explicit placement and matching color/depth passes, twice to check retained resources. No GPU result enters simulation state. Different poses can share an automatic instance run when their shader, mesh, atlas page, other textures, uniforms and draw settings match; no new explicit skinned-instance syntax was added.

- A game's code runs on the GPU as `frag` (once for each pixel) and `vert` (once for each vertex), declarations like views, which a `Draw.Mesh`, or a target's `Mesh`, names after its other arguments, for 2D and 3D meshes of any vertex struct with a `position` (`docs/spec.md`, Views and drawing; `docs/game/shaders.md`). Their signature says what they read and the engine supplies it: the vertex first, a frag's pixel as `out Color`, components of the entity the calling view runs for, singletons, and the built-in `Instance`. Manual instancing can also supply one read-only ordinary struct from its list, a draw one read-only `Texture`, its explicit source, and a draw one more read-only struct, its values, written after the vert and the frag (below). No individual plain value parameters, no return value (decided: ECS style).
  - **A frag's `this` is the pixel it runs for** (agreed 2026-10-07), as a system's is its entity. It needs no parameter: `this.world` is its `float3` place on the mesh in the world, `this.position` its `float2` place in the destination's logical pixels from the top left, and `this.depth` its `float` depth from 0 at the near side to 1 at the far side. The fields are read-only. `this.Discard()` leaves the pixel undrawn, writing no color, depth or stencil, and ends the frag there, with nothing owed to its `out` parameters. A vert has no pixel yet: its `this` is its vertex as the engine would place it (below: A vert puts its vertex itself). Ordinary helper functions inherit none, so take any coordinates they need as values. The old built-in `Pixel pixel` parameter is an error that says to remove it and use `this`; a game's own type named `Pixel` is still its own.
  - **What a frag and a vert write is `out`** (agreed 2026-10-07, built the same day; `docs/spec.md`, Views and drawing, Code the GPU runs, with the picks under Provisional there): a frag's color is `out Color color` (the owner's idea, now that `out` is a keyword), and a vert hands its frag a struct of its own, `vert Place(mut Corner corner, out FromLamp lamp, Sun sun)` and `frag Look(Corner corner, FromLamp lamp, out Color color)`, which the GPU blends across the triangle, so what a vert works out needs no field in every vertex of the mesh. A vert's vertex stays `mut`. What's built, and what code relies on:
    - **The parser lets `out` through for these two alone** (`parse_query_params` in `compiler/src/parser.c`, by `d->kind == DECL_SHADER`): `param.is_out` with `mode` `PARAM_MUT`, as a function's. A system's, a view's and a handler's `out` is the error it was. `param.mode_word` is the `mut` or `out` token as written, which the checker hands `suggest_replacement` for the quick fixes (`mut` to `out`, and `out` to `mut` on a vert's vertex).
    - **`check_shader_decl`** (`compiler/src/check.c`) sorts each parameter: the vertex first; a frag's `out Color`s, four at the most (`decl.outputs`, each one's place in `param.output`; an `out` of another type is the "isn't there yet" error); a vert's `out` structs, as many as it likes, each type once, whose fields have to blend (`check_handed_struct`: floats, their vectors and colors; an int, bool, enum, matrix, quaternion or struct is an error there); and the rest as before. `mut Color color` is an error that names `out`, and so is `mut` on a vert's struct; each then goes on as the `out` it meant (`is_out` set, `out_at` left alone, so editors show the word as written), so nothing else is said of it.
    - **A frag's read-only struct is its vert's or its instances' (or, since, its draw's values: see A draw's values, below), and the draw says which** (`check_shader_binding`, `shader_writes`): by type, as a system finds a component. The draw's vert writes it, or the draw is `Instanced` over a list of it; neither is the error at the draw ("frag 'Look' reads a 'FromLamp', which vert 'Lift' doesn't write", or "...and this draw names no vert that writes one"), which took the place of the two "reads instance data" messages for frags (a vert's are as they were, and a vert still takes one instance struct, a frag any number of structs). A vert that writes the type the draw's instances are is an error there too. Where an `Instanced` draw's list is written as a literal, its element type is taken from the first struct the vert or the frag reads that the vert doesn't write.
    - **Definite assignment is what makes a frag write its color** (`compiler/src/assigned.c`, which `check_method_body` now runs for frags and verts too): the same pass as a function's `out` parameters, with messages of its own (`gpu`): "frag 'Shade' can end without writing its pixel's color, 'color'", "'color' is read before it's written", "vert 'Place' can end without writing 'lamp.glow'". `this.Discard()` ends a path with nothing owed, as `fail` does (`CALL_DISCARD` in `flow_stmt`). One level: a field of a struct in it, and a vector's or a color's component, is a part of that field.
    - **In the shaders** (`compiler/src/shader.c`): `shader.handed` is what a combination's vert writes (`shader_handed`: the struct, the vert's parameter, the frag's parameter of that type or NULL, and which fields the frag reads), made in `plan`. While checking (`em->sh` is NULL) both go the bound way, which only notes what's read. Each field carried counts among the 15 values corner-to-pixel checked at the draw.

  - **A draw's values: a struct after its vert and frag, the same for the whole draw** (card 4 of the reshaping, built 2026-10-07. That `Mesh` and `Blit` take a struct their frag reads, bound as an `Instanced` draw's is, is the owner's, with the example `Draw.Blit(src, dst, Blur, BlurParams { direction = float2(1, 0) })`; where it's written elsewhere, what it can be and each error are Claude's picks, Provisional in `docs/spec.md`, Views and drawing, A draw's values): `Draw.Mesh(..., vert, frag, values)`, `Draw.Instanced(..., vert, frag, values)`, a target's two, and `Draw.Blit(source, destination[, blend], frag, values)`. `docs/game/shaders.md` (Values for one draw) is the users' page.   - **A function is written for the textures it's called with, as for lists** (`ex_user_call`, `need_function`): `emit.spec` is a `given` a parameter, the list or grid (`data`) and the frag's expression for a texture (`sampled`); such a parameter (`is_given`) is in neither the function's head nor the call; and the suffix's number for a texture is the first of the shader's textures that's a way it's read (`texture_number`), a grid's still its texture of numbers where it has one. Each of the shader's textures is one source's, so no two sources share a number, and a source that's read no way gets 0, which no function's text then depends on. So every pin of `compiler/tests/shaders/` is as it was.
  - **The body is checked once, so what it samples is kept on it** (`decl.gpu_samples`, a `function_sample` each: which parameter, or the asset's name, the kind of read, and the filter and the wrap as the `Sample` says them, -1 for what it leaves to the texture). `pass_samples`, from `ex_user_call` while checking, hands them on: in a frag or vert, each becomes a sample of the root's for the texture the call names (`sampling_of` with that texture: what's unsaid is resolved there, by source); in a function, one of that function's own, by its own parameter or the asset. **A function's Sample that never reaches `pass_samples` reads a texture the shader hasn't got**: everything that calls a function goes through `ex_user_call`.
  - **Filter.Trilinear never works through a function** (`pass_samples`, in what a frag reaches): a frag asks how fast a uv changes as it starts (`lifts` in `ex_sample`, which wants `em->code == em->root`), and a function's uv is its call's. One that says Trilinear, or leaves its filter to a texture declared so, is an error at the Sample, with the frag and the call as a note; one that leaves it to a `Texture` that may say it (`!filter_said`, in a game that names Trilinear) is a warning, once a Sample however many frags and textures reach it (`function_sample.warned`; `refused` is the error's, so a Sample that warned for one texture still refuses another). What's written reads the texture's own pixels (`textureLod`, `textureSampleLevel`). A vert's reach says nothing, as a vert's own Sample doesn't.
  - **A function's texture parameter is no value** (`ex_name`): named anywhere but as a Sample's object or an argument, it's `type_fits`'s error, as nothing is written for it. A texture argument that's no name is `refuse_texture`'s ("a texture a function samples is one the frag or vert was given, by a name"); a `mut` one is refused in the head, as a list's.
  - **Generated C is what a frag that sampled itself gives:** codegen goes by `shader.textures`, which the root's samples make. A game with no function that takes a texture generates the C and the shaders it did (below).
  - **A grid parameter is still one of the shader's textures of numbers, read or not** (`data_of` notes it where the argument is resolved): one that's only sampled costs a binding of the 8 and its size's ints, with no texture behind it. A function that only samples takes a `Texture`.
  - **Editors** (`compiler/lsp/analysis.c`): completion offers `Sample` and `Compare` on a `DepthTexture`, `Sample` on a `Texture` and on a `Cubemap`, in any function or method (`samples`), where they were a frag's, a vert's and a `gpu_only` function's; the hovers of the three types and of their reads say a function takes one.
  - **Sumo and Tag have one lookup each** (`Sunlight` in `examples/sumo/light.tide`; `SunlightAcross`, two looks, and `Sunlight`, two of those, in `examples/samples/tag/light.tide`). ## T? fields (2026-10-11)

Code the GPU runs has no values that may be missing, so a `T?` field read there is the error any `T?` is (`type_fits` in `compiler/src/shader.c`). A component or a singleton that has one still gives a frag or a vert its other fields, as only the parts code reads are sent. A struct that has one, or holds a struct that does (`optional_field_in`), isn't a GPU value at all: a local of it, a parameter, a draw's values or `sun.tone.gain` through it is an error that names the field, since the struct the field is kept as would have to be declared in GLSL and WGSL, and is no type of the language's to read. A mesh's vertex with one is refused by the vertex rules. Goldens are unchanged. `compiler/tests/errors/optional_field_gpu_struct`, `optional_field_gpu_read` and `optional_field_vertex`.
