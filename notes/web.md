# Web builds

Browser playground (2026-10-14): `Tide.reload = 'manual'` opts the docs preview
into supplied builds. After device setup, `Tide.ready()` is called with
`Tide.replace(bytes, pack, fresh = false)` and `Tide.restart()` installed.
These provisional JS host properties reuse the watching page's replace/save/
migration path, serialize replacements and restarts, copy submitted bytes and
retain the last successfully installed program for restart. The first install
is fresh; later ones migrate unless explicitly reset. A module that fails to
instantiate leaves the running program, room, assets and restart cache intact.
There is no /build poll in manual mode. Existing watched and standalone paths
are unchanged; all new lines are inside the excluded `tide run` markers.
`tide.release.js` remains 68,931 bytes; its source fingerprint was regenerated.
The docs compiler worker/bundle and integration checks are in notes/docs-site.md.

Texture compression (2026-10-11): WebGL enables `WEBGL_compressed_texture_s3tc` before querying supported formats; WebGPU requests `texture-compression-bc` only when advertised, alongside optional timestamps. Timestamp failure retains BC support on a fresh adapter; an adapter without requested optional features still gets a plain device request. BC uploads include physical block extents for tail mips. Missing format support uses the existing RGBA upload path. Test pages can disable compression with `?texture-compression=off` (or `Tide.textureCompression = false`); renderer fallback checks run on both web backends and repeat after WebGPU device loss. The checked-in release runtime was regenerated with the pinned toolchain (66,519 bytes). Contracts and final validation are in `notes/textures.md`.

Multisampled depth (2026-10-13): `gpu_resolve_depth` in `tide.js` and its import in `gpu_web.c` make a multisampled WebGPU target's depth a texture a shader reads (`notes/render-targets.md`). WebGL 2 goes through `gpu_gl.c`'s blit with functions the page already had. The checked-in release runtime was regenerated with `node cmake/web_runtime.mjs --write` (68,931 bytes).

A request's time limit (2026-10-11): `startFetch` in `tide.js` takes the seconds a request may take and aborts it with a timer (`AbortController`), ending it as `timedOut` (11, `TIDE_IO_TIMED_OUT`); `io_request_begin` gained the parameter, and `io_fetch_forget` clears the timer. The checked-in release runtime was regenerated with `node cmake/web_runtime.mjs --write` (67,144 bytes). Contracts and tests are in `notes/assets-and-files.md`.

## Building

### Web builds

- Standalone release pages use checked-in `platform/web/tide.release.js` and gzip program/pack payloads only when smaller (2026-10-10). The runtime detects gzip magic after base64 decoding and inflates synchronously before WASM instantiation or asset loading, checking the output length and CRC32; raw payloads still work. Debug and watched pages keep `tide.js` and raw bytes. CMake Release/MinSizeRel selects the generated runtime; CLI release builds select the installed copy, with embedded clang's existing zlib supplying compression. The gzip header fixes mtime to zero and OS to 255 for reproducible output. No engine ABI, WASM import, worker-message or public page property is renamed.
  - `cmake/web_runtime.mjs --write` is a maintainer step after `npm ci --prefix docs`, pinned to the existing Rolldown 1.2.12. It tree-shakes only synchronous gunzip from fflate 0.8.3 (upstream commit `a661bab4c135c368b6e68af3be1904f89ed070cf`), then removes comments/whitespace and mangles local identifiers with compression and property mangling disabled. Keeping scope boundaries matters because `threadMain` is serialized for workers. fflate's MIT notice is included in every generated page and installed under `licenses/fflate/`.
  - `tide.release.json` records normalized source/generator/vendor hashes and the generated output hash. `cmake/WebRuntime.cmake` validates them with CMake alone, including on fresh checkouts without npm dependencies; `--check` does the same with Node's built-ins. Only regeneration needs docs dependencies. Paths are canonical before entering `CMAKE_CONFIGURE_DEPENDS`, to avoid Ninja seeing the included verification file under two spellings. The checked-in runtime is 65,134 bytes with its decoder, checksum checks and full license notice, versus the previous shipped readable runtime's 148,672 bytes on this checkout.
  - Matched controls using the same final decoded WASM/pack and shell measured minimal HTML at 953,958 -> 394,619 bytes (-58.63%), Duel at 1,531,082 -> 609,187 (-60.21%) and the retained-image fixture at 1,056,344 -> 424,189 (-59.84%), before HTTP compression. The final CLI supplied the 65,134-byte runtime in each page. The final decoder, including CRC validation, took approximately 6.0/10.5/6.8 ms for minimal/Duel/retained-image WASM under warmed Node/V8. These local startup measurements exclude base64 decoding and WASM compilation, and are not browser or cold-start guarantees. No DecompressionStream API or new browser baseline is required.
  - `tide_web_runtime` passed its three checks of generated-source freshness without loading minifier dependencies, inline license/hot-reload exclusion, exact bytes across gzip levels, empty/tiny payloads, corruption/CRC/ISIZE errors and debug/raw versus release/compressed page generation. The generated runtime passed 240 identical thread-test ticks and 24 skinning pixel checks on both file-page WebGL and served WebGPU. A staged CLI release page passed on served WebGL and WebGPU with separately compressed WASM (672,172 -> 271,538 bytes) and BMP pack (16,560 -> 205 bytes), asserting decoded dimensions and exact RGBA values. All browsers were muted. CMake tracks the page writer itself in `LINK_DEPENDS`, so compression/paging changes regenerate existing pages.
- The `web-debug` and `web-release` presets build everything as WebAssembly with clang's own wasm target and wasi-libc, not Emscripten: `cmake --workflow --preset web-debug` (see `cmake/wasi-toolchain.cmake`). They need clang with `wasm-ld` (LLVM's releases have it; on Linux, the distribution's `lld`) and Node. wasi-sdk's C library is downloaded once into `build/wasi-sdk-<version>`, pinned.
- Tests run under Node's WASI through CTest (`cmake/run_wasi.mjs`), so the determinism hashes cover exactly what ships. Games generate their C with a native tidec, which web builds build first in `<build>/host` (`cmake/HostTidec.cmake`), with the same `TIDE_VERSION`, which `#if TIDE_0_3_OR_NEWER` reads (`compiler/src/version.c`).
- In the browser, `platform/web/tide.js` runs the program: the canvas, input and frame loop (`platform/web/tide_web.h`), what the renderer draws with (WebGPU, or the OpenGL ES 3 functions of `platform/src/gl.h` on WebGL 2: see Rendering and platform), and the few WASI functions wasi-libc needs. The platform layer's window there is the page's canvas (`platform/web/canvas.c`). A web page is one self-contained `.html` with the program inside (`cmake/web_page.mjs`, or tide).
- A page's address says a few of the things a command line does (`tide.js`, where it makes the program's arguments): `debug-views` is `--debug-views`, and `host` and `join=<code>` are `--host` and `--join <code>`, unless the page's own `Tide.arguments` say which match; so a link can be an invitation, and a page that shows games in frames can put them in one match (the docs' examples do: see Docs site). For such a page, `Tide.room` is the code of the room the program hosts or joined, `""` for none, read as it is at that moment. `Tide.lag`, or `lag=<ms>` in the address, is the round trip to its match's server the page's player is to have (2 seconds at most), which the page can change as the game runs: latency to look at with both players at one desk, since nothing else gives a page any. These three are Provisional: picks of the docs' examples' that the owner hasn't confirmed, but for what a lag means (below).
  - A lag is a ping (agreed 2026-10-05): the session's, the network's whole round trip to the match's server (see Networking), with what the network takes already in it. A lag of 100 reads as a ping of 100: not 100 each way, and not 100 more than the player had.
  - So the page has to know the ping. The session measures it, and a host says it every frame: `tide_platform_room_ping(ping_ms, answer_ms)` (`platform/src/rooms.c`; nothing on desktop), which `tide/host.h` calls with its client's `ping_ms` and `answer_ms`, the ping -1 (none) for a machine that runs the server and for one not in the match yet: the round trips of joining aren't like a match's. A host that never says gets the lag on top of its ping.
  - The page adds what's missing (`added` in `tide.js`: the lag less `rest`, what the ping is with nothing added), half to what it sends and half to what it receives, so each way is late by as much. What it holds back arrives, to the program, when it's let go: the datagram's arrival, which the ping is measured to (`room_arrived`), is noted then.
  - A ping less what's added is what it is by itself only if all of its trip went under what's added now, so only trips that set out after that last changed count (`room_ping`: `answer_ms` ago, which is by the program's frames, a frame's work behind the page's clock, so not within 50 ms of the change), and never one said again with nothing heard since. The page's timers fire a little late, so `rest` is what's left on the whole (a moving mean).
  - A page that hosts adds nothing (a pick): its machine runs the server, so it has no trip, and each player who joined says its own. Every page of a match can then be told the same lag, whoever hosts, after a host migration too.
  - `Tide.minLag` is the least a lag can make the ping, for the page around the game (the owner asked for the least to be shown, 2026-10-05; the name is a pick): the pings while the page added nothing (`least`: their mean, of the last 32 or so, as it's there to be read), `undefined` until 8 were measured so and on a page that hosts. So a page that wants it starts with no lag. With both players in one page it's next to nothing (measured: 0.6 ms), as a ping is.
  - `tide_platform_web_lag` (`platform/tests/web_lag.c`) checks it in the web tests' virtual time, the page standing in for the relay and for WebRTC with an other end that sends back what it's sent, and the program measuring as a session does, by the room's clock: that a ping is the network's time and an answer takes a frame longer, then a lag untold and told, changed, on a network that got slower, shorter than the ping (where the least lag is known), and on a page that hosts.
- Two more are for a game shown in a frame of a page that scrolls, and Provisional the same way (the owner asked for what they do, 2026-10-05: demos that come up at once, and a page that scrolls over them, on a phone too; the names and the rules are picks):
  - `Tide.wait`, or `wait` in the address: the program loads (its bytes, its compile, its GPU device, its files) and starts when the page calls `Tide.start()`, so a page loads a game before it shows it. `Tide.start()` gives a promise of the program's first frame that drew something (a draw call, `drew` in `tide.js`), with `wait` or without, which a program that stopped before one breaks: that's when the canvas has something to show. Not its first frame: a game whose views read the match draws nothing until this machine is in it, a few frames after it started, and a frame that draws nothing is black.
  - `Tide.embedded`, or `embedded` in the address, which the page can change as the game runs: the page keeps its scrolling. The wheel is the page's, always (no game reads it yet; one that does needs a rule for when it's the game's). A finger that swipes up or down on the canvas scrolls the page (`touch-action: pan-y pinch-zoom`, and its touch events keep their defaults) until the player taps the game: from then every touch is the game's as it lands, as without `embedded`, until the frame loses the focus (a press on the page elsewhere). Before that tap the browser may still take a finger to scroll with, which it says with a pointercancel, so the program hears of a finger once it lifted, all at once, a tap, and never of one the page scrolled with: a swipe down a page presses no game it starts on. Nothing about it is timed.
  - `#download` after the address: the page is only being downloaded, and nothing in it runs (`tide.js` returns at its first line). It's how a page has the browser download a game before a frame shows it: browsers keep a frame's page apart in their cache from what a script fetches or a link prefetches (measured in Chrome: after `fetch()` or `<link rel="prefetch">` of the same address, the frame downloaded all of it again), so only a frame's load puts it where a frame finds it, and a frame that may run no script (`sandbox`) logs an error for each script it didn't run. It's after the `#` because that's no part of the address a cache goes by, where one more word in the query would make it another page.
  - The program's bytes load while the page waits to hear about its GPU (`Uint8Array.fromBase64` where the browser has it), and it starts once both are there. The canvas takes the focus without scrolling the page around it (`preventScroll`).
  - `tide_platform_web_embedded` (`platform/tests/web_embedded.c`, with `embedded` in its page's address) checks the wheel, a finger the page scrolled with, a tap, the fingers after it, the focus lost, and the page saying it's embedded no more.
- Web builds have threads: the target is `wasm32-wasip1-threads`, and programs import their memory (`--import-memory`, up to 4 GiB). A cross-origin isolated page (served with `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`) makes it shared, and each thread the program starts (`pthread_create`, through wasi-threads' `thread-spawn`) is a worker running the same program on it (`tide.js`). Browsers won't share memory with other pages, so there the page gives the program memory of its own, changing the flag in its import to match, and it runs on one thread (`tide_web_threads` says 1), with the same results. The page's main thread can never block, so the web's pool (`platform/src/jobs.c`) only spins there and wakes workers with atomics, and wasi-libc's `malloc` spins too (`sched_yield`); its workers sleep when they have nothing to do (below). Browsers won't take views of shared memory for some calls (`TextDecoder`, `crypto.getRandomValues`, data channels): copy out first. When one thread grows the memory, V8 (Node 24's, at least) lets the others use what was added only once they hear of it, so memcpy and memset into memory another thread's growth made trap until then: engine code that runs on threads allocates with `tide_alloc`, `tide_alloc_zeroed` and `tide_realloc` (`tide/page.h`), never calloc or realloc, and calls `tide_memory_sync` where it picks up what other threads made (tasks, settling, a system's finish, the end of a tick's threads). The engine's `sbrk` notes how far the memory grew, so that's a comparison until it did. A worker's crash ends the program under Node (`run_wasi.mjs`), where it would leave the main thread spinning. The pool makes its workers the first time a tick has enough work for them (about three times desktop's threshold, since waking a worker costs more), as each costs a page far more than a thread does. Node runs tests the same way (`cmake/run_wasi.mjs`, with `worker_threads`), and `tide_platform_web_threads` ticks on threads in a cross-origin isolated page in headless Chrome, against one thread. `tide run --web` serves its page isolated; pages made to ship need a host that sends those headers (itch.io's SharedArrayBuffer option does) to run on threads.
- The web's C library compares memory a byte at a time (wasi-libc's `memcmp`, in wasi-sdk 24: a load, a compare and a branch for each byte; its `memcpy` is `memory.copy`), and a tick compares megabytes: each page a system wrote apart against the one a snapshot shares, each chunk of a list C filled against what the list held, a parallel loop's copies against the grid or the list, a delta's pages against its base's. Those go through `tide_same_bytes` (`tide/page.h`): `memcmp(...) == 0` natively, inline, so native code is what it was, and on the web the engine's own loop (`engine/src/page.c`), 64 bytes a round with no way out inside it, which the compiler makes SIMD loads of. Found with Sumo (2026-10-06), whose physics state was a 4 MB list that C wrote every tick before resident state on 2026-10-07: under Node, the list's write-back after a whole image went from 0.59 ms to 0.15 and after an image in parts from 0.19 to 0.09, and a tick with four bots at a full ring from 1.13 ms to 0.96 (see What Sumo costs). It's every web game's: a system that takes a component `mut` has its pages compared this way each tick on a client. Engine code that compares more than a few hundred bytes for equality, where web builds run it, calls it and not `memcmp`. `tests/test_page.c` checks it against `memcmp` at every length around its rounds, wherever the two runs start and wherever the byte that differs is, natively and under Node.
- A page's pool has a thread for each processor the browser says the machine has (`navigator.hardwareConcurrency`, through `tide_web_threads`): both threads of a core that runs two, where desktop's pool counts cores, as a browser says nothing else, and half as many would be too few where cores run one thread (Apple's, most phones'). So a page's worker gives up a processor it has had no work for (the owner, 2026-10-05: cheaper waiters before another count). WebAssembly has no instruction that tells a CPU a loop only waits, and a page can't yield, so a loop that waits takes a core, or half of one, from a thread with work; and with one on every processor, the system takes a processor from a thread with work to run whatever else the machine has, and everything that waits for that thread waits a time slice. A hint to the CPU (`Atomics.pause`, tried) changes nothing: it's the processors being taken, not what the loops do on them. How:
  - A worker that looks for something to do in a tick 256 times in a row and finds nothing leaves the tick: the work returns on it (`IDLE_LOOKS`, `work` in `engine/src/jobs.c`), and it sleeps on the pool's count of calls (`calls` in `platform/src/jobs.c`, with `memory.atomic.wait32`). The caller's thread stays: the tick is its to finish, and a page's own thread can't sleep.
  - Whatever makes work for more threads than are at it asks for them: `tide_jobs.more(self, count)`, which a pool has when its threads can sleep (the platform layer's, on the web and on desktop; NULL for a host's own pool that has none, whose threads then stay in a tick, with the CPU's pause and the system's yield), through `ask` in `engine/src/jobs.c`. A system's end asks for the tasks it lets start, less the one its own thread goes on to, so a chain of systems of one task each wakes nobody. A parallel loop asks for its tasks less its own share. C's jobs ask for one thread at the first of a run, and each thread that takes one asks for those still there (`help_task`), so C that starts 23 pays for one call.
  - Nothing waits for a sleeper to wake: what nobody came for, the threads that are there do. And no call is lost: it's counted before the caller looks for sleepers, and a sleeper counts itself before it looks at the calls, so one of the two sees the other (`more` and `worker`; `tide_job_sleep` and `tide_job_wake` the same way).
  - Waking costs, which is why a thread looks a while before it sleeps and why what's known to be needed is asked for in one call (measured under V8, on Windows): the caller pays 2 to 6 µs to wake one thread and 7 to 12 for 23 at once, and the last of 23 is awake 60 to 90 µs later.
  - C whose tasks wait for each other inside their work (a solver's workers, for each stage it gives them) has `tide_job_sleep(word, seen)` and `tide_job_wake(word)` for a wait that has gone on long (`tide/jobs.h`; see Language, jobs). Box2D's and Box3D's solvers use them.
  - Measured (2026-10-05, 12 cores of two threads each, web-release under Node, each number the least of several runs taken in turn with the code before; the two libraries were on their scalar paths on the web then, a day before they had WebAssembly's SIMD, which takes a quarter off a step on one thread and next to nothing off a shared one: see Box2D and Box3D): 2,400 crates moving, Box3D's tick takes 3.3 ms on one thread, and on 24 went from 4.4 to 2.4 (on 12, from 2.4 to 2.1); Box2D's takes 1.5 on one, and on 24 went from 3.8 to 1.7 (on 12, from 1.5 to 1.2). With four other busy threads on the machine, as a player's has something else going on: Box3D's on 24 from 8.3 to 2.7, Box2D's from 6.2 to 1.75, and of ticks with no C, `versus_particles`' from 0.51 to 0.31 and the median of `versus_life`'s from 0.61 to 0.42 (on a quiet machine those were no slower before). In headless Chrome, which gives a page the same 24 (a scratch page of the same match, before spare pages made every tick shorter): Box3D's from 4.0 to 2.7, Box2D's from 2.4 to 1.7.
  - What's left is the count's own, and it stays (decided 2026-10-05: the pool keeps a thread for each processor the browser counts, and the solvers a worker for each of the pool's threads; no smaller pool and no fewer workers): on that machine 12 threads are still quicker than 24 for the physics packages, by a seventh for Box3D's tick and by two fifths for Box2D's, which on 24 is no quicker than on one thread. Their solvers gain nothing from a core's second thread, and a tick with every processor at work has none to spare for the rest of the machine. Fewer workers for the solvers alone, on a pool of 24, gets about half of that back (Box2D's tick 1.4 with 6 or 8 workers, Box3D's 2.2 to 2.3 with 8 to 16): the rest is in the tick's other work, which is slower on the bigger pool too, and not for the threads woken as a tick starts (waking only as many as its first tasks need was tried, and changed nothing).
  - `TIDE_THREADS=<n>` tells a program under `cmake/run_wasi.mjs` the machine has that many, for measuring. Desktop's pool had the same cost in a smaller measure, and its workers leave a tick and sleep the same way (see Determinism, Systems that touch the same data: the tick runs on threads).
  - `jobs_threads_come_back` (`platform/tests/jobs.c`, where a pool has `more`: on desktop and under Node) runs a system until the other threads have left the tick, then sixteen tasks, and checks threads that had left ran some. `jobs_threads_change_nothing` and `tide_platform_web_threads` run C that works in stages (`stage_out` in `platform/tests/jobs_tasks.c`), whose workers sleep between them where they can: in a page, a wait on its own thread would stop the program.
- Games keep running where nobody sees them, so a match goes on for the other players when its host switches tabs or minimizes. Browsers stop a hidden page's animation frames and slow its timers to about one a second, so while the page is hidden, frames come from a worker's timers (`tide.js`). Desktop windows keep running while minimized, waiting between frames on GLFW's events (`glfwWaitEventsTimeout`), so a window restored or closed goes on at once. Either way, each frame comes when the host says it next has work (`tide_platform_next_frame`), which for `tide/host.h` is its match's next tick (`tide_session_until_tick`), so frames follow the tick rate; a host that doesn't say gets 60 a second. Neither draws meanwhile (`tide_platform_draw`). `tide_platform_web_rooms` hides the host's page past the players' timeout, with its own timers and animation frames stopped (stricter than browsers, which slow them), and the match has to go on, with frames never faster than its tick rate. Like every test, it can't rest on how fast the machine is: a flaky test is a broken test, fixed rather than loosened or skipped.
- Web tests that need real time are served to the browser (`cmake/run_web_served_test.mjs`): the WebGPU ones, `tidec_e2e_fetch_web`, and `tide_platform_web_io`, the files test, which goes through seven pages in one browser, a phase each (`platform/tests/web_io.html`). The page's shell sends each line the program prints, and its result, to the runner's server, in order.
  - **A served test that fails ends with an account**, each line with when: the pages the server was asked for, and what the browser itself said of the page, which the runner hears over DevTools (`--remote-debugging-pipe`, as `rooms.mjs` has it; the browser opens on an empty page and is sent to the test's once DevTools listens, so nothing goes unheard): where the page went, what it threw, its console's errors, what it couldn't load and why, its process crashing. A crash, or the browser ending, fails the test at once.
  - **A page that gives no result is asked before the test gives up** (`where` and `tries` in the runner). Where it is: its address, how far it loaded, whether it's shown, and `window.tideSteps`, the steps its shell noted as it went (the page started, the program's first line, its exit, a line that couldn't be sent, the page hidden or frozen; `web_io.html` also what IndexedDB was asked and what it answered, as a program that keeps files starts once they're read, so a page that waits there prints nothing). And whether a timer, IndexedDB and a request to the server still come to it, read back 3 seconds later. So "no result" says which it was: a page that never loaded, one that waits for something that never came (and what), one whose thread is busy (no answer at all), one that's frozen (it answers, and none of the three comes), or one that's gone.
  - **A page never ends with nothing said.** The shells (`platform/web/test_shell.html`, `demo/shell.html`, `web_io.html`, and `platform/tests/web_threads.html`, whose runner is its own) send lines one after another in a chain of promises, and one fetch that failed left the chain rejected: no line after it, no next phase and no result. A line that can't be sent is the test's result now, and each answer is read to its end, which is when the browser has a request as done.
  - The browser closes itself (`Browser.close`), so its scratch folder is let go of: killed from outside, the processes it started kept the folder for a moment, and a run right after in the same folder failed to clear it. These tests' limit in CTest is 150 seconds: the guard around the runner's own 100 and what it asks after them.
  - That account is there for a failure it would have explained (CI's Macs, 2026-10-06, run 37464860319, once: `tide_platform_web_io` printed its `write` and `other` phases whole, then nothing of `read`, and "no result within 100 seconds"). Its cause isn't known: every way above leaves that same log. What didn't bring it back, on Windows: 841 runs of the test, 12 at a time, and 14,400 page loads of its first three phases in a loop. What was ruled out there, each made to happen: a server that closes idle connections as the page's posts reuse them fails no post (Chrome sends again; 3,000 posts over 462 connections), and a hidden page's posts don't stall on answers nobody read (which the browser does keep as unfinished requests until the page goes). The next one says what it was: read its account first.
  - Found in that account's steps since, and fixed (2026-10-06; see Tech stack, local files), not shown to be its cause: each phase that changed files and flushed wrote them in two transactions, and went to the next page once the first was done, the second made a moment before. The page's steps showed both complete before the program's exit in every run that was looked at.
