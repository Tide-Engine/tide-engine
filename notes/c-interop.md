# C: lists C makes, jobs, systems written in C

## Borrowed immutable asset lists (2026-10-11)

Generated `mut List<T>` extern wrappers now receive destination ownership internally and call the owner-approved `tide_list_prepare` before writable flattening. The C extern's public parameter shape is unchanged. `out` still avoids copying discarded data; ending an out call releases old immutable descriptor leases as appropriate. A C caller using `tide_list_copy` may now receive a borrowed asset value. Before manually writing it, call `tide_list_prepare(&local, sizeof(element), TIDE_IN_SCRATCH)` (or the actual field's match/local ownership). Raw `_at_mut` returns NULL for immutable values. Plain nonasset lists retain their old copying path. Updated owned-model C regressions and `asset_sharing_c.c` exercise these contracts.

## Language

- An extern function's `out List<T>` is a list C makes (built for C that fills big lists, like Box2D's image, without a copy of what they held; Provisional: its C API awaits the owner, `docs/spec.md`, C functions). It's an `out` parameter like any other (below) to everything but C. What's built, and what code relies on:
  - `out` is a word before a type and a name in a routine's parameters, parsed as `in` is (`parse_routine_params` in `compiler/src/parser.c`), and a name anywhere else. The parameter is `PARAM_MUT` with `param.is_out`, so to the schedule, evaluation order and generated code it's a `mut` list the call changes, with no code of its own; only what C gets differs. The call says `out` (`WriteImage(out physics.image)`), as for every `out` parameter.
  - C gets a `tide_list_out *` (`tide/list.h`). `tide_list_out_room(out, count)` is memory for `count` elements, with whatever was there in it, from the buffer the engine keeps between calls (`flat_take` in `engine/src/list.c`, see ECS and simulation state), so a call every tick allocates nothing; asking again gives the buffer back and takes one for the new count. `tide_list_out_count(out, count)` says how many of them the list gets, at most the room: none when it's never called.
  - tidec calls an extern that takes lists through a wrapper (`gen_extern_lists`, `tide_c_<name>`), which takes an `out` list by address with its `where` after it (`place_where` at the call, as a list's methods get it: an empty list's handle doesn't say whose heap it's in) and brackets the call with `tide_list_out_begin` and `tide_list_out_end`. The end makes the list exactly what C said: it takes elements off (`cut`) or makes room (`reserve`), then writes run by run, only where the bytes differ (`put_elements`), so chunks that come out the same stay shared with the world's snapshots and keep their hashes. A list that borrows another's block gets one of its own. No copy of what the list held is ever made.
  - C that knows which elements changed says only those (built for Box3D's image, of which a tick changes a few records, and Box2D's since; Provisional with the rest). `tide_list_out_keep(out, count)`: the list keeps what it holds and is `count` long, zeros where it grows. `tide_list_out_part(out, first, elements, count)`: these elements go over the ones from `first` on. The parts are kept in the `tide_list_out` (an array from `flat_take` too) and written by `tide_list_out_end`, each compared with the elements it goes over (`put_elements_at`: a part that starts a chunk makes a shared one the list's own without copying what it's about to write, `tide_heap_write_over`; one in the middle copies the chunk). So what a call costs goes by what C gave, never by the list: nothing else of it is read. A part's elements are C's memory, read after C returned, so never the function's own variables, and nothing may change them meanwhile. Of `keep` and `room`, what C said last stands, so C that finds too much changed asks for room and fills it. Generated code is as it was: `tide_list_out` grew, and tidec only names the type.
  - A program with no `out` generates the C it did, byte for byte: checked by running old and new tidec over every game's source list.
  - `compiler/tests/e2e/lists_out` checks it in the match, the local world and locals, and `tests/test_list.c` the runtime's part, natively and on the web (`list_out_keeps_what_it_holds` for parts: which chunks become the list's own, growing, shrinking, the scratch area, a list that names another's).
- C that shares its own work out does it on the tick's threads, through jobs (agreed 2026-10-05; `tide/jobs.h`, `engine/src/jobs.c`): `tide_job_start(work, context)` hands a task to another thread and returns at once, and `tide_job_wait` returns once it ran. It's what a library with a task interface of its own needs (Box2D's solver starts its workers and then works beside them), which `tide_parallel_for`, a loop that returns once it's done, can't serve. How:
  - A job is a slot in the running tick (`task_slot`, 64 of them), which a thread with nothing else takes before loops and systems (`help_task`). One nobody took by the time it's waited for runs in the wait, so each runs exactly once whatever the threads do; with no other thread (a tick on one thread, no pool, code outside a tick) it runs inside `tide_job_start`, which returns 0.
  - tidec can't tell how much work C is, so a tick whose C started jobs runs on threads the next time whatever its systems look like (`tasks_wanted`), until a tick that had threads to use starts none. So C with little to do starts none: Box2D's bridge only shares a step out past a number of bodies awake.
  - `tide_job_threads` is how many threads the tick can have at work, in a tick that runs on one too, for a library that sizes its workers once.
  - Jobs have to come out the same however many threads take them, as everything C does on threads: that's the caller's to get right.
  - Jobs that wait for each other inside their work, as a solver's workers wait for each stage it gives them, wait in a loop, since such a wait is mostly shorter than a sleep and a wake. On the web a loop holds its processor for as long as it goes on (see Web builds), so for a wait that has gone on long there's `tide_job_sleep(word, seen)`, which sleeps until `tide_job_wake(word)` unless the 4 bytes at `word` aren't `seen` any more, and `tide_job_wake(word)`, which whoever changes the word calls after, for a comparison while nobody sleeps (Provisional: the names and the shape are Claude's, built for Box2D and Box3D, and await the owner). It sleeps on a thread of a pool whose threads can, in a tick (`may_sleep` in `engine/src/jobs.c`, said where a thread can leave a tick); on a page's own thread, which can't, and everywhere but the web, where the pause and the yield are there for the wait, it returns false at once and the caller goes on with its loop. How long a wait is before it sleeps is the caller's: about as long as a wake takes, or every wait pays for one.
  - `tide_platform_jobs` (`platform/tests/jobs_tasks.c`, a C function `jobs.tide` calls) checks each ran once, with the same world as on one thread, and that other threads took some, and that work in stages whose workers sleep between them comes out the same; `tide_platform_web_threads` runs the same game in a browser.
  - `tide_task` is the async tasks' type in generated C, so these are jobs.
- A system can be written in C: `extern system Move(mut Position position, Velocity velocity, Time time, without Frozen);`, whose C function is handed its entities' components as the arrays the match keeps them in, where an extern function gets one entity's at a time (the owner approved the direction, 2026-10-05: "in a way that lets others use this too for their own situations"; Provisional: the syntax, the semantics and the C API are Claude's picks, in `docs/spec.md`, C functions). What's built, and what code relies on:
  - It's a `DECL_SYSTEM` with `decl.extern_system`, no body (`body` is NULL, as an extern function's) and a `c_name`, from `[NativeName]` or its own name (`parse_extern_system` in `compiler/src/parser.c`, `check_extern_system` and `check_extern_c_name` in `check.c`). Everything that goes by a system's signature takes it as that system: `check_params`, the schedule (`compiler/src/parallel.c`: what it takes `mut` is written, the rest read), `system_splits`, `[Stage]`, `[Before]` and `[After]`, the language server. Nothing warns about access it doesn't use, and `tidec --schedule` and the lens say `in C`. Code that walks a system's body has to stand a NULL one.
  - v1 takes components (read or `mut`), `with` and `without`, and singletons (read or `mut`). Errors that say what to write instead: a sparse component or a filter by one (`check_extern_sparse`, once the archetypes are derived, which is when a tag's sparseness is known), the `World`, a query, `Devices`, the input, an `Entity` parameter, a component with no fields. A component or singleton that holds text or lists is allowed: its handles are C's to leave alone.
  - C is called once for each run of rows, a chunk of an archetype the filters admit or the task's piece of one, never with none, in the order a Tide system goes through them on one thread: `void name(tide_rows *, <singletons, each by address, in order>)`, declared in the generated `.c` (`gen_routines`), never the header. A system with no component or filter is called once a tick with a run of no rows. `gen_extern_system_run` (`compiler/src/codegen.c`) writes its `tide_tasks_` and `tide_task_` as any system's, a `tide_rows_component` table for each archetype it runs on (each component parameter's first lane, size and where its lanes' pages are held), and the call between `tide_rows_begin` and `tide_rows_end`; it has the same `tide_own_` a Tide system has when it splits.
  - `tide/rows.h` (`engine/src/rows.c`) is what C reads the run through: `tide_rows_count`, `tide_rows_entities`, `tide_rows_floats` and `tide_rows_ints` (the lane of a 4-byte field, by the component's number among the system's component parameters and the field's `offsetof`), their `_mut`, and `tide_rows_get` and `tide_rows_set` for a row's whole component. **Nothing is copied to read, and writes are on demand, a lane at a time**: the first `_mut` or differing `set` of a lane a snapshot shares takes a page (`tide_page_take`), copies the chunk's rows into it, puts it in the table and keeps the shared one in the run's `held`; `tide_rows_end` puts the shared one back where the bytes came out the same (its hash intact), and else zeroes past the rows and lets the snapshot keep it. A page the table alone has is written in place. So C that writes nothing costs nothing, which matters as a client's every tick starts with every page shared. A read array asked for before a `_mut` of the same lane may be the snapshot's page: C reads through the one it writes.
  - The pieces of a chunk write the same pages at once, so a run that isn't its chunk's whole (`tide_rows.whole`, `tide_pieces == 1u`) never takes a page: `tide_own_` made them the table's before the pieces started, and a shared one found there stops the program.
  - A row counts as 256 operations (`EXTERN_ROW_COST`) where a tick's work is reckoned, as its code can't be read: enough for a full chunk to go in two pieces.
  - What C gets wrong stops the program, naming the function, the system and what to write (`stop` in `rows.c`): `tide_rows_stops` (`tests/stops/`) makes each call and CTest reads what it says.
  - A program with no `extern system` generates the C it did, byte for byte: checked by running old and new tidec over every game's source list.
  - `compiler/tests/e2e/extern_system` checks it natively and on the web: arrays, rows at a time, entities, singletons, filters, runs of several archetypes in a Tide system's order, what stays shared with a snapshot lane by lane, chunks in pieces (a pool of one thread that says it has four) and on the platform layer's threads against one thread, `[Before]` and `[After]` against Tide systems, and a world packed and unpacked between. `tests/test_rows.c` checks the runtime without the compiler, `compiler/tests/schedule/extern_system` the schedule, `compiler/tests/errors/extern_system_*` each error, and `lsp_extern_systems` the language server.

## Internal physics tick completion (2026-10-11)

Owner-approved generated/runtime boundary: tide_rows carries readonly entity/Snap metadata for the call and an internal completion slot for once-per-tick C systems. `tide_rows_after_tick` registers a callback and stable context; generated code calls `tide_rows_finish_tick` after tide_apply_commands, before advancing Time. Each extern system has its own zeroed stack slot, with deterministic declaration-order completion, so parallel systems share neither a registration slot nor callback allocation. Entity/chunk runs receive no completion slot. No row/lane pointer may outlive its C call. Finalization may write only the declared mutable singleton state; physics SealHistory uses this to finalize history metadata. The world pointer to slots is transient and excluded from copy/hash/pack/layout migration. No Tide syntax/API was added for the hook.
