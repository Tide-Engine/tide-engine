# The GUI

## Host pool on a frame (2026-10-24)

tide_gui.jobs is an optional borrowed tide_jobs provider for generated local
worker calls during a frame. It is not available to Tide GUI code. The standard
host sets it before frame; zeroed/custom hosts keep the synchronous fallback.
GUI interaction/layout behavior is unchanged. Hosts/games rebuild for the C
layout addition. Worker ownership/lifecycle contracts: notes/language.md.

Build notes, moved here from `AGENTS.md` as they were: what's built, what code relies on, the tests and the measurements. `AGENTS.md` has the rules every session needs and the index of these files. The headings below are that file's sections as they were, and "see <Section>" names one of them: the index says which files each is in. What a note calls "below" or "above" may be in another of these files now: search `notes/` for its name.

## Rendering and platform

- The GUI (`GUI` and `GUILayout` in Tide, `tide/gui.h` in C) is immediate mode, like drawing, and local: widgets change local state, never the match. It records into a list of its own, which `tide_gui_end` adds after the world's, in pixels (from the top left, y down), so widgets keep their size when the window changes. It measures text with the platform's font (`tide_platform_measure_text`). Views read the devices through a `Devices devices` parameter: `tide_gui_begin` works out what changed since last frame and hides what the GUI uses.
- A host samples the game's input before the frame's GUI runs, and views read the devices before its widgets do, so what the GUI hides can't wait for the GUI to see a press. Whether the pointer is the GUI's is where it is now against where the last frame drew its widgets and areas (`on_gui` in `engine/src/gui.c`, which `tide_gui_hide` and `tide_gui_begin` both ask), never where the GUI last saw it: a finger that touches a button is hidden from the sample of the frame it lands in. A widget that first appears under the pointer takes it a frame later. Tests of hiding go in the host's order, sample then frame (`finger_sample`, `mouse_sample` in `tests/test_gui.c`).
- Which widget the pointer is on goes by the same places (the owner's card, 2026-10-08: a finger's tap on Play was lost while the mouse rested on the Rooms menu): where the pointer is now against where the last frame drew its widgets and areas, never where the GUI last saw it. A press is in one frame's `mouse_pressed`, so the widget under it has to be known in that frame, for a pointer that wasn't there the frame before: every finger's first touch, a finger that lands while the mouse rests elsewhere (a laptop or a desktop with a touchscreen), a mouse that moves and clicks between two frames. What's built, and what code relies on:
  - **Where widgets are over one another, one is on top:** the one drawn last of those at a place, and of an area and its content, the area only where none of its content is (its panel is under its widgets, and over what was drawn before it). `g->hot` is that one's id, and only it is hovered (`hovered` in `engine/src/gui.c`); with none there, a widget the pointer is on is hovered at once.
  - **It was a frame late, by where that frame saw the pointer,** and a pointer that had moved since found the old one on top wherever the old one's rect still held it. The mouse on a menu's title has the menu's panel on top; a tap on a button of that menu is inside the panel's rect, so the button wasn't hovered in the frame of the press, and nothing was pressed. Not which pointer the press came from: the mouse alone lost the click the same way when it went from the title to the button and pressed within one frame, and the tap worked with the mouse on another button, or off the menu. A finger with nothing before it had none on top (`hot` 0), and then every widget under it was hovered and the first one called took the press: the one at the bottom, and a button under an area's panel.
  - **A frame begins by working it out again where the pointer is now** (`on_top`, in `tide_gui_begin`), from the places the last frame remembered: each has its widget's or area's id, and an area's says how many places came before its content's (`tide_gui_rect` in `tide/gui.h`; `remember_place`). It's the rule a frame applies as it draws (`hovered` setting `hot_next`, `close_area` taking it where it's unchanged since the area opened), over again, and the frame still applies it: what it found is `hot` until the next frame begins, which tests read.
  - **Past `TIDE_GUI_MAX_RECTS` places it's as it was,** a frame late (`rects_full`): a widget whose place isn't remembered can't be found on top of one whose place is, so working it out from the places alone would give its press to the one under it for good.
  - A widget that first appears where another was takes the pointer a frame later, as before: the last frame drew the other there.
  - Tests (`tests/test_gui.c`, all in the host's order): `gui_a_finger_presses_a_button_of_the_menu_the_mouse_rests_on` (a tap, a tap shorter than a frame, and the mouse's own jump), `gui_a_finger_presses_the_widget_on_top` (a button on a view's control, a button under an area's panel, the panel's own button, with taps a frame apart) and `gui_a_widget_past_those_remembered_is_on_top_a_frame_late`, which fails without the fallback. `rooms_a_finger_presses_play_with_the_mouse_on_the_title` (`packages/rooms/test/rooms_test.c`) is the card's case on the package's own page.
  - A script's `mouse` line was checked and isn't part of it: it moves the mouse and says no button (`apply` in `platform/src/script.c`), and a headless window's mouse is outside the window until a line puts it somewhere, which is why a script with no `mouse` line never showed this.
- A key or a gamepad's button is the GUI's by when its press began, as the pointer on the stats' drawer is by where (the owner, 2026-10-06, of the bug it was: "yeah sounds like a bug"): one that goes down while the keyboard and the gamepad are the GUI's (a widget has the focus, a field is typed into, a modal is up) stays the GUI's until it's let go, whatever became of the widget. Before, the keyboard was the game's again the frame after nothing had the focus, with the key that clicked still down: Space on a lobby's Play, which closes the lobby, fired the game's cannon too.
  - A frame notes each press as it sees the key go down (`keep_presses` in `engine/src/gui.c`, from the platform's devices against last frame's: `tide_gui.kept_keys`, `kept_pad`). A new press of a key is the GUI's or the game's afresh, and a key that was down before the GUI took the keyboard is never kept: it's the game's again as soon as the GUI lets go.
  - It's hidden from views until a frame has seen it up, that frame included (`hide_kept_from_views`), and from samples until one has (`hide_kept_from_sample`, in `tide_gui_hide`), apart, as a key's `pressed` and `up` stay in the platform's devices until a sample consumes them, which can be frames after it was let go. Where nothing samples and the host clears the devices itself, a frame that finds the key up with nothing left to read lets it go.
  - Both go by which keys are still down, so they run before the rest is hidden (`hide`).
  - Sticks and triggers aren't kept, nor what a view claimed (`GUI.ClaimKeyboard`): a claim that ends with a key down gives the key back at once.
  - `gui_a_key_that_clicked_a_widget_is_the_guis_until_its_let_go` and the two tests after it (`tests/test_gui.c`) check it in the host's order, with samples every frame, rarer than frames, and never. Siege's lobby (which is Towers' since), and the one Sumo's came from, waited a frame of their own for this, and don't any more.
- A field says when the player entered what they typed, through an `out` parameter (agreed 2026-10-06: "yeah im ok with that", of `GUILayout.TextField("Code", lobby.code, out var entered)`, with what it returns staying whether the value changed, `entered` true in the frame Enter ends the typing, and the number fields and both of `GUI` and `GUILayout` having it). A view couldn't tell before: Enter ends the typing and the next one starts it again, and the keyboard is the GUI's while a widget has the focus, so `devices.keyboard.enter.down` is never true there. The rest is picks (Provisional in `docs/spec.md`, GUI). What's built, and what code relies on:
  - **Two things in the owner's sketch aren't Tide,** and the docs show what is: an argument for a `mut` parameter is written as it is, with no `mut` (the parser says so now, where it said "expected an expression": `parse_args`), and a widget can't be on the right of `||`, so it's `if (GUILayout.Button("Join") || entered)`, the button first.
  - **Runtime** (`engine/src/gui.c`, `tide/gui.h`): `tide_gui_text_field_entered`, `tide_gui_int_field_entered`, `tide_gui_float_field_entered` and their `tide_gui_layout_` twins take a `bool *entered` last, which every call assigns, and the functions there always were call them. It's true when the field is typed into, has the focus and Enter went down this frame (`KEY_ENTER`, the numpad's too; for a number field `PAD_ACCEPT` as well, which ends its typing as it always did, and not a text field's), and false for anything else that ends the typing: Escape, the focus moving on, a click elsewhere, a Disabled block, a modal over it.
  - **What's typed in the frame Enter comes in is entered with it** (`type_text` and `type_into` run before the typing ends), in every field, with `entered` or not: it was dropped, which a script's `text` and `key enter` on one frame, or a slow frame, would have joined a room with.
  - **Opening and closing a float field keeps every bit** (fixed 2026-10-08): `start_typing` writes `FLT_DECIMAL_DIG` significant digits into the edit buffer for floats and color channels; the compact text outside editing still uses `%g`. Six digits in the buffer formerly changed values when Enter, Tab or a click elsewhere kept a number nobody typed. `NUMBER_FLOAT` parses with `strtof`, rounding once to the field's float before rejecting infinity or NaN, so decimal text that rounds to `FLT_MAX` remains valid even when its double interpretation is slightly larger. Color channels still parse as doubles and clamp to `[0,1]`. `gui_float_fields_keep_untouched_values`, `gui_float_fields_accept_full_precision_numbers` and `gui_vector_and_color_fields_keep_untouched_values` (`tests/test_gui.c`) cover both signs, full-precision decimals, both finite extremes, normal and subnormal minima, signed zero, Enter/Tab/click exits, and vector/color fields in either call order, on native and web builds.
  - **tidec:** a built-in signature has `out` parameters (`signature.out` in `compiler/src/builtins.c`, a bit each, with its bit in `mut` set, so generated code passes the address as for a `mut` argument and the call counts as one that writes: nothing in `codegen.c` changed). `add_gui` reads `out bool entered` in a widget's parameters, and the three fields are registered a second time, as `tide_gui_<field>_entered`, after every first version, so completion still leads with the one there always was.
  - **An `out` argument of one of the engine's functions goes through the code a function's does,** not a copy of it: where a version of the name has an `out` parameter (`builtin_takes_out`), the argument is begun as any (`begin_out_arg`, in `check_method`'s built-in branch), `resolve_builtin_call` picks the version by the arguments' count and lets an `out` argument go to the parameter in its place whatever that is (`fits`), and `check_gui_call` then finishes it and checks it against its parameter (`finish_out_arg`, `check_out_param`, with the parameter's own name from `builtin_param_name`). So the word missing, the word before another argument, a type that isn't `bool`, a read-only variable, a list's element and the match's state in a view are the errors, notes and quick fixes they are for a function. An argument with no `out` that isn't a `bool` variable gets "no version of ... takes", which lists both. `out` on a widget with no such version (`GUILayout.Float2Field(..., out var entered)`) says so, and which widgets have one, from the table (`refuse_entered_arg`, `builtin_out_versions`): the note `out` gets where nothing takes one, to declare the variable first, wouldn't help there.
  - A program that calls no such version generates the C it did, byte for byte: checked by running old and new tidec over every game's source list, with `--layout` and without.
  - **Editors:** signature help and hovers have each version from the same table. Completion offers `out var entered` where the argument goes (`out_argument_at` in `compiler/lsp/analysis.c` reads the engine's versions' signatures, `visit_builtin_out`), and a function of the engine's with several versions says so in its item's detail, ` (+1 version)`, with the others under its doc (`builtin_list_members`): that's every such function's, not only the fields'.
  - **A phone's keyboard:** its Enter is the GUI's Enter. On the web the page takes a key event that names Enter with no position, and a line break typed into its hidden field (`platform/web/tide.js`: `onKey`, the field's `input`), which `tide_platform_web_keys` checks with made-up events; on Android the system's keyboard sends the key itself to the input queue (`AKEYCODE_ENTER` in `platform/android/activity.c`). No phone was tried.
  - Tests: `gui_a_field_says_when_its_typing_is_entered` and the five after it (`tests/test_gui.c`), in the host's order, for the three fields; `compiler/tests/e2e/gui_entered` (each way to write the argument, both forms, by name, through a function that passes its own `out` parameter on, and a statement that reads the variable before and after the call); `compiler/tests/errors/gui_entered_*.tide` and `call_argument_mut.tide`; `lsp_gui_entered`. Duel's menu, Sand's panel and the docs' `rooms` example join with Enter.
  - **A number is kept whichever field the player goes to** (it was dropped when they clicked a field that a frame calls before the number's). The GUI has one buffer for what's typed (`tide_gui.edit`), which a field that starts its typing takes: by a click, or with the focus and something typed, as after Shift+Tab in a slow frame. Text is its field's as it's typed, so a text field never lost any. A number isn't until its field keeps it, and the field it was typed into has yet to run in that frame (having run, it would have ended its typing itself, without the focus), so before the buffer goes, a valid number in it is left for that field (`leave_typing` in `engine/src/gui.c`: `tide_gui.edit_left` and `edit_left_value`, read as the kind of number the typing started as, `edit_kind`). The field keeps it as it runs (`number_box`) and says it changed, with `entered` false. What code relies on:
    - The first one left in a frame stands: a field that took the buffer from it and is left in turn has run already, and was only typed into in that frame.
    - What no field took by the frame's end is dropped (`tide_gui_end`): a field that isn't called any more has nowhere to keep a number, and none is kept for a later frame.
    - Escape drops the number, as ever, and so does a field in a Disabled block, left for or not.
    - A modal that comes up doesn't end the typing where it takes the focus any more (`focusable`): the field under it ends its own as it runs, which keeps a number wherever the frame calls the modal. It was dropped when the modal was called first.
    - `gui_a_number_is_kept_when_the_player_clicks_another_field` and the eight tests after it (`tests/test_gui.c`) have fields at rects of their own, so a frame calls them in either order: an int and a float field left for a text field, two number fields, a number and a text field and back, a vector's and a color's boxes, Escape, Tab and Shift+Tab (with something typed in that frame too), a field that goes, one that's disabled, and a modal.
- A view's own widgets are controls (agreed: the GUI stays bare, and games bring their own controls). `GUI.Control(rect)` (`tide_gui_control`) is a widget the view draws itself: the GUI handles its input as a button's and draws nothing, so showing hover and focus is the view's.
  - It's a button's code without the drawing (`clicked` in `engine/src/gui.c`): its rect is one of the places a frame remembers, so a press on it is the GUI's from the sample it lands in (`on_gui`), it's in the focus's order with the other widgets, and a Disabled block or a modal over it stops it.
  - It gives a `tide_control` (`hovered`, `pressed`, `focused`, `clicked`), which generated C makes Tide's `GUIControl` of in a helper (`tide_gui_control_value`), as the two are different C types. `pressed` is the pointer holding it, wherever it goes meanwhile, as a `Devices` button's `pressed` is held.
  - While a control has the focus, the view that called it goes on reading the keyboard and the gamepad, less what moves the focus and clicks (`focus_view`, `hide_navigation`, `tide_gui_view`): the game and the other views read neither, as with any focus. So a menu's own shortcuts work with one of its controls focused.
  - Controls a loop makes come from one call, and are told apart as the GUI's own widgets in a loop are, by their turn (`tide_gui_id` counts the calls from a site in a frame): one left out gives its turn to the next.
  - `GUILayout` has no control: what a view draws is under the GUI's own widgets, a panel included, and under a modal's dim, since the GUI draws last. That's documented, and stays.
- The focus moves in the order widgets are called: down and right go on, up and left go back (`navigate`). A widget that steps its value with left and right keeps those (`focusable`'s `steps`: sliders and number fields), and the press that brought the focus to one doesn't step it too. The arrows, the d-pad and the left stick only start the focus while the game isn't reading the devices, or while a view says a menu is up, frame by frame (`GUI.Navigate()`, `tide_gui_navigate`), as a menu over a running match needs: a HUD's button never takes the d-pad.
- Container sizes use a bounded probing cache (fixed 2026-10-08). IDs with the same low bits previously overwrote each other every frame, so vertical groups never stretched their narrow widgets to their widest one and rows lost their fitted widths. `remembered` and `remember` resolve collisions; only a full cache evicts a container, choosing the oldest frame stamp. No GUI layout or memory limit changes. `gui_colliding_containers_keep_their_layout_sizes` checks independent widths across frames, and `gui_size_cache_reuses_old_containers_when_full` checks replacement and the root's retained width.
- Slider normalization and interpolation are double-width internally (fixed 2026-10-08): finite float endpoints can span more than a float holds, and nearby large ints can be the same float. Pointer coordinates and the drawing stay floats. An int slider applies keyboard and gamepad steps directly to its clamped integer in `int64_t`, exactly one toward the appropriate end, then clamps again; a reversed range reverses the step. Right still wins over Left, and a key's step over a held pointer. Idle widgets leave values unchanged, including values outside the range; a degenerate range clamps to its one value on interaction. A NaN pointer fraction is ignored. `gui_int_sliders_step_by_one_across_the_int_range`, `gui_int_sliders_place_large_values_on_the_track` and `gui_int_slider_steps_keep_their_input_precedence` (`tests/test_gui.c`) cover narrow ranges near both int limits, the full range, reversed and degenerate ranges, out-of-range values, keyboard/gamepad steps, pointer positions and precedence. `gui_float_sliders_keep_finite_ranges_finite` and `gui_float_sliders_step_with_extreme_finite_bounds` cover finite extremes, both range directions, endpoints, quarters, midpoint, and keyboard steps, natively and on the web.
- The GUI's own widgets have one look, and a simple theme for it (agreed: no styles for single widgets, no text sizes, no fonts). `tide_gui_theme`, Tide's `GUITheme`, is the colors the widgets use and their corners' radius, and nothing else.
  - Its defaults are the look the widgets always had, in two places: `tide_gui_theme_default` in `gui.c`, and the built-in struct's fields in `add_builtins` (`compiler/src/check.c`). A change to one goes to the other, and `gui_set_themes_hold_for_the_views_after` (`compiler/tests/e2e/gui_test.c`) checks they agree.
  - It follows the rule for a frame's settings: the plain name wraps a block and puts back what it found (`GUI.Theme(theme) { }`, `tide_gui_begin_theme`: a block that lays out nothing, like a Disabled one, `open_scope`), the `Set` name stays for the views that follow until it's set again or the frame ends (`GUI.SetTheme`), and every frame starts from the defaults (`tide_gui_begin`). Each form's misuse names the other (`check_gui_call` and `check_stmt` in `compiler/src/check.c`).
  - With a radius of 0 a part is the plain rect it always was (`paint`), so a game with no theme draws the commands it did. With one it's `Draw`'s round rect, and an area's panel, a shape then, is sized when its area closes like the plain one (`panel`, `close_area`).
  - The stats' drawer and the profiler's panel draw into lists of their own, never through the GUI, so they keep their look (`profiler_keeps_its_look_whatever_the_guis_theme` in `tests/test_profile.c`).
- A view with widgets that read the devices themselves, like a C library's, claims what they use, with the effect the GUI's own use has: `GUI.ClaimPointer()` and `GUI.ClaimKeyboard()` (`tide_gui_claim_pointer`, `tide_gui_claim_keyboard`). A claim lasts a frame and is made again each frame: it stands from the end of its frame to the end of the next, hiding the device from the samples taken meanwhile (`tide_gui_hide`) and from the other views, while the view that claimed it goes on reading it. So generated code says which view runs (`tide_gui_view`, before each), and `tide_gui.devices` is that view's. `GUI.ClaimPointer(rect)` (`tide_gui_claim_pointer_at`) says where a view's widget is each frame, and the pointer on it is the view's by where it is now, as on the GUI's own widgets: a claim with no rect can only hide a frame late, which a finger's first touch gets past. The GUI's own use comes first: no view reads what the GUI is using. `GUI.ShowKeyboard()` is apart from the keyboard's claim, as a widget's shortcuts don't want a phone's keyboard up. What's typed (`devices.keyboard.text`, `tide_keyboard.text`) is a frame's: views read it, and it's never in a sample or the input.
