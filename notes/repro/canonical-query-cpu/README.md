The parent [PowerShell script](../canonical-query-cpu.ps1) compares the same fixed simulation workload generated by two compilers on native Windows. It needs clang, lld, and optimized native engine libraries. No installed Tide or platform/GPU library is used.

For example, build the baseline from its immutable source archive and the candidate from the current checkout:

```powershell
$env:TIDE_HIDDEN = '1'
New-Item -ItemType Directory -Force build/cpu-baseline-source | Out-Null
git archive --format=tar -o build/cpu-baseline-source.tar d8c35ae91
tar -xf build/cpu-baseline-source.tar -C build/cpu-baseline-source
cmake -S build/cpu-baseline-source -B build/cpu-baseline-native -G Ninja '-DCMAKE_BUILD_TYPE=RelWithDebInfo' '-DTIDE_PLATFORM=OFF' '-DTIDE_EXTERNAL_DIRS=' '-DTIDE_VERSION=0.6.0-dev'
cmake --build build/cpu-baseline-native --target tidec
cmake -S . -B build/cpu-candidate-native -G Ninja '-DCMAKE_BUILD_TYPE=RelWithDebInfo' '-DTIDE_PLATFORM=OFF' '-DTIDE_EXTERNAL_DIRS=' '-DTIDE_VERSION=0.6.0-dev'
cmake --build build/cpu-candidate-native --target tidec
./notes/repro/canonical-query-cpu.ps1 -BaselineCompiler build/cpu-baseline-native/bin/tidec.exe -CandidateCompiler build/cpu-candidate-native/bin/tidec.exe -RuntimeInclude build/cpu-baseline-source/engine/include -RuntimeLibrary build/cpu-baseline-native/engine/tide.lib
```

Run after other builds, tests, and agent-launched games finish. The script preserves outputs in a new directory, records source/binary hashes, compiles the frozen `query_narrow.tide` fixture in production split-code/ThinLTO mode, and alternates eight baseline/candidate blocks. Each block starts a fresh world, warms up 20 ticks, then measures 2,000 ticks, including the required hash every tick. It compares the initial and final world hashes, the folded sequence of every tick's hash, the result, and tick counts. Both binaries link the same runtime library. `-Unsplit` runs the control case where clang can already inline and eliminate unused gather lanes.

The workload has 3,000 entities across two archetypes, a 352-byte/88-lane component, and 24 canonical queries per tick consuming `position.xz`. It has no devices, inputs, randomness, views, GPU, or wall-clock simulation reads. The timer records wall time, current-thread CPU time, and current-thread cycles. Windows CPU time has coarse resolution; use sufficiently long blocks. Alternating order and CPU time reduce background-load bias; they do not make a shared desktop an isolated benchmark machine.

The guarded live-write, whole-value, sparse-query, and snapshot cases in the ordinary `query_narrow` tests validate semantics independently. This benchmark runs their default disabled states and measures the narrow read workload. It does not model the entire game's CPU cost or retained rollback snapshots. Actual 1,000-bot battle profiles remain a secondary check: compare system cost per call and tick/work counts, since input/render timing can affect work between separate runs.

Measured on 2026-11-07, the eight production split-code/ThinLTO blocks averaged 16.184 seconds of thread CPU for the baseline and 5.699 seconds for the candidate per 2,000 ticks: **2.84× faster for this workload**, or 64.8% less CPU time. Wall time and cycles agreed closely. Initial/final hashes, every tick's folded hash sequence, result, and tick counts matched in all eight blocks. The unsplit control's LLVM output already eliminated unused gather lanes; its preliminary timings overlapped other work and support no performance claim.

The secondary public ARMY battle used mount-and-rifle `349c35a`, the same byte-identical asset pack and script, and 2,100 frames. Both **client 2** profiles executed 15,977 ticks, with 15,977 calls to each system below; the final logged battle counters also matched at integer elapsed 34 seconds (389/366 men, 3,024 shots).

| Client 2, whole profile | Baseline | Candidate |
|---|---:|---:|
| Reported systems time / executed tick | 14.162 ms | 11.996 ms |
| BuildKitBodies / call | 4.383 ms | 1.890 ms |
| BotSense / call | 3.333 ms | 3.560 ms |
| FallOnField / call | 0.319 ms | 0.326 ms |
| Match work / frame, including reruns | 111.883 ms | 95.754 ms |

BuildKitBodies' inner Trooper query now copies only its two x/z lanes on both archetypes; its outer whole-Place consumers remain conservative. BotSense did not improve in this measurement. These separate game runs do not pin Sample/input/render timing or expose a final authoritative clock/hash, so matching work counts and high-level battle counters do not establish equal full-game state. The fixed workload remains the primary CPU claim.
