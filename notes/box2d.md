# The Box2D package

## Joints, collider completion and live settings (2026-10-22)

The owner requested completion of the missing Box2D package features, including
joints. `box2d.tide`, `bridge.c`, `joints.inc` and `colliders.inc` now expose all
nine joint types in the pinned Box2D: distance, filter, motor, mover, pogo,
prismatic, revolute, weld and wheel. A joint entity has `Joint` and exactly one
settings component. Its anchors and angles are local frames at each body's
origin. Motors, springs, limits and common settings follow edits through native
setters; reaction force/torque are read after stepping. Disabling removes the
native constraint while retaining the entity. Rebinding or changing the type
recreates it. Pogo's creation-only normal, force bounds and initial state also
recreate it; hertz, damping and rest length have setters. Missing bodies, the
same body twice, invalid settings or a missing/ambiguous settings component
destroy the joint entity. Removing `Joint` removes its native constraint.

Creation stamps explicitly include the joint type. Default prismatic and
revolute definitions otherwise record identical scalar bytes despite different
constraints, so their native caches could share an incorrect stamp. The new
two-world regression checks those otherwise-identical replacements have
different stamps. The unchanged Box3D adapter uses the same older recording
pattern and should receive a separate audit; it was not changed here.

Capsules, convex polygons, two-sided segments and one-sided open/loop chains
join boxes and circles, directly or as parts. Polygons hull three to eight
vertices. Open-chain ghost vertices extrapolate the endpoint edges; chains
require static/kinematic bodies and distinct consecutive points more than
5 mm apart. Geometry/material/filter/sensor edits rebuild fixtures and update
mass. Invalid geometry removes its fixture and repairing it attaches again.
The README and user docs specify the finite numeric bounds. Chains enable the
same contact/hit and sensor-detection events as the other native shapes.

`Physics.fixtures` stores each entity's six attachment records and segment
handles in ordinary match lists/maps. Component removal and body replacement
are reconciled against the world, including `Body` removed from a surviving
entity, a removed shape or `Part`, and `Part.of` changes. Stored handles hide a
destroyed part from queries immediately and retain end-contact body ownership
until the step. An exact, bounded snapshot of entity-slot metadata gates the
cleanup scan; zero body handles also invalidate it. This is match state, not
process identity. Source bytes are retained through the ordinary Tide writers.

The common box/circle checks run as native row systems. Their per-world cache
compares the actual source lanes, body generation and filter presence, and is
invalidated by restore and topology changes. Cache misses reconcile against
the match's fixture records. Only changed records return through Tide's owned
list/map writers. Existing sparse `BoxMade`/`CircleMade` registration markers
are retained: removing them changed ECS traversal and the existing Towers
simulation. Stage offsets are distinct through preparation, creation and
reconciliation, so a game's ordering against one named system cannot move
joint cleanup ahead of opening the correct native world.

`CollisionFilter` provides 64-bit `category`/`mask` and signed `group`, with the
same defaults/names as Box3D. Optional trailing `QueryFilter` arguments apply
to current and rewound rays, casts, all-hit queries and overlaps. Capsules,
polygons and segments have every convex query overload. Historical records
retain exact geometry kind and filtering, and use native polygon/capsule/
segment narrow phases, including chain ray sidedness. `Inside` follows the
sensor's collision masks/groups. Sensors still ignore other sensors, including
explicit positive groups: a pure native filter callback is installed at every
create/restore, and enabled for filtered sensors. No callback pointer is saved
in match state. Existing query ordering and native image/body/answer pins stay
unchanged.

`Body` gravity scale, linear/angular damping, sleep speed, fixed rotation and
bullet mode follow later writes. Changed native settings wake the body, before
the existing final deferred sleep pass. Native setting caches are invalidated
on restore. `Physics` is 256 bytes (the old fields retain their offsets),
`Body` remains 96, `Joint` is 88, historical `Collider` is 152, and the checked
inline polygon `Hull` is 88. The new match records change whole-world/sequence
pins; native/WASI agree on replacements. The original stack body pin remains
`a2292c6100587813`, native image-byte pin `b43aa576ef744d1e`, and query-answer
pin `53abf452b7c6e40b`. The complete fixture sequence is `39d1697495a58b42`.

One vendored correction: `b2GetJointConstraintTorque` now returns zero for
mover and pogo joints instead of asserting on valid linear constraints. It is
marked `Tide:` and recorded in `box2d/TIDE.md`. No solver equation, engine,
compiler or platform API changed, and no game workaround was introduced.

`tide_box2d_complete` adds eleven tests: all joint families actually constrain
or drive bodies; all live settings replay after native restore; disabling,
rebinding types and component removal; geometry and filter edits; masks and
positive/negative groups; sensor contents and one-sided rays; current and
historical convex query families; malformed geometry/joints; body settings;
and snapshot/packing/forced-native-restore replay. Every incremental native
image is checked against a whole image. Its sequence pin agrees in native and
WASI debug/release. Existing package, Towers, order and rewind-network fixtures
remain covered, with original motion/image/answer pins unchanged.

Release cost comparison against the previous engine checkout (`f8468b30`),
2,400 crates, three alternating runs of `box2d_costs`: least moving tick
0.646 ms before / 0.748 after, one crate pushed 0.070 / 0.109, and rest

## All-hit queries and game filtering (2026-10-18)

The owner approved `RaycastAll`/`CastAll` and ignore-body overloads after the
prototype gap review. Live `Physics` and detached rewound `Query` now have
`RaycastAll(from, to, out List<RayHit> hits, bool includeSensors = false)`
and an overload with `Body ignore` before the optional sensor flag.
`CastAll` has the same two forms for `Box` and `Circle`, with the existing
`shape, from, angle, to` argument order. Named arguments are `ignore: body`
and `includeSensors: true`. The latter opts into sensors; closest-hit queries
continue to skip them. The ignore handle includes its generation and excludes
every collider on the body, including its parts.

These methods replace the output list, return whether it has any hits, and
give each collider's first hit, sorted by fraction then the existing closest
query's shape-slot tie order. Separate colliders remain separate even when
they have the same body and part entities. These are ordinary `RayHit` values
that the game may filter, save in match/local state, snapshot and pack. An
unstepped world, an invalid/empty rewind context or invalid cast inputs gives
an empty list and false. Live queries still omit destroyed bodies/parts;
an already prepared rewind context retains the geometry it captured.

The bridge uses Box2D's ordinary query callback, returning 1 to keep the whole
sweep. It collects actual hits in 32 stack slots, growing only when needed,
sorts once and writes a checked `out List<Met>`. Growth is bounded by the
runtime's 1 GiB output-list byte limit with overflow-safe arithmetic and the
existing fatal allocation failure path; there is no smaller hit cap or silent
truncation. Each native record is cleared before fields are assigned, including
padding. Tide maps it through `Told`. The rewound path reuses the captured
scene's BVH candidates and narrow phase, then sorts by the same keys. No new
process-global query state, world layout, `Body` or public `RayHit` fields were
introduced. Closest-hit methods retain their clipping path.

The new invalid-input regression also exposed an existing assertion: finite
endpoints whose subtraction overflows passed an infinite sweep to Box2D.
Both closest and all-hit paths now reject that displacement. Starting overlaps
keep fraction 0 and zero normal. Their point has no unique surface meaning;
the native and detached narrow phases can choose different points there.
Valid closest-hit answers and existing determinism pins are unchanged.

`test/query_all.tide` and `packages/test/query_all_test.h` cover rays and both
cast shapes, closest/all-first agreement, equal-fraction order, compounds and
parts, sensor options, body-generation reuse, gameplay filtering, empty and
invalid queries, first-step availability, initial overlaps, 70-hit growth,
fractional rewind, deletion and retained contexts, local/match result storage,
snapshot/pack/restore, and serial/job-pool equivalence. The public-hit digest
is `7533602157f73627`, identical in native/WASI debug and release. Full debug
suites passed (native 2374, web 2284); both query fixtures passed in native and
web release, and the docs build passed. Existing physics/result pins did not
change. User references are `README.md` and `docs/packages/box2d.md`.

Scene visibility unification (2026-10-15): removal of generated scene audience
fields changes only the complete-world and world-sequence pins in stack,
sensors, kit and sleep. Native and WASI agree on all replacements. Body motion,
query answers and Box2D's own image-byte pins stay unchanged; no package or
vendored physics implementation changes. Validation is in notes/language.md.

## Packaging and releases

### Box2D

An experiment the owner asked for (2026-10-05: "we can always remove it"), written as a user's package would be: Tide and C in `packages/box2d/`. What it needed of the engine is general, and noted where it is: jobs, `out List<T>`, systems written in C and `world.Set<T>(this, ...)` beside a read parameter (see Language and Determinism), and how a big list goes to C (`tide_list_flatten`). Its names and its shape aren't agreed, and its `README.md` says what it has and hasn't, and what it costs. Its page for users is `docs/physics/box2d.md`, with a live example (see Docs site).

- `packages/box2d/box2d/src/` is Box2D as it came (`main` at `ac7c751`, MIT, so a game that lists the package ships Box2D's notice), its public headers in `src/box2d/` beside the sources so they're found with no include path, and the changes `box2d/TIDE.md` lists, each marked `Tide:`. `box2d.tide` (namespace `Box2D`) is the components, events and systems, and `bridge.c` their C, whose functions are `b2t_`: tidec keeps `tide_` for the engine, in a package too.
- **The bridge mirrors the generated `Physics` ABI.** With maps carrying insertion-order cursors, each map is 24 bytes aligned to 8 and `Physics` is 152 bytes; `owners`, `parts` and `sensors` start at 80, 104 and 128. The old four trailing padding bytes are gone. The bridge asserts every Physics field's offset as well as its total size against this layout. This changes the match representation and therefore its world hash pins, including the stack, sensors, kit, sleep and Towers matches; body, Box2D image and query-answer pins remain checks of their existing behavior. There is no physics rule change.
- **Box2D's state rides in the match.** Its world is in C's memory, where rollbacks, joins, host migration and reloads don't reach, so after each step its whole state goes into the match: Box2D's own image of its world into `Physics.image`, a `List<byte>`, with `Physics.stamp`, which names it. C's worlds (`worlds` in `bridge.c`, four) are only where a state is stepped: a tick's first system finds the one at its match's stamp (`b2t_open`) or has one made from the image (`b2t_restore`). Two matches at one stamp are at one state, so either's world serves both, as the server's and the client's in one program are. Nothing else is needed for any of it, and nothing in the engine knows.
- **A stamp is the stamp before it and everything done to the world since, hashed** (`note` in `bridge.c`): Box2D's next state is its last and what's done to it. So the image is never read to name it, and everything that changes C's world has to say so there, or two worlds that differ would go by one stamp.
- **Everything that changes Box2D's world happens in the package's systems, from what the match says.** Code moves a body by writing its component: `Enter` compares each with where the last step left it (the `step` fields, which `Leave` writes) and syncs the ones that differ, and a destroyed entity's body is listed (`Physics.gone`) and goes at the next step. A call into Box2D from anywhere else would change C's world after its image was taken, and a machine that then restored would have another world.
- **Its systems are one stage, in an order nothing a game writes can change** (`PhysicsStages.Step`, an enum of one member; each system says its offset in it: `Begin` 0, `Enter` 1, `Own` 2, the shapes' 3 and 4, the parts' shapes' 5 and 6, `DropParts` 7, `Simulate` 8, `Leave` and `Report` 9). Ordered only by where they were declared, a game's `[Before(Step)]` moved the step itself to after `Leave` and `Report`, and `[Before(Enter)]` moved `Enter` to after `Own`, which stopped the program. What a game uses, and the docs teach, is one thing: `[Before(PhysicsStages.Step)]` on a system that has to write into this tick's step, which then runs before all of them. The names `PhysicsStages` and `Simulate` are agreed (the owner, 2026-10-06). What code relies on:
  - The system that steps is `Simulate`, not `Step`, on purpose: a system of a game's that's `[Before(Simulate)]` runs after `Enter` gave Box2D what code wrote, and `Leave` then writes the step's own over what it wrote of a body's place and speeds, silently. With no system of that name, `[Before(Step)]`, which is what one writes first, is an error. Don't name a system of the package's `Step`.
  - A game's system with no attribute runs after the stage in a game where none is before it. Once one is, the ones declared before that one run before the stage too, by the default order (the package waits for a system that comes after them): `[After(PhysicsStages.Step)]` holds one after. The docs say so.
  - `tide_box2d_order` (`packages/CMakeLists.txt`, `tide_package_order_test`) runs `tidec --schedule` on `test/order.tide`, a game that orders a system each way against the package's, with the package as tide builds a game that lists it (`--package`), and compares the order of the systems' names with `test/order.txt`; `box2d_orders_a_games_systems` (`test/course_test.c`) checks that what's written before the stage is in that tick's step, and what's written after it in the next.
- **A body's impulses are given once, and a new body's by the step** (`push_new` in `bridge.c`): `Enter` makes a body before the systems after it put its shapes on, when it weighs nothing, so the impulses its component was spawned with are kept with the body in `made`, for the tick, and `b2t_step` gives them right before it steps. They're noted where they always were, with the body's component (`sync_body`), and bodies that are there already get theirs from `Enter` as before, in the order of its rows.
- **A body code moves wakes, and what it touched** (`b2Body_SetAwake`, `b2Body_WakeTouching`, after `b2Body_SetTransform` in `sync_body`): Box2D moves a sleeping body and leaves it asleep, hanging where it was put, and code has no other way to say. **Gravity that changes wakes every body**, and is stepped though nothing was awake: `b2t_step` compares the gravity it's given with the world's own (`b2World_GetGravity`), which is in the image, so it's the last step's wherever the world came from, and turns sleeping off and on again (`b2World_EnableSleeping`), which is the one call Box2D has that wakes everything; with `Physics.sleeping` off it turns on and off instead, leaving the setting as the match says, because manually sleeping bodies still need to wake. Neither is noted: the first follows from the move and the second from the gravity, which are.
- **A body says whether it's asleep, and code that writes it puts the body to sleep or wakes it** (the owner, 2026-10-06: "we might also want to allow to manually Sleep/Wake bodies"; that it's a field of `Body`, `asleep`, with no function for it, and every rule here are Claude's picks, which the owner hasn't confirmed: `docs/physics/box2d.md`, Bodies at rest). After each step `Body.asleep` is Box2D's, as a body's place is: true for a dynamic or a kinematic body the step has no work for, and never for a static one. Box3D's package has the same, rule for rule (see Box3D, A body's `asleep`; brought onto dev 2026-10-07 from the branch it was built on, with Sumo's ring put to sleep after its one step). What code relies on:
  - **A write is told by a second field, `stepAsleep`, the package's own**, as a body's place is by its `step` fields: `Enter` compares the two, a byte each of the four a body's bools are in (`FLAGS`, `flags_asleep`), with no call into Box2D. Asking Box2D whether the body is awake, and comparing, was what was to be preferred, and doesn't hold: by the time `Enter` comes to a body the tick may have woken it already (`Begin` destroyed a body beside it, `Enter` moved one before it in the rows), and Box2D's answer would read as code having written `asleep = true`. A body's type is told the other way (`kinds`, below), which holds because only code changes a type, where every step changes what's awake. The two bytes are two of the six a `Body` had to spare after `bullet`: it's 96 bytes as it was, with no lane more, and a world where nothing sleeps is, byte for byte, the world it was.
  - **Waking is `Enter`'s, and sleeping the step's, last** (`lulls`, `put_to_sleep` in `b2t_step`: after the world's tuning, the new bodies' impulses, the gravity and what a new one wakes). Newborn sleepers join the same deferred list, so gravity or automatic sleeping turned off in their creation tick cannot override their sleep. Box2D sleeps and wakes an island at a time, so a body put to sleep where `Enter` came to it would be woken again by whatever the tick wrote into a body of its island further down the rows: by which of them comes first, that is. So what code puts to sleep in a tick is asleep as the step starts, whatever else the tick wrote: a push or a speed written with it is lost, a place written with it is where it sleeps, and a new gravity in that tick doesn't wake it. A body another runs into in that step wakes all the same. Both are noted where `Enter` syncs the body, with its component as code wrote it and a bit of `did`, so nothing is noted at the step.
  - **Only a write does anything.** `asleep = true` in a body that's asleep already is nothing written, so such a body that code moves wakes, as any that's moved does, and so does one a new gravity wakes: `asleep` is false after that tick, and code that wants it asleep says so then. A static body's `asleep` is written back false wherever `Enter` syncs it (`sync_body`), with nothing noted for it: one that was written asleep, and a sleeping body that was just made static.
  - **It works where `Physics.sleeping` is off**: Box2D's switch only says what the step does, and a body that's put to sleep there stays so until something wakes it.
  - **An island is the bodies that touch each other, as the last step found them**: every touching contact between two bodies of which neither is static joins their islands (`b2LinkContact`), a kinematic body's too. So a stack goes to sleep from any of its crates, a crate that slides along a plank stops where it is when the plank is put to sleep, a lift goes with what stands on it, and two crates on one static floor are apart. What hasn't touched it yet stays awake, and wakes it when it does. A body that's put to sleep has no speed any more (its `b2BodyState` goes): `Leave` writes zeros.
  - **`Leave` writes the field for the bodies the step says something of**: awake for one it moved, asleep for one that fell asleep in it (`left.awake`). Of any other it reads the field only in a tick whose step put bodies to sleep for code (`slept`): Box2D says none of which bodies an island took along, so each that was awake by its component, isn't static, and that the step says nothing of is asked (`b2Body_IsAwake`). The flags are only asked for to write once a body's changed.
  - **Spawned asleep** is `b2BodyDef.isAwake`: alone in a set of its own, where it's spawned, with none of the speed or the impulses it was spawned with (`made` gets none for it). Bodies spawned asleep on each other are each an island, as no step saw them touch: one that's hit wakes, and the ones on it a contact a step. Where there are thousands, that costs more in the ticks many wake than a stack that sleeps as one (measured in 3D, with Sumo's ring, on the branch above): the docs say to spawn such bodies awake and put them to sleep a tick later.
  - **The one change to Box2D's sources**: `b2TrySleepIsland` looked a body's move event up among the last step's, which a world that was made from an image has none of, so a body put to sleep before such a world's first step wrote past them (`box2d/TIDE.md`).
  - **Putting a body to sleep and waking one are calls Box2D's image in parts follows** (`b2SnapNoteOp`, which named `b2Body_SetAwake` already, for the wake of a body that code moves): `tide_box2d_sleep` runs with every image in parts compared with the image written whole (`b2t_check`), 253 of its scripted match's 320, and `tide_box2d_parts` puts bodies to sleep at random right after a restore too, which it kept away from until `b2TrySleepIsland` was changed.
  - **Pins.** The bodies' pin (`BODIES_HASH`), Box2D's own images' (`BYTES_HASH`) and what was answered (`ANSWERS_HASH`) didn't move: every image is the bytes it was. The worlds' did (the stack's two, the sensors' two, the kit's three, and Towers' two), with the worlds stepping as they did: a sleeping body's `asleep` and `stepAsleep` are 1 where its component had two zeros, and a stamp notes a body's component as code wrote it, so a body that was asleep when code pushed it is noted otherwise, which every stamp after it carries (with the two bytes left out of the note, the pinned match's last world had the hash it had before: tried).
  - `tide_box2d_sleep` (`test/sleep.tide`, `sleep_test.c`: a game built with the package as tide builds one that lists it) is its tests, each a few bodies: a resting crate put to sleep, which then costs nothing, and woken in a world at rest, where the write is seen; one made static while it sleeps; a world whose bodies don't fall asleep; a falling crate put to sleep, which hangs where it was until a ball hits it, and one put somewhere else and to sleep in one tick; a plank and the crate sliding on it, a lift and the crate on it, and one of an island put to sleep while another is pushed, either way round; a stack from its bottom crate, with a crate on its way down that wakes it; bodies spawned asleep, three of them on each other; gravity; and a match that does all of it from a system, at its ticks, whose hashes are pinned, the same in debug, release and on the web, and which is run again from a snapshot three times, from its packed bytes, and with C's world made from the image before every tick.
  - **What it costs against `dev` at `c5753f2`**: `box2d_costs`, release, 2,400 crates, seven alternating runs behind the continuation benchmark gate. The least tick was 0.739 ms before and 0.910 after with everything moving, 0.084 and 0.078 with one crate pushed, and 0.019 and 0.019 at rest. The moving ticks ranged from 0.739 to 1.317 before and 0.910 to 1.284 after, with concurrent browser tests and builds taking about 43% CPU before the round: these do not establish the cost of the extra field under quiet conditions. No regression is visible with one crate moving or at rest. The image is still 2,549,152 bytes, the same bytes as before; the moving run writes all 120 images whole, the one-crate run 13 whole and 227 in parts, and rest writes none. The image's least time was 0.092 and 0.141 ms for the whole moving world, and 0.013 and 0.013 in the one-crate run. This round supersedes the comparison made before Box2D's image in parts was merged; its raw runs remain in the task's `build/sleep-wake-costs-contended.txt`.
- **A sensor sends `Touched` and `Parted`** (`b2t_touches`, `b2t_touch`: the step's contact events, then its sensor events, each a sensor's shape and the shape that came into it or left). What code relies on:
  - Box2D only reports a shape to a sensor when both were made with `enableSensorEvents`, which is off by default, for a sensor too: every shape is made with it (`shape_def`). It's a byte of each shape in the image, which is what moved the pinned hashes when sensors were built (below).
  - Sensors see each other in this Box2D, each reporting the other: the package's are made in one collision group below zero (`filter.groupIndex = -1`), which Box2D never sets against each other, so a sensor doesn't report another, and nothing is heard twice.
  - What a sensor has in it is in the image (its arrays of visitors), and a step's events aren't, so a world made from an image says the same after its next step. Upstream writes a visitor as its 8 bytes, of which 2 are no field's: `snapshot.c` writes zeros there (`b2SerVisitors`, `box2d/TIDE.md`). Without it the match of sensors had another hash of its images in a debug build than in a release one.
  - A shape that's gone has no owner (`owner_of`), so `Parted` from an entity that was destroyed while they touched comes with `default` for `other`, from a sensor as from a contact (decided to leave it: saying which entity would take keeping whose each body was for a tick after it's gone).
- **A `Body`'s `position` is `[Position]` and its `angle` `[Rotation]`** (see Networking), so views see it turn the short way where Box2D's angle goes from π to -π, and glide through a correction. They change nothing of the match, which the pins show.
- **The image is in the match's hash, so it's the same bytes on every machine for the same state**, which Box2D doesn't promise by itself: its own determinism check is of bodies. The changes for that: `userData` as wide on 32-bit platforms, a layout hash that doesn't name the pointer's width, a tree's capacity as a restore would leave it, and a contact point's `normalVelocity` decided per contact, where upstream decides per block of 4 or 8 by the CPU's SIMD width (the same simulation, other bytes on an AVX2 machine than on the web).
- **The image is in sections that keep their place** (`b2World_GetSnapshotAt`, `place` in `bridge.c`): a table after its header says where each of 17 starts, and each stays where it was while the one before it leaves it between none and a quarter of itself to spare. Upstream's image is one run of bytes that starts with its parts of changing size, so a contact that starts or ends moved every byte after it. Where the sections go is part of the state: a restore takes it from the image's table. It's what makes a tick's image differ from the last where the world does, which is what the match's snapshots can share and what's hashed again.
- **An image is written as what changed of the last one, where Box2D can say** (built 2026-10-06, a card the owner asked for; `b2World_GetSnapshotParts`, `snapshot.c`; `b2t_image`, `bridge.c`), by the design Box3D's has (see Box3D, An image is written as what changed of the last one, for what's the same: one writer that writes both, the match's list keeping the rest through `tide_list_out_keep` and `tide_list_out_part`, every call that changes a world going through one gate, and `b2t_check`). So what the package adds to a tick goes by what's awake, where the image written whole goes by how big the world is. **The image the parts make is, byte for byte, the image written whole**: no pin moved, in the package's tests or in Towers', and the pins of `tide_box2d_stack` are of images written both ways. What's Box2D's own, which code relies on:

It goes on for as many ticks as it takes another thread to have answered, as `platform/tests/jobs.c` does, and its crowd never sleeps (`Physics.sleeping` off): a world at rest isn't stepped, a tick with no step to share runs on one thread, and no other thread would ever answer. Asserting it of the first 60 ticks failed on CI's two-core runners and, under load, on the web, where a pool's workers start late.
    - **A cast shape that's flush with something touches it** (Box2D counts within about 6 mm), at fraction 0 with a zero normal: code that slides a shape along what it rests on casts a slightly smaller one. The docs say so, and Towers' `Slim` does it.
    - Left out, and listed in the docs: every hit along a ray, layers and masks, more than one body left out, sensors as things to meet, other shapes to cast.
  - **`Inside(physics, sensor, out found)` takes an entity, as Box3D's does**, and reads its sensors' visitors (`b2Shape_GetSensorData`), which are in the image. A function has no `World`, so the match keeps each entity's sensor shapes: `Physics.sensors` (`Map<Entity, Sensors>`, a box's and a circle's handle), written where a shape that's a sensor is put on (the four `Attach` systems) and taken out by the `Destroyed` handlers, with an entry only for entities that have a sensor. An entity's own sensors are what's asked: a body's parts are entities of their own.
  - **The names are Box3D's wherever both packages have the thing** (reconciled the day both landed, 2026-10-06, Box3D's first): `Part { of }`, `part` and `otherPart`, `Hit`, `RayHit`, `Raycast`, `Cast`, `Overlap`, `Inside` by entity, `contactStiffness`, `contactDamping`, `contactSpeed`, `bounceSpeed`, `hitSpeed`, `sleeping`. A name that changes in one changes in the other. What differs is listed in the package's `README.md` (Picks): this one's `Hit` says the parts, its rays and casts leave a `Body` out, and a `Body` has `sleepSpeed`; Box3D's body settings other than the type follow later writes, and this one's don't.
  - **`Hit`** is sent to both bodies that meet faster than `Physics.hitSpeed`, from Box2D's hit events (`b2t_hits`, `b2t_hit`), with the point, the normal (from the receiver into the other: the second entity gets it turned round) and the speed. Box2D only reports a contact between shapes made with `enableHitEvents`, off by default: every shape is made with it (`shape_def`), a byte a shape in the image, which also has the solver keep each contact's `normalVelocity` (see `box2d/TIDE.md`). That's what moved the image's pin. Events of a step aren't in the image, like the contact events.
  - **Tuning is fields of `Physics`**: `contactStiffness`, `contactDamping`, `contactSpeed` (Box2D's contact hertz, damping ratio and push-out speed), `bounceSpeed` (its restitution threshold), `hitSpeed` and `sleeping`, each Box2D's own default, so a game that sets none has the stamps it had. `tune` in `b2t_step` compares each with what C's world has, which is in the image (`b2World_GetContactTuning` is ours, the one vendored change of this work: upstream has the setter alone), sets what differs and notes it (`'k'`, `'r'`, `'i'`, `'z'`), which makes that tick step. `Body.sleepSpeed` (Box2D's sleep threshold) is read when the body is made. Box2D counts contact hertz up to an eighth of the substep rate, 30 at 4 substeps and 60 ticks, the default: stiffer needs more substeps, which the docs say and `box2d_a_tall_stack_stands_longer_with_stiffer_contacts` shows (30 crates and a heavy one dropped on them: 22 off at 15, 15 at 30, none at 60 with 8 substeps; 60 at 4 substeps is 30).
  - **Nothing in `compiler/`, `engine/` or `platform/` changed for any of it.** What got in the way, each worked around in the game or the package: a `local event(Spawned)` handler that takes a component nothing ever spawns (only `Add`s) generated a `tide_hear_Spawned` nobody called, which `-Werror` refused (Towers lights a landed brick from its own `Landed`, sent to the brick; it builds since 2026-10-07, as arriving entities are heard through that function, but such a handler still hears nothing in the tick that adds the component: see Networking, Local handlers of match events); and the public helpers and the names above.
- Box3D is the same package for 3D (below).

## Collider history and query contexts (2026-10-11)

Current queries are Physics singleton methods (`physics.Raycast/Cast/Overlap/Inside`), including existing ignore overloads; helpers are methods too, with no free-function aliases. `Body.rewind` opts a body and all its parts into bounded history enabled by maxRewind. The bridge captures native local geometry/pose at the completed physics step; SealHistory registers the approved internal tick-completion callback. After queued changes apply, it refreshes final body Snap counters and removes colliders whose body/part entities despawned at that endpoint. Old frames retain historical entity generations. Disabled history does no capture or bookkeeping; disabling after reload clears retained history. History is ordinary match lists/maps, so snapshots, hashes, packing and rollback include it.

`physics.Rewind(ViewTime, out Query)` explicitly prepares detached readonly geometry once for a batch. Invalid/stale/future times or unavailable endpoints return false and an empty context, with no clamp/fallback. Opted-in poses interpolate; shape membership/geometry use the upper endpoint, and Snap blocks blending. Current non-opted walls/geometry remain in the scene; live opt-out uses current geometry. All existing queries work on Query, with native body overlap order and shape-slot ties. Native exact geometry helpers validate finite values/counts. Contexts retain no native pointers or mutable contacts. An immutable preorder BVH prunes candidates; sorting short candidate lists preserves native order. Rays preserve Box2D's starting-overlap behavior.

`rewind` covers current moving walls, interpolated boxes/circles and parts, all cast/overlap forms, sensors, ignore, queued Snap/despawn endpoints, opt-out, saved contexts, malformed/unavailable times, expiry, pack/unpack, snapshots and readonly world hashes. Its 1,024-collider/1,000-ray batch compares current native queries with historical queries. Release on this Windows machine: prepare 0.93 ms; batch historical 0.22 ms versus current 0.12 ms (one measured run, timing informational). Existing world/sequence pins changed for the added Body/Physics/Time schema; native body results, answer hashes and Box2D image bytes are unchanged.

rewind_network adds 28 end-to-end two-client profiles shared with Box3D (packages/test/rewind_network_test.c). The oracle is the last verified view's actual rectangle draw position, retained before Sample; normal engine stamps, input packing, lossy loopback delivery and server validation precede the query. It checks moving player-owned boxes, reversals, both hits and misses, exact presented stamp equality, hit-point/fraction error below 0.0001, and per-shot age-based rejection beyond the 250 ms window. Independent server/client/update/render rates, stalls and network conditions are detailed in notes/netcode.md. Accuracy here is for translating axis-aligned boxes; existing rewind tests cover other shapes/rotations. This does not measure GPU/display scanout or real Internet traffic.
