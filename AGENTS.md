# Tide: Agent Guide

Rules and decisions for anyone, human or AI agent, working on Tide. Only agreed decisions go in this file. Open questions stay out until they're decided.

## Working agreement

- The project owner is the lead programmer and writes most of the code.
- Agents help with specific, scoped tasks. Do what was asked. Don't widen scope, scaffold systems, or refactor nearby code unless asked.
- Agents validate changes locally and merge directly into `dev`. Do not create pull requests or push feature branches unless the owner explicitly requests them.
- If it's unclear whether the owner wants code or discussion, ask.
- **Exception: Claude owns the transpiler.** The owner decides the language design (what it should do, its syntax and semantics). Claude implements and maintains the transpiler, including its tests and build integration, and proposes designs for the owner to approve.
- The contract between the two sides is the C the transpiler generates and the engine runtime functions that code calls. The owner writes the runtime. Any runtime function the generated code needs is agreed on before either side depends on it.

## What Tide is

A networking-first game engine:

- The simulation is deterministic and uses floats, not fixed point, on supported hardware.
- User code and the engine's built-in systems are written in a custom language that compiles to native code.
- An ECS runs systems on multiple threads automatically. Data dependencies come from the ECS and the language, so users never have to think about threads.
- Graphics work is kept to a minimum. Rendering is not the focus.

## Platforms

- The main targets are desktop and consoles.
- Mobile is a target too: Android first, then iOS.
- A phone that goes to the background, or closes, can no longer simulate, so it leaves the match: with host migration on (see Networking), another player's machine takes over the match it hosted. Nothing keeps a phone's match running in the background.
- Touch is input on every platform, not only phones: the web (on phones and desktops) and desktop touchscreens have it.
- The web (WebAssembly, rendering with WebGL) is actively supported and tested, not an afterthought. Changes must keep the web build working.
- Determinism holds on every platform, the web included, so web and desktop players can share one simulation.

## Rendering and platform

- Windows, input and rendering are the platform layer's own, with no engine under it:
  - `platform/src/platform.c` is the frame loop, the devices and the renderer. What it needs of the system is `platform/src/window.h`: a window, what draws in it, and what its input devices say. Each build has one: `platform/desktop/glfw.c` (GLFW, for the window, keyboard, mouse, gamepads through its mappings, and clipboard), `platform/web/canvas.c` (the page, through `tide.js`) or `platform/android/activity.c` (NativeActivity and EGL).
  - The renderer is written once, against `platform/src/gpu.h`: buffers, textures, pipelines, targets and passes, whichever API is under them (shared, agreed, rather than a renderer per backend). It's shaped by WebGPU, the strictest: a pipeline is made once with its shaders, the vertices it reads and how it blends and tests depth; its uniforms are one block of bytes; drawing happens in passes that start cleared or as they were left, so a clear inside a list is drawn (a triangle over the target, which the clip cuts, and which sets depth back). Clip space is OpenGL's, and pixels and rows count from the top left; each backend turns those into its own. Compute joins it when Tide code computes on the GPU.
  - Backends so far: OpenGL (`platform/src/gpu_gl.c`: OpenGL 3.3 on desktop, OpenGL ES 3 on Android, WebGL 2 on the web) and, on the web, WebGPU (`platform/web/gpu_web.c`, whose functions are the page's: `tide.js` has the WebGPU objects, as it has WebGL's). Vulkan is next. The window says which draws (`tide_window_gpu`), and `tide_platform_renderer` names it; the stats overlay shows it.
  - The web draws with WebGPU by default, and with WebGL 2 only where that isn't possible (agreed): the browser has none, gives no device, or only its software one, which is slower than WebGL on a GPU. The page asks for the device before the program starts (`tide.js`), as asking takes a while and the program can't wait for an answer. `Tide.backend`, or `backend=` in the page's address, is `webgpu` (the software one too, and no falling back) or `webgl`: for tests, and for a player whose browser gets one of them wrong. A device that goes away while the game runs (a driver that starts over) takes what was made on it: the page asks for another, and the renderer, which sees it's another (`tide_gpu.epoch`, `gpu_ready` in `platform/src/platform.c`), forgets what it had there and makes it again as lists draw, from the copies the lists and the font keep. Nothing draws meanwhile. `tide_platform_draw_webgpu` loses its device on purpose and checks its pixels again. A canvas that draws with WebGPU can't go to WebGL, so with no device to be had again it stays as it is, and the page says to reload.
  - `platform/src/gl.h` is OpenGL as its backend uses it: only the functions it calls, which the three share, with no system header. On the web they're the page's (`tide.js` has each by its C name), on Android libGLESv3's, and on desktop they're looked up in the window's context through GLFW (`platform/desktop/gl.c`). A function it starts calling is added there and in `tide.js`, and it uses no extensions.
  - The renderer's own shaders (shapes, text, clears, the built-in meshes) are in `platform/src/shaders.h`, each written by hand for every backend: GLSL (one source, with a version line per platform, attributes at fixed locations, uniforms in a std140 block) and WGSL. A change to one goes to the other, and the same tests check both draw the same pixels. A game's shaders are tidec's, from its `frag` and `vert` declarations (below).
  - A pipeline samples up to 8 textures (`pixels0`... in GLSL; in WGSL, texture i and its sampler at bindings 1 + 2i and 2 + 2i), each through a sampler of the backend's, nearest or blended, so one texture can be read both ways in a draw (OpenGL's are sampler objects, bound by unit). Its vertex attributes are floats or ints (`TIDE_GPU_INT`...), 16 at most, and its uniform block 4096 bytes at most (`TIDE_GPU_MAX_UNIFORMS`), of which a game's shader has 3984 of its own (`TIDE_SHADER_UNIFORM_BYTES`, which tidec checks at the draw) after the engine's 96 (its camera, the screen and the tint): 255 float4s in all, as Android's emulator links no shader whose block is 256, counting its members as the vertex shader's uniform vectors; on WebGPU a draw's uniforms take as many 256 byte slots of the uniform buffer as they need. `pipeline_free` lets one go.
  - A backend sets all the state it draws with at each pass, so nothing depends on what drew before it: a pass on another target or, on the web, the build this one took over from (see Hot reloading).
  - Text is `stb_truetype`'s (`platform/third_party/stb_truetype.h`, version 1.26 from nothings/stb, public domain, kept static to `platform/src/font.c` so a game's C can bring a copy of its own), in Tuffy, in two weights, each a file: regular (`platform/font/Tuffy.ttf`) and bold (`platform/font/Tuffy_Bold.ttf`), both version 1.28, from the one archive at tulrich.com/fonts (`tuffy-20120614.zip`), under the one `LICENSE.txt` beside them, public domain too, so games carry no license terms for any of it; GLFW's zlib license asks nothing of binaries. The build puts each in the library as an array (`cmake/embed.cmake`), an object of its own. A text's size is its font size, as CSS's and Unity's: the height of a line of it, with its capitals in the line's middle (what the font draws past a line, accents above and tails below, goes past evenly). Text has to be sharp at the sizes it's read at, and the font has no hints (stb_truetype would read none), so it's fitted to the target's pixels (`platform/src/font.c`): drawn at the whole number of pixels nearest its size, never stretched (but past 128 pixels, where nobody sees it); each glyph's outline moved onto them before it's drawn, as a hinted font's is; and each glyph a whole number of pixels from the last. The fitting finds a glyph's stems in its outline (an edge is a run of it along an axis, a straight side or a curve where it turns back; two edges that are each other's nearest across ink are a stem): upright stems and flat ones (bars, the tops and bottoms of bowls) are a whole number of pixels thick between pixel edges, those about as thick as the font's usual stem all alike, so letters keep one weight; the heights letters share (the baseline, the x-height, the capitals', the descenders') are on the same pixel edges in every glyph, and what round letters go past them by is dropped until it's a pixel; and the rest of the outline moves in proportion between the edges that moved. Stems and bars then fill their pixels, where an outline drawn as it falls blends them between two. What's slanted or round still covers pixels in part, and colors blend as the display's values, not as light, so light text's parts count for more (the text shaders, `platform/src/shaders.h`: a pixel's share to a power under 1, 0.55 for white), or they'd fade beside the stems; dark text is as it is. `tide_platform_font` (`platform/tests/font.c`, no window or GPU, so every platform's tests run it) checks that glyphs of upright and flat strokes have no pixel covered in part at any size from 8 to 48, and that letters share their heights and their stems' thickness, in both weights. Glyphs are drawn the first time each is needed at a size and in a weight into an atlas of a byte a pixel that grows as it needs, and text goes to the GPU as two triangles a glyph. `tide_platform_measure_text` is the size that's drawn (`tide_font_size`): its widest line by the same whole-pixel advances, and its lines' height, a line as high as the size and each newline the whole pixels lines are apart (`tide_font_pitch`, which drawing uses too), at the window's scale or, for a render target, at its image's own (the `tide_target_size` it's given). It needs no window open. It's the `tide_measure_fn` (`tide/draw.h`) hosts give the GUI, and what Tide code measures with: `Draw2D.MeasureText` is `tide_draw_measure_text` (`engine/src/draw_coordinates.c`), which asks it at the size the frame's 2D camera draws text at and gives the answer back in the units the view draws in, so a view measures what it draws, to the pixel. A host with no measure function gets a guess (`tide_draw_guess_text`). `tide_platform_draw` (`text_measures_as_drawn` in `platform/tests/draw.c`) draws text in parts, each where the last measures to, and checks they're the pixels of the text drawn at once, in both weights.
  - A text's position is a place of its box (agreed): `Draw2D.Text(text, position, size, color[, anchor][, font])`, with the GUI's `Anchor` (`tide_anchor`, in `tide/draw.h`), its top left corner without one. The box is what `MeasureText` gives, upper is towards the top of the screen under a camera too, and each line is against the anchor's side. The command keeps the anchor (`tide_draw_command.words`), and the platform places each line (`line_start`, `add_text` in `platform/src/platform.c`), on whole pixels as ever: text at an anchor is, to the pixel, its lines drawn from the corners its box puts them at, which `text_anchors` in `platform/tests/draw.c` checks for the nine, on the screen and under a camera, with one line and several, in both weights. `Anchor.UpperLeft` goes through the arithmetic it always did.
  - Bold is the font's own bold weight, an argument of the draw (agreed: `Font.Bold`, as `Filter.Point` is an argument), and a game that never uses it doesn't carry its file (agreed). How:
    - C names a weight by its file: `TIDE_FONT_REGULAR` (NULL) or `TIDE_FONT_BOLD`, the array `tide_font_bold_ttf` (`tide/draw.h`). `tide_draw_text_at` takes one, and so does a renderer's `tide_measure_fn`. A text command only says it's bold (`words.bold`), and its list has the file (`tide_draw_list.bold`, set by the frame's first bold text and cleared by `tide_draw_reset`), which the platform draws with. So the file reaches the renderer as data, from the code that draws with it.
    - Nothing in the engine or the platform layer names `tide_font_bold_ttf`: no source file of either may. Its array is alone in its object (`tide_font_bold.c`, which the build makes) in the platform layer's library, which stays a static one, so a linker only takes that object out for a program whose own code names the array. Generated C does for a game that says `Font.Bold`, or makes a `Font` of a number (`program.names_bold`, in the `tide_font_file` helper that turns a `Font` into its file), and for no other.
    - That's a program's link: CMake's, and `tide build`'s on every target. `tide run`'s library of the game has none of the platform layer, as its host does, so for a game that names the file (`game_info.bold`) tide links the library with the platform layer's too, which gives it that one object (`link_objects` in `compiler/cli/build.c`). A program with no platform layer that such a game is built into (a test's host, a server) needs the object too: `tide_add_game` links a `HOST`'s program with `tide_font_bold`, a library of that one object (`cmake/Tide.cmake`), so `duel_tests` builds as it did; a host built some other way links the platform layer's library, or defines the array itself, as nothing draws with it there.
    - `platform/src/font.c` keeps what it measures of a font per weight (`weight`: the file, its lines, its advances, and the fitting's heights and usual stems), and a glyph's key has its weight's number, which is another whenever a weight's file is: a game's library that was built again has its own copy of it, at another address, and nothing of the old one is read again. Both weights have the same lines, so text of both stands on one baseline. A code point the bold weight has no glyph for (it has 887 code points of the regular's 1499) is the regular weight's, drawn and measured so.
    - Stems are a whole number of pixels thick in both, by each weight's own usual stem, so under 13 pixels both are one pixel thick (and at 20, both two): there, bold differs in its letters' shapes and widths alone. Nothing fattens it to tell them apart. What the agreed design left open (this, the regular weight's name, what a missing glyph is) is in `docs/spec.md`, Views and drawing, awaiting the owner.
    - The GUI, the stats overlay and the debug views are in the regular weight.
    - `tide_platform_font_files` (`platform/tests/font_files.mjs`, every platform) reads two games as the build left them, `tests/text.tide`, which says `Font.Bold`, and `tests/text_plain.tide`, which doesn't, and checks the bold's file is in the first and none of it in the second. `tide_platform_text` is also text to look at: `build/debug/bin/tide_platform_text --frames 2 --capture text.png --size 1180 900` draws both weights at the sizes text is read at, light on dark and dark on light, and a text at each anchor.
- Tide code runs on the GPU on the backends there are (agreed, ahead of Vulkan): `frag` and `vert` (see `docs/spec.md`, Views and drawing), which tidec compiles to GLSL (OpenGL 3.3, OpenGL ES 3, WebGL 2) and WGSL (WebGPU). What the GPU computes is for what's seen, never the match: GPUs don't give the same bits everywhere.
- The agreed order from here, with OpenGL staying as a small fallback for machines without the main backends (browsers without WebGPU, older phones):
  1. Vulkan natively (MoltenVK on Apple until a Metal backend is worth writing), under the same `gpu.h` as WebGPU: explicit pipelines, buffers and compute. tidec writes SPIR-V for it then, beside GLSL and WGSL.
  2. The rest of render state (which side draws, depth, masks), as draw settings like the ones there are (below), frags with other outputs than one color (drawing into a texture is there already: render targets), and Tide code that computes on the GPU. On the OpenGL fallback, compute runs on CPU threads instead, so games work everywhere.
  - How a draw blends was part of that second step, and the owner brought it forward (2026-10-05), with tints, transforms and the settings rule: "these are things we need as part of the foundation of our drawing apis".
- Rendering stays disconnected from the simulation, so it can be replaced later (for example for consoles):
  - The simulation never includes a platform header.
  - The view reads the world and draws it. It never writes simulation state.
  - The platform layer's only link to the simulation is filling `Devices`.
  - Game code never shares a source file with the system's headers or GLFW's: generated headers name types after the game's components (`Transform`), and those define many of the same names. Hosts include `tide/platform.h`, which includes neither, and `tide_platform` keeps them private.
- `tide/run.h` is the standard host: `tide_run(&(tide_run_desc){.title = "...", .argc = argc, .argv = argv})` opens a window and runs the game in a session (`tide/session.h`), sampling this machine's input from the devices once per tick it runs, and draws its views and their GUI. The devices keep what happened for the next sample (a key that went down and up between two ticks, how far the mouse moved), and a sample clears them (`tide_devices_consume`). Where no tick can sample, the host clears them itself at the end of each frame (`tide_run_frame`): in a game with no input, and while the session isn't connected (in no match, connecting, or finding a match that changed hands), which is the session's to say, never a count of frames. So a match started from a menu reads what's held as it starts, never what was pressed before it; in a match that runs, a frame with no tick clears nothing. `tide_platform_web_first_tick` (`platform/tests/web_first_tick.c` with `first_tick.tide`) checks both in a page, and `tide_platform_first_tick` (`first_tick.mjs`, label `gpu`) the first in a run with no window. When `Main` is the match's, it starts at once, and opens it with `--host [port]`, or joins another with `--join code` (a room's) or `--connect address`. This machine's player joins before the first tick. A game needs no other C. Its loop is in `tide/host.h`, which runs a game through a table of its functions (`tide_host_game`), so that `tide run` can swap builds (see Hot reloading).
- Seeing what a game draws needs no window (agreed: agents never open one on the owner's screen, and CI wants pictures too; the names are provisional). The standard host runs a game headless when its command line has `--capture <file.png>` (the run's last frame, as a PNG), `--frames <n>` (the run ends after them) or `--script <file>`, with `--size <width> <height>`, `--scale <s>` (as on a display scaled that much) and `--seed <n>` (the seed of its matches, below), so every game `tide_add_game`, `tide run` and `tide build` make has it: `build/debug/bin/duel --script play.txt --size 1280 720`. `tide run` passes them on and runs the game once: nothing is watched or reloaded, and tide's exit code is the game's. It's the way to look at a game: no scratch host, no hidden window of one's own.
  - A script (`platform/src/script.c`, `docs/tools/cli.md`) is a line an event, the frame it happens at (from 1, in order) and what: `120 key d down`, `200 key enter` (a tap), `210 mouse 640 360` (logical pixels from the top left), `211 button left`, `220 move 40 -8`, `230 scroll 0 -1`, `260 text K7QF2M`, `300 touch 1 down 100 200`, `330 pad buttonSouth down`, `400 capture fight.png` (beside the script) and `500 quit`. A line that's wrong is named, with what to write, before anything opens.
  - `tide_platform_open_headless` (`platform/src/platform.c`) is what the host opens. Its window is GLFW's, never shown, and only there for its graphics context: frames draw into a target of the platform's own (`gpu_state.frame`), the size asked for times the scale, through the path a window's frames take (not `offscreen`), so text is measured and fitted at that scale, and the stats and the profiler are in the picture. `tide_platform_frame_pixels` reads a frame whole, and `tide_platform_capture` writes it as a PNG (`platform/src/png.c`: ours, from the RFCs, deflate's fixed codes with matches, or stored blocks where that's shorter, so a frame of flat colors is a few kilobytes).
  - Nothing about a run is this machine's, or timed. The frame loop makes time up, a 60th of a second a frame (`step`), frames are counted, and the host's session takes no clock and no entropy (`tide_run_new_session` in `tide/host.h`, which every session the host makes comes from), so its matches start with seed 0 and a game that rolls plays the same every run. `--seed <n>`, from 0 to 2147483647, picks another seed, to see the game roll otherwise: it's the seed of every match the machine starts in that run (`tide_session_desc.seed`, which a session with no entropy starts its matches with). It's the standard host's on every platform and with a window too, where it stands in for the system's entropy, and `tide run` passes it on. The devices are made up too (`script.c` says what `window.h` would, and `tide_platform_poll` takes it the same way, so the GUI's hiding and views' claims go as in play): never the system's, as even a hidden window knows where the real cursor is. The cursor locks whenever the game asks, and the clipboard is left alone. So a run's match is the same on every machine, and its pictures on one machine byte for byte; GPUs differ in what they blend.
  - Exit codes: 0 at `--frames` or `quit`; 1 when a picture can't be written; 2, before anything ran, for a flag or a script's line that's wrong, or a run nothing ends. Desktop only: a web page is driven and screenshotted in headless Chrome, as the web tests do.
  - `tide_platform_png` (`platform/tests/png.mjs`, every platform, no GPU) reads what the writer wrote with Node's zlib; `tide_platform_capture` (`capture.mjs`, label `gpu`) runs `capture.tide` with a script of every kind of input and reads its pictures' pixels, the match's seed and what it rolled from it among what they show, then runs it again for the same bytes, and with `--seed` for the seed it asked for and other rolls; `tide_platform_capture_refused` checks what a run refuses, with no GPU.
- That nothing an agent runs shows on the owner's screen doesn't rest on the agent remembering: `TIDE_HIDDEN` in the environment, set to anything but nothing or 0, says nobody watches a run (`tide_hidden`, `tide/page.h`), and then no Tide program shows a window or a dialog. Desktop only.
  - Agents' shells have it. Claude Code sessions get it from `.claude/settings.json` (`env`), the one file of `.claude/` that's checked in, so every checkout and worktree has it. A Codex session exports it before anything else it runs: `export TIDE_HIDDEN=1`, or in PowerShell `$env:TIDE_HIDDEN = '1'`. It's never set where it would reach the owner's own runs: not the user's environment, not the editors' run configurations. `tide run`, CTest and the tests' scripts pass the environment on as it is.
  - Two rules stand beside it, as a program built before the variable doesn't know it: an agent runs only programs built in its own checkout (another checkout's `build/` can be older than the flags it's given, and opens a window), and never runs a game without `--capture`, `--frames` or `--script`.
  - A window that isn't `hidden` has only its closing to end its run, which nobody could do, so the program is refused: it ends with exit code 2 before it opens anything, having said what to give it instead (decided over running hidden for a counted number of frames, which would end with 0 as if something had been checked, and as a run with no window that nothing ends is refused already). `tide_platform_open` refuses any such window (`platform/src/platform.c`), the standard host names its flags first (`tide_run_open` in `tide/host.h`), and `tide run` refuses before it builds (`compiler/cli/main.c`); `tide run --web` serves its page and opens no browser. A window that's `hidden`, as every test's is, and a run with no window go as they do without the variable. Under the refusal, `tide_window_open` shows no window whatever asked (`platform/desktop/glfw.c`).
  - A program that stops shows no dialog either. On Windows a debug build's `abort()`, which every stop of the engine's and of generated code ends in, shows one that waits for a click, a failed `assert` shows one in a program with no console, and the system shows its own for a crash or a library that's missing. With the variable they're off before `main` (`hidden_start` in `engine/src/page.c`, a constructor, there because every program of the engine's links that file: programs with no window stop too, and none has to remember it), and tide turns the system's off for what it starts (`sys_hidden`).
  - `tide_platform_hidden` (`platform/tests/hidden.mjs`, with `hidden.c`, no GPU) checks what's refused, by a game and by a host of its own, that a stop ends at once, and that nothing changes without the variable; `tide_platform_hidden_runs` (label `gpu`) that a run with no window draws the same picture with it and without, and that a window asked to show doesn't. `tide_tests_hidden` and `tide_tests_watched` check a program with no window, and `tide_cli_hidden` checks `tide run`. Whoever runs the tests may have the variable, so a test that starts a program says which it's for: set, or taken out of the environment.
- Views are written in Tide (`view` declarations). Their `Draw2D` and `Draw3D` calls record commands into a renderer-agnostic draw list (`tide/draw.h`), which grows as it needs, with no limit but memory. The platform layer renders the list (`tide_platform_draw`), so another backend only means another of that function. Drawing a lot has to stay cheap: shapes (rects, circles, their outlines and lines, and the smooth shapes, below) go to the GPU as instances of one quad, each its shape in window pixels, so a run of them between text and clears is one draw call (`platform/src/platform.c`), and so is a run of text. `tide_platform_draw --bench` (`?bench` on the web) times frames of 65,536 shapes, of as many textured quads of one mesh, and of as many instances of a 3D cube. The stats show in the bottom right corner when the host asks (`tide_run_desc.stats`: `STATS`, `tide run --stats`) or the game's `stats` setting does (`tide_game.stats`), which the host reads every frame (`tide_run_stats` in `tide/host.h`), so a reload brings them or takes them away. They're a drawer (below): one line, which opens to the frame rate, what a frame's work takes on its thread (`cpu`: the frame function up to the drawer, so not the wait for the display), ping, bandwidth (sessions count the bytes of their datagrams over networks, not loopback: `tide_session_status.sent_bytes` and `received_bytes`), tick, entity count, the threads ticks run on (`tide_platform_jobs`), the memory the program has (`tide_platform_memory`, `platform/src/memory.c`: the working set on Windows, what's in RAM on Linux and Android, the footprint on macOS, and on the web the WebAssembly memory's size), what draws and in how many draw calls (`tide_platform_draw_calls`: the steps of the last list that drew, the drawer's aside). It's for a glance, so a number that joins it has to earn its line: the drawer holds 16.
- The stats are a drawer (agreed 2026-10-05: always open, they covered two thirds of a game at the size the docs embed one, and a game can't ask where they are; what's picked is Provisional in `docs/spec.md`, Settings). `tide/stats.h` (`engine/src/stats.c`, in the engine beside the GUI and the profiler, so its tests need no window) is the drawer, and `tide/host.h` drives it:
  - Closed, it's one line, with what's worth a glance: the frame rate, and the ping when another machine runs the match (`tide_stats_values.remote`: this machine's own is the loopback's). Open, the rest is listed above that line, which stays where it is, so a click in the same place closes it again. The list is cut from its end where a screen is too low for it, and a system's name is cut where a line is too wide, never what the system took. It shows outside a match too, with the lines that aren't a match's.
  - A click or a tap on it opens it and closes it (the left button or a finger that went down on it and is let go on it), and so does F8, beside the profiler's F7: the game reads the key too. `tide_run_drawer_input` asks right after `tide_platform_poll`, before anything reads the devices.
  - It starts closed, and `tide run --stats` starts it open (`tide_run_desc.stats_open`, which tide sets for `run` alone: `opts.stats_open` in `compiler/cli/main.c`), since whoever typed that wants to read it. A game's setting, `tide build --stats` and `STATS` are what players get: the one line.
  - Open or closed is the host's (`tide_run_drawer`), never a build's, so a hot reload keeps it: on desktop the host outlives the game's library, and on the web it goes with what a program leaves the next one (`saved.stats_open` in `platform/src/reload.c`).
  - **A press on it is the host's, as the pointer on a widget is the GUI's,** but by where the press began, not where the pointer is now: a button that goes down with the cursor on the drawer, and a finger that touches it, are the drawer's until they're let go, wherever they go meanwhile, and a press that began elsewhere stays the game's when it crosses the drawer (a brush that paints across the corner isn't cut). A mouse whose cursor is locked is on nothing. `tide_stats_hide` takes the drawer's presses out of a copy of the devices: the copy `tide_run_sample` samples the game's input from, after `tide_gui_hide`, and the copy the frame's GUI and views read (`tide_gui_begin` is given it while a press is on the drawer), so neither sees the press, from the frame it lands in. The drawer keeps a press once it's let go while the devices still say it was down (a button's `pressed`, `down` and `up` stay until a sample consumes them, and a finger's slot until then), or the next tick's sample would take it for a click; in a host that never consumes, it's the drawer's until the button goes down elsewhere. The GUI knows nothing of the drawer: a widget under it still shows the pointer on it, and games keep the corner free (the line's rect is about 84 by 40 logical pixels, and up to about 190 wide with a ping).
  - **Nothing is measured that isn't shown.** Closed, the frame rate is frames counted over made-up or real seconds the host has anyway, and the ping is the session's: no clock is read, ticks get no `tide_profile`, and the memory isn't asked for. Open, a frame's work is timed (`began`), the pool gets the profile (`tide_run_debug_views`), and the memory is read: the list's `cpu` line shows once a frame was timed. The numbers that are rates change once a second, and the first time after a quarter of one: the drawer shows from then (`tide_run_stats_known`), never a frame rate of 0.
  - It's drawn into a list of the host's own (`tide_run_over`), over the frame (`tide_platform_draw_over`, as `tide_platform_draw_overlay` draws a host's text: neither counts in the frame's draw calls, nor moves its camera). So a run with no window has it in its pictures, and a script's click or `key f8` opens it as a player's would. Closed, it shows nothing this machine measured, so such a run still repeats byte for byte (a frame is a 60th of a second, so the line says 60); open, it shows this machine's clock, and pictures differ there.
  - Tests: `tests/test_stats.c` has the drawer with made-up numbers and devices, each frame in the host's order (closed and open, the key, a click, a tap, a tap shorter than a frame, a second finger, whose each press is, a game that samples nothing, small screens); `tide_platform_stats` (`platform/tests/stats.mjs` with `stats.tide`, label `gpu`) runs the standard host with no window and reads the drawer and what the game read off its pictures; `tide_platform_web_stats` (`platform/tests/web_stats.c`) does it in a page with the DOM's own events, and checks nothing is measured while it's closed, and that it's open as it was left when the setting goes and comes back.
  - Examples that ask for the stats keep their own things out of that corner by their own numbers: Duel (`examples/duel`, `StatsCorner` in `hud.tide`) has its Menu button in the top right corner on every layout, its touch ring above the line, and its row of keys as far left as the line needs.
- Drawing is `Draw2D` (shapes, text, 2D meshes, the screen's pixels and clipping) and `Draw3D` (3D cameras, meshes, and cube, sphere, cylinder and plane primitives). `Draw` itself only has what the two share: `Blend` and `Tint` (draw settings, below), and `Blit` and `window` (render targets, below). Both clear the same target and hand C the same draw list, and each has a camera of its own. Screen and world conversions (`engine/src/draw_coordinates.c`) go through the frame's current camera, in logical pixels from the top left with y down. Device positions count from the bottom left with y up, as Unity's Input System's do (decided), so views take them through `Screen.Flip(position)` (`tide_draw_screen_flip`: the same point counted from the window's other edge, its own inverse; the name is provisional), never `Screen.height - y` by hand. 3D depth is 0 at the near plane and 1 at the far limit, and picking rays start on the near plane with a normalized direction in the world. The primitives (`engine/src/primitives.c`) are cached unlit meshes, given their full sizes and an optional rotation; a cylinder's axis is its local y, and a plane spans its local xz.
- Draw settings change how everything drawn after them comes out (agreed 2026-10-05; `docs/spec.md`, Draw settings, where the picks beyond what was agreed are Provisional). One family, two forms each, told apart by name: the plain name wraps a block and puts back what it found when the block ends (`Draw.Blend(Blend.Add) { ... }`), and the `Set` name stays for the views that follow, until it's set again or the frame ends (`Draw.SetBlend(Blend.Add);`). A form written as the other is a compile error that names the other, and so are the spellings from before there were two (`Draw2D.Camera(...);`, `Draw2D.Clip(rect);`, `Draw2D.Clip();`, `Draw2D.Screen();`), with the rename as a quick fix. A setting that joins the family (depth, cull, mask) gets both forms and the same rule.
  - The family: `Draw.Blend` and `Draw.Tint`, which are the same wherever a draw goes, and what belongs to a destination, the window's as `Draw2D`'s and `Draw3D`'s and a target's as its methods: `Transform`, `Clip`, `Camera` and `Screen`. Every frame starts from the defaults (`tide_draw_reset`), and the GUI, the profiler and the stats overlay never draw with a game's: `tide_draw_append` and `tide_draw_defaults` start from them, and the overlay's list is its own.
  - In `tide/draw.h`, a `Set` is `tide_draw_set_*` (and `tide_draw_unset_*` with no arguments), and a block `tide_draw_push_*`, which saves what it found on the list's stack and returns a mark, then `tide_draw_pop(list, mark)`, which puts back everything saved since: generated code pops the outermost block's mark where code leaves early (`closing` in `compiler/src/codegen.c`, with the GUI's containers).
  - A setting never comes between draws a renderer would draw at once. A command carries its blend (`tide_draw_command.blend`), a tint and a 2D transform are worked into shapes, text and 2D meshes as they're recorded (`plain_altered`, `alter_shape`, `alter_vertices` in `engine/src/draw.c`), a 3D transform into each instance's, and a 3D mesh's and a shader's tint are their run's. The list has the cameras and clips it was given (`tide_draw_list.cameras`, `clips`, a clip naming the clip it's inside and the camera it was made under), and each destination's `tide_draw_place` says which the commands to come go through and which the commands so far play: the commands that say so (`settle`) are recorded before the next one that draws, and only where the two differ. So a setting set to what it was, or set and put back around nothing, records nothing, and the same block around each entity's draw is still one run.
  - Recording a plain shape is a few stores (`push` is part of each function that records one, and what's rare isn't, nor what a tint or a transform does to a shape or a mesh's corners): a change there is measured, as the renderer's path is (`bench/results/draw.jsonl`, `draw-settings-before` and `draw-settings`).
  - A pipeline is made with how it blends, so the engine's are made once for each way the first time a list draws that way (`engine_pipeline` in `platform/src/platform.c`), and a game shader's too (`pipeline_for`, by `tide_shader.id` and blend). What multiplies needs a color that's gone to white where it's clear: the shaders do that by a uniform (`fix.x`, a game shader's `tide_screen.w`), so no shader has a version of its own for a blend, and the plain shapes' pipeline has none of it: a run of plain shapes that multiplies goes through the smooth shapes' pipeline. A game shader's color is multiplied by `tide_tint` after its frag (`put_fragment_main` in `compiler/src/shader.c`).
  - Text a transform turns, stretches or mirrors can't be fitted to pixels: it's laid out as upright text of the size the transform's mean scale makes it, and each glyph goes through the transform (`add_text_turned`), so it measures as upright text does; its anchor's place goes through the transform and its box is laid out against it, as upright text's is (`add_text`). Moved and scaled as much each way, it's fitted text of that size.
  - `tide_platform_draw` checks each blend, tint and transform's pixels for every kind of thing that draws, clips in clips, and that a blend, a clip, a tint and a transform around each of 200 draws are still one draw call, on OpenGL, WebGL 2 and WebGPU; `tests/test_draw_settings.c` checks the list without a GPU, and `compiler/tests/e2e/draw_settings` what blocks, lists of them and early exits generate.
- Calls that take a block can be listed with commas before one block (agreed 2026-10-05; `docs/spec.md`, Calls that take a block): draw settings, the GUI's containers and a game's functions with an `Action`, each beside the others. The parser makes each call's block the call after it (`expr.stacked`), so it means what nesting them does, and the rest of the compiler sees nested calls. A call in the list that takes no block is an error at that call. The formatter puts a call a line (`stacks_calls` in `compiler/lsp/analysis.c`).
- Smooth shapes are primitives, drawn by the engine's own shaders: they take no `frag` or `vert` (agreed: not every draw function takes a shader). `Draw2D.RoundRect`, `Ellipse`, `Arc`, their outlines, the thick `Line`, `WireRect` and `WireCircle`, the turned `Rect`, and `Draw2D.Shape(shape)`, the general one the others but `Arc` are short for: a built-in `Shape` struct's box or ellipse, turned, with a fill from `color` at its top to `color2` at its bottom (`Color.none`, its default: one color), an outline inside its edge, and an edge that fades outwards (`soft` above 0) or inwards (under 0). See `docs/spec.md`, Views and drawing, and `docs/game/views.md`, Smooth shapes.
  - `Rect`, `WireRect` and the `Line` with no width stay as they were, filling whole pixels, so rects side by side leave no seam (`tiles_leave_no_gaps` in `platform/tests/draw.c`). Only the smooth shapes are drawn by distance.
  - Angles are in radians from +x towards +y in the units the call is in (counterclockwise under a camera, clockwise on the screen), and a fill's first color is at the shape's top as the screen has it, in both. Outlines are inside the edge. `Arc`'s ends are cut straight across, so a width of the radius is a slice of a disc.
  - The list keeps one as a `TIDE_DRAW_SHAPE` command: its center, size and fill in the command, like a rect's, and the rest in `tide_draw_list.shapes` (`tide_draw_shape_data`: its rotation as cos and sin, its corners' radius, its outline, how far it fades, its form). The functions of `tide/draw.h` (`tide_draw_round_rect`, `tide_draw_thick_line`...) fill those themselves; `tide_draw_shape` takes a `tide_shape`, which generated C makes of Tide's `Shape` in a helper (`tide_draw_shape_value`), as the two are different C types.
  - The platform has two pipelines of shapes (`platform/src/platform.c`, `platform/src/shaders.h`). A run of the plain kinds alone goes to the GPU as it always did, an instance of 24 bytes each. A run with a smooth shape in it goes through the pipeline that draws every kind, each shape with a `shape_extra` (32 bytes) in a buffer of its own, so it's still one draw call whatever kinds it mixes. Both pipelines draw the plain kinds from the same shader lines, so a rect is the same pixels in either. The plain pipeline's shaders are, byte for byte, what they were before there were smooth shapes, and a plain shape is added to its run by the code that always added it (a mixed run's plain shapes get their extras when the run ends, `settle_extras`), so a frame of plain shapes costs what it did: a change to that path is measured against `bench/results/draw.jsonl` (`smooth-shapes`). A plain circle's edge is smooth over a logical pixel, which would be soft on a scaled display, so there the renderer draws circles as the smooth shapes they also are (`add_circle`).
  - A pixel is in a smooth shape by how far it is from the edge, in the shape's own frame: a box's distance is exact; an ellipse's is found (three steps towards the nearest point of the edge, then two of Newton's, which 32-bit floats need for flat ellipses), so its outline is as wide all the way round; part of a ring is a ring and the wedge it's cut to. Edges are smooth over one pixel of the target, which the shaders know from `scale` (the platform's `pixel_scale`), and colors blend with their alpha in them, so a fill to a clear color fades and doesn't darken.
  - `tide_platform_draw` checks every kind's pixels, edge by edge, on each backend, and that a run of every kind is one draw call. `tide_platform_draw --bench` has workloads of smooth shapes too, and `--dump <file.ppm>` writes the smooth shapes' scene as an image, to look at.
- Meshes are the general primitive (`Draw2D.Mesh`, `tide_draw_mesh`): triangles with a position, a uv and a color at each corner, indexed, which the list keeps (`vertices`, `indices`) and draws in order with its other commands. The platform expands each run of them with one texture and filter into triangles in window pixels, a draw call. A clip (`Draw2D.Clip`, `Draw2D.SetClip`) is a scissor, its rect in the units the commands are in, which clears honor and the GUI never draws through; the screen (`Draw2D.Screen`, `Draw2D.SetScreen`: `TIDE_DRAW_SCREEN`) is the GUI's pixels, for views. The shapes' instanced path stays as it is.
- 3D is meshes too, kept bare so that games and libraries scale it up: `Vertex3` (`tide_vertex3`: a position, a uv and a color), drawn by `Draw3D.Mesh(vertices, indices, transform)` (`tide_draw_mesh_3d`) through a camera of their own, `Draw3D.SetCamera(position, rotation, fieldOfView)` or any `transform` and `projection`. No lighting is built in: normals and what a pixel does with them are a vertex struct and a `frag` of the game's.
- Manual instancing is `Draw2D.Instanced` and `Draw3D.Instanced` (`(vertices, indices, instances[, texture[, filter]][, vert][, frag])`): one mesh for each list item, without entities. In 3D, a `List<float4x4>` supplies transforms, or an ordinary struct's optional `float4x4 transform` does (identity without it). A shader's read-only ordinary struct parameter receives the list item; other components still come from the view's entity and singletons are shared. In 2D a vert places each item, and the engine applies no instance transform. Only read fields are sent, beside a 3D transform; an empty list draws nothing, and each compatible run is one GPU draw. See `docs/game/shaders.md`, Instances from a list.
- A game's code runs on the GPU as `frag` (once for each pixel) and `vert` (once for each vertex), declarations like views, which a `Draw2D.Mesh` or `Draw3D.Mesh` names after its other arguments, for 2D and 3D meshes of any vertex struct with a `position` (`docs/spec.md`, Views and drawing; `docs/game/shaders.md`). Their signature says what they read and the engine supplies it: the vertex first, a frag's pixel as `mut Color`, components of the entity the calling view runs for, singletons, and the built-in `Pixel` and `Instance`. Manual instancing can also supply one read-only ordinary struct from its list, and a draw one read-only `Texture`, its explicit source. No individual plain value parameters, no return value (decided: ECS style).
  - `compiler/src/shader.c` writes the shaders: for each combination a draw uses (a vertex struct, with a vert, a frag, both or neither), GLSL for both stages and WGSL, in `plan_shaders`, which the checker calls once code is checked. `tidec --shaders` (`tide shaders`) prints them, and `compiler/tests/shaders/` pins what it writes.
  - The code that writes a shader is the code that checks it: a first pass (`emit.checking`) goes through each frag and vert and the functions they reach, writes nothing, and reports what a GPU can't run (`refuse`), with which frag reaches a function's code. What's written afterwards always compiles, with no warning: nobody sees a shader compiler's error. So every name of the game's gets a prefix no keyword has (`name_of`); conversions are written out; a `mut` parameter is `inout` in GLSL and a pointer in WGSL, whose argument is a whole variable or goes through a copy; WGSL's swizzles are assigned a component at a time; code after a `return` is dropped; and constants a shader compiler would fold into an error (WGSL's are: a division by zero, a function's argument out of its range) go through `tide_f` and `tide_i`. A number with a minus before it is written as that number. A loop's own line has only numbers and variables (`st_for`): what it starts at, and what it goes to and steps by when those are constants, are worked out before the loop when they're anything more, as compilers read how far a loop goes off that line, and the Android emulator's loses a function that only that line calls when the loop samples a texture (it stopped a blur's `for (var x = -1; ...)` from compiling there). Textures are sampled at their one level (`textureLod`, `textureSampleLevel`), so sampling is allowed in any branch and in a vert.
  - Everything in `Math` is on the GPU unless it makes no sense there (decided), with the math types and what builds them (`quaternion.AxisAngle`, `float4x4.TRS` and the rest): a function `Math` gains gets its GPU side with it, or an error in `ex_math` that says why not and what to write instead. One is left out: `Math.Hash` of a `long`, as these GPUs have no 64-bit integers (`Math.Hash(int2(low, high))` of its halves is the same number). What a shader language has no function for, or has one that does otherwise than `tide/math.h`'s, is a function of the engine's own in the shader (`helper_text` and `need` in `compiler/src/shader.c`): math.h's formula, in its order, written once in the GLSL both languages can say, which `put_helper` turns into WGSL, so a change is one change.
    - `Math.Hash` is the CPU's number exactly: unsigned integers, which wrap the same in every language.
    - Floats are the CPU's formula with the GPU's rounding, which differs between GPUs; the docs say so, and that warning stays accurate.
    - What's forgiving on the CPU is forgiving there: `Normalize`'s zero and identity, and `Min`, `Max`, `Clamp` and `Saturate` with NaN, which they tell by its bits (`tide_nan`), since a shader compiler may reckon without NaN and fold `x != x` away.
    - Where the CPU gives a number, the GPU does, though the languages' own functions leave it open: `Pow` of a number under 0 to a whole power and of anything to the power 0, `Atan2(0, 0)`, `SmoothStep` with its edges the wrong way around, a matrix's `Inverse`.
    - `tide_platform_shaders` runs each on the CPU and on the GPU, in a frag and in a vert, and compares (`Probe` in `platform/tests/shaders.tide`): the same number for integers, and floats within a tolerance. `compiler/tests/shaders/math` pins the functions' text in both languages.
  - What the code reads is what's sent (`param.reads`): a component's fields with each instance and a singleton's once for the draw, as words of float4s and int4s (`shader_value`), laid out the same in both languages: the instance's are vertex attributes after the vertex's own (a 3D mesh's transform first), and the draw's follow the engine's own (`tide_camera`, `tide_screen`) in one uniform block. What a frag reads of the instance, the vertex stage passes on, flat. A `local` field of a match component or singleton is read like any other (`param.local_reads`): its draws are handed the local part too (`shader_reads_local`).
  - Generated C has a `tide_shader` (`tide/draw.h`) for each, its sources as arrays of chars (C promises string literals of 4095 only), and a `tide_shade_<n>` that fills an instance and the uniforms from the view's components and singletons and calls `tide_draw_mesh_shaded` (`tide/mesh.h`). A view is handed what its frags and verts read that it doesn't take itself, as parameters codegen adds (`bind_views`), so they're gathered and blended like its own.
  - The draw list keeps such a mesh as its list's bytes (`TIDE_MESH_BYTES`, `tide_draw_mesh_fill_bytes`), and a run of instances through a shader as one `TIDE_DRAW_SHADED` command (`tide_draw_run`: its instances' bytes, its uniforms, its textures): instances drawn in a row with the same shader, uniforms and textures are one, which the platform draws in one instanced call. A 2D shader's `tide_camera` is the 2D camera's or the screen's, so its meshes land where the other 2D commands do, in order with them.
  - The platform makes a pipeline for a shader the first time it's drawn and finds it again by `tide_shader.id`, a hash of its sources, so a hot reload keeps the pipelines of shaders that didn't change: after `tide_draw_forget` it frees the ones the next frame doesn't draw. A lost device takes them all, and they're made again as lists draw.
  - `tide_platform_shaders` (`platform/tests/shaders.tide`, `shaders.c`) draws through frags and verts written in Tide and checks their pixels, the same on OpenGL 3.3 (label `gpu`), WebGL 2 and WebGPU, where the device is then lost and found again. It's also what makes every backend compile what tidec writes: a test page fails on a shader's warning (`Tide.checkGL`).
  - The list keeps a camera as one matrix from the world to clip space (`TIDE_DRAW_CAMERA_3D`); the platform fits the perspective one to the screen's shape. 3D meshes are the only commands that test and write depth: everything else draws over what's there, in order, through its own camera, and a clear clears depth.
  - The list keeps 3D meshes as it keeps textures, by whose they are and a version (`tide_draw_mesh_slot`): a Tide list's from the hashes its heap keeps of its pages, C's from `tide_mesh.version`, and lists made along the way by what's in them, wherever they are in the scratch area. A mesh keeps its place in `meshes` while frames draw it, found through a hash table, and another version takes another place, so a mesh is never changed under a command that drew it. The platform keeps its GPU copy in the same place (`mesh_for` in `platform/src/platform.c`): its corners, each once, and its triangles as indices into them, of 16 bits where they fit.
  - Instances of one mesh drawn in a row are one command (`TIDE_DRAW_MESH_3D`, its transforms in the list's `matrices`), which the platform draws in one instanced call. So a view that runs for each entity draws thousands of them at once, and static scenery costs a hash per page a frame.
- Nothing but a render target (below) holds a GPU texture: a mesh names pixels where the game keeps them, and every layer keeps a copy it can make again.
  - The draw list copies a texture's pixels when they aren't what it has (`tide_draw_texture_slot`: whose they are, and a version), and the platform uploads from that copy (`texture_for` in `platform/src/platform.c`). Each lets a texture go once a frame draws without it.
  - Tide's textures are grids, `Grid2<Color>` (`tide/mesh.h`), local or the match's. Their version is a hash of their chunks' page hashes, which a heap keeps until a page changes (`tide_heap_block_hash`), so an unchanged grid costs a hash per chunk, not its cells. Asking counts as a move of the heap, so a chunk cache that held the page looks it up again and says it changed.
  - C's are `tide_texture`: its own pixels, and a version it changes when they do.
  - So reloads carry nothing. On the web a new program uploads again. On desktop the host has the list forget its copies when it swaps the game's code (`tide_draw_forget`, whose epoch the platform checks), as the new build's C may name other pixels at the same address and version.
- Render targets are the exception: images the GPU alone holds, local to a machine. `RenderTarget(width, height)` makes one, `target.Resize(width, height)` changes its size and discards what's in it, `target.color` is its `Texture`, and `target.Dispose()` lets it go, explicitly. Copies share the image, and its color and depth stay from frame to frame until they're cleared. A target's own drawing methods (`target.Clear`, `target.Mesh` and the rest) draw into it; `Draw2D`, `Draw3D`, the GUI and the stats overlay draw into `Draw.window`. `Draw.Blit(source, destination[, blend], frag)` runs a frag over the whole destination, replacing its color (or going over it as its own `blend` says) and keeping its depth whatever the camera, the clip and the other draw settings are, with the source as the frag's read-only `Texture` parameter: a target's color or a `Grid2<Color>`, never the destination's own, which is an error. Tide code can't read a target's pixels back, so a hot reload and a lost device make its image again, empty. `tide_platform_targets` (`platform/tests/targets.c`) checks targets on each backend, at `gpu.h`.
- A target's size is in logical pixels, like the window's, at the display's scale (agreed 2026-10-05; `docs/spec.md`, Views and drawing): drawing into one is the same as drawing into the window. `RenderTarget(width, height, pixelsPerUnit)` has pixels per unit of its own (`RenderTarget(320, 180, 1)` is exactly those pixels on any display), and `RenderTarget.Screen()` and `RenderTarget.Screen(factor)` are always the window's size, or that part of it: made again, empty, when the window's size or the display's scale changes, and never resized by the game. Nothing reads the display's scale (no `Screen.scale`). What the design left open is picked and Provisional there: sizes are floats, an image has the nearest whole number of pixels, `Resize` on a target that follows the window is a diagnostic, and an image past the GPU's largest texture keeps its shape with fewer pixels.
  - A size is a `tide_target_size` (`tide/draw.h`): a width and a height in logical pixels, `scale` (the image's pixels in one, 0 for the display's) and `window` (above 0: the part of the window's size it always is). A `tide_render_target` is an id and one, a managed target's state has one, and the draw list records one with each destination and each target it samples (`tide_draw_target_data.size`, `tide_draw_texture.target`), so a list says nothing in pixels. The engine only knows logical sizes: `tide_target_size_logical` is what the conversions and `MeasureText` use, with the window's size for a target that follows it.
  - The platform works a target's pixels out as a list is drawn (`target_extent` in `platform/src/platform.c`), under the draw's root (`draw_root`): what the list's window commands go to, with a size in logical pixels and one in its own. The root's pixels over its logical size are the display's scale for that draw: the window's, a headless run's `--scale`, or 1 for `tide_platform_read_pixels`. A target that follows the window has the root's own pixels times its factor, so `RenderTarget.Screen()` is the window's pixels exactly. A destination's logical size and pixels are then all the renderer goes by (`draw_width`, `draw_pixel_width`, `pixel_scale`), the window's or a target's alike: text fitting, circles drawn as smooth shapes where the scale isn't 1, clips, and a shader's `tide_screen`.
  - The GPU's copy of a target is made again when its image comes to another number of pixels, as when its version changes (`target_for`, and `prepare_source_target` for one that's only sampled): that's all that happens when the window is resized or moves to another display. `tide_gpu.target_limit` is the most pixels a side an image has (OpenGL's smaller of its texture and renderbuffer limits, WebGPU's `maxTextureDimension2D`).
  - Text is measured where it's drawn: `tide_measure_fn` takes the target's `tide_target_size`, or NULL for the window, and `tide_platform_measure_text` works its pixels out as drawing does.
  - `tide_platform_read_pixels_as(list, width, height, scale, ...)` draws a list as a window of that size would on a display of that scale, and reads its pixels: how tests see a scaled display and a window that changes size on any machine and every backend, with no window resized. `tide_platform_targets` draws a pattern one real pixel wide into a screen target at scales from 1 to 3 and expects it back pixel for pixel, checks that a scene drawn into a screen target is the window's pixels (text, circles and smooth shapes), that a target with pixels of its own keeps them and its contents on any display, and that the others are made again when the scale or the window's size changes; `tide_platform_shaders` does it from Tide (`RenderTarget.Screen`, `RenderTarget(4, 4, 1)`, a frag's `pixel.position`).
  - Hot reload keeps a target's size, its scale and whether it follows the window: they're in the `tide_render_target` values the local state holds, which `tide_render_target_recreate` makes a web build's targets from.
- A game's C draws through the view's list: an extern function takes a `DrawList` (`tide_draw_list *`), which only `Draw2D.list` and `Draw3D.list` are (the same list), in views and the functions they call. C calls `tide/draw.h` itself (`tide_draw_vertices` and `tide_draw_triangles` for vertices several batches share), so libraries that hand over triangles (Dear ImGui, Nuklear, Spine) need no copy through Tide lists.
- The GUI (`GUI` and `GUILayout` in Tide, `tide/gui.h` in C) is immediate mode, like drawing, and local: widgets change local state, never the match. It records into a list of its own, which `tide_gui_end` adds after the world's, in pixels (from the top left, y down), so widgets keep their size when the window changes. It measures text with the platform's font (`tide_platform_measure_text`). Views read the devices through a `Devices devices` parameter: `tide_gui_begin` works out what changed since last frame and hides what the GUI uses.
- A host samples the game's input before the frame's GUI runs, and views read the devices before its widgets do, so what the GUI hides can't wait for the GUI to see a press. Whether the pointer is the GUI's is where it is now against where the last frame drew its widgets and areas (`on_gui` in `engine/src/gui.c`, which `tide_gui_hide` and `tide_gui_begin` both ask), never where the GUI last saw it: a finger that touches a button is hidden from the sample of the frame it lands in. A widget that first appears under the pointer takes it a frame later. Tests of hiding go in the host's order, sample then frame (`finger_sample`, `mouse_sample` in `tests/test_gui.c`).
- A view's own widgets are controls (agreed: the GUI stays bare, and games bring their own controls). `GUI.Control(rect)` (`tide_gui_control`) is a widget the view draws itself: the GUI handles its input as a button's and draws nothing, so showing hover and focus is the view's.
  - It's a button's code without the drawing (`clicked` in `engine/src/gui.c`): its rect is one of the places a frame remembers, so a press on it is the GUI's from the sample it lands in (`on_gui`), it's in the focus's order with the other widgets, and a Disabled block or a modal over it stops it.
  - It gives a `tide_control` (`hovered`, `pressed`, `focused`, `clicked`), which generated C makes Tide's `GUIControl` of in a helper (`tide_gui_control_value`), as the two are different C types. `pressed` is the pointer holding it, wherever it goes meanwhile, as a `Devices` button's `pressed` is held.
  - While a control has the focus, the view that called it goes on reading the keyboard and the gamepad, less what moves the focus and clicks (`focus_view`, `hide_navigation`, `tide_gui_view`): the game and the other views read neither, as with any focus. So a menu's own shortcuts work with one of its controls focused.
  - Controls a loop makes come from one call, and are told apart as the GUI's own widgets in a loop are, by their turn (`tide_gui_id` counts the calls from a site in a frame): one left out gives its turn to the next.
  - `GUILayout` has no control: what a view draws is under the GUI's own widgets, a panel included, and under a modal's dim, since the GUI draws last. That's documented, and stays.
- The focus moves in the order widgets are called: down and right go on, up and left go back (`navigate`). A widget that steps its value with left and right keeps those (`focusable`'s `steps`: sliders and number fields), and the press that brought the focus to one doesn't step it too. The arrows, the d-pad and the left stick only start the focus while the game isn't reading the devices, or while a view says a menu is up, frame by frame (`GUI.Navigate()`, `tide_gui_navigate`), as a menu over a running match needs: a HUD's button never takes the d-pad.
- The GUI's own widgets have one look, and a simple theme for it (agreed: no styles for single widgets, no text sizes, no fonts). `tide_gui_theme`, Tide's `GUITheme`, is the colors the widgets use and their corners' radius, and nothing else.
  - Its defaults are the look the widgets always had, in two places: `tide_gui_theme_default` in `gui.c`, and the built-in struct's fields in `add_builtins` (`compiler/src/check.c`). A change to one goes to the other, and `gui_set_themes_hold_for_the_views_after` (`compiler/tests/e2e/gui_test.c`) checks they agree.
  - It follows the rule for a frame's settings: the plain name wraps a block and puts back what it found (`GUI.Theme(theme) { }`, `tide_gui_begin_theme`: a block that lays out nothing, like a Disabled one, `open_scope`), the `Set` name stays for the views that follow until it's set again or the frame ends (`GUI.SetTheme`), and every frame starts from the defaults (`tide_gui_begin`). Each form's misuse names the other (`check_gui_call` and `check_stmt` in `compiler/src/check.c`).
  - With a radius of 0 a part is the plain rect it always was (`paint`), so a game with no theme draws the commands it did. With one it's `Draw2D`'s round rect, and an area's panel, a shape then, is sized when its area closes like the plain one (`panel`, `close_area`).
  - The stats' drawer and the profiler's panel draw into lists of their own, never through the GUI, so they keep their look (`profiler_keeps_its_look_whatever_the_guis_theme` in `tests/test_profile.c`).
- A view with widgets that read the devices themselves, like a C library's, claims what they use, with the effect the GUI's own use has: `GUI.ClaimPointer()` and `GUI.ClaimKeyboard()` (`tide_gui_claim_pointer`, `tide_gui_claim_keyboard`). A claim lasts a frame and is made again each frame: it stands from the end of its frame to the end of the next, hiding the device from the samples taken meanwhile (`tide_gui_hide`) and from the other views, while the view that claimed it goes on reading it. So generated code says which view runs (`tide_gui_view`, before each), and `tide_gui.devices` is that view's. `GUI.ClaimPointer(rect)` (`tide_gui_claim_pointer_at`) says where a view's widget is each frame, and the pointer on it is the view's by where it is now, as on the GUI's own widgets: a claim with no rect can only hide a frame late, which a finger's first touch gets past. The GUI's own use comes first: no view reads what the GUI is using. `GUI.ShowKeyboard()` is apart from the keyboard's claim, as a widget's shortcuts don't want a phone's keyboard up. What's typed (`devices.keyboard.text`, `tide_keyboard.text`) is a frame's: views read it, and it's never in a sample or the input.

## Tech stack

- Local files are `File`, `Directory`, `Path`, and the read-only runtime properties `Application.persistentDataPath` and `Application.temporaryCachePath` (`docs/game/files.md`). File contents are UTF-8 text or `List<byte>`; `byte` is an unsigned 8-bit scalar. File/directory operations, application paths and `await Storage.Flush()` are local only, including functions that reach them; their results reach the match through input. `Path` is pure. Whole-file operations fail with `IOError`, except `Exists`, which is a bool. Directory results are sorted full paths, with recursion off by default; directory creation creates parents, writes do not, and recursive deletion is explicit. Relative paths use the persistent root. Save identity is the stable `appId`, never the window title. Native files use the OS; browser files are an in-memory filesystem loaded from IndexedDB before startup, with automatic background commits and an awaitable flush that confirms preceding changes committed. The page keeps its files and commits across hot reload. Storage failures are reported, and failed commits retain dirty data for retry; temporary storage stays usable when persistence is unavailable. Open file handles and streams are outside this first API.

- The engine is written in C and compiled with clang on every platform.
- The custom language transpiles to C.
- User code and engine code are compiled and optimized together, so calls between them cost nothing.

## Building

Requires CMake 3.25+, Ninja, and clang. The build finds clang automatically, checking `$LLVM_ROOT/bin`, then a standalone LLVM install, then `PATH`, then Visual Studio's bundled clang. This works with any CMake invocation, not just the presets.

- Configure, build and test in one step: `cmake --workflow --preset debug`
- Build only: `cmake --build --preset debug`
- Run tests: `ctest --preset debug`, or run `build/debug/bin/tide_tests [name-filter]` directly
- Run the sandbox: `build/debug/bin/sandbox`
- Run the demo: `build/debug/bin/demo`, or open `build/web-release/bin/demo.html` in a browser after a web build. Two players: `demo --host` in one window and `demo --connect 127.0.0.1` in another (or another machine's address).
- Run a benchmark: `build/release/bin/bench_sand` (see Benchmarks).

There are two presets for everyday work. `debug` has no optimization. `release` is optimized and keeps debug info for profiling. Web, MinGW and Android builds and the package have their own (see below). `sanitize` is the whole build under AddressSanitizer and UndefinedBehaviorSanitizer, on Linux and macOS (see Language: no Tide code can corrupt memory).

Warnings are errors, wherever they come from, and one that's already there gets fixed, never left alone:

- The compiler's: our C builds with `-Werror` (`cmake/TideFlags.cmake`). Third-party code (GLFW, stb_truetype, LLVM's headers) is built with its warnings off.
- tidec's, in the games `tide_add_game` builds (`cmake/run_tidec.cmake`). A test of what tidec generates for a program it warns about lists those warnings after `WARNINGS`, and the build checks they're there.
- The browser's, in web tests: test pages set `Tide.checkGL`, so a GL error stops the program and names the call (`platform/web/tide.js`), where WebGL would only warn in the console. It checks every call, which is too slow for pages that ship. WebGPU's errors (a shader that's wrong, a call it refuses) stop a test page the same way; pages that ship print them.

Every native build also copies the language server to `build/tools/tidels`, the fixed path editors run: the VS Code extension and the JetBrains plugin use it when the open folder is this repo and the editor trusts it (see `tools/`). On Windows, a build replaces the server while an editor still runs the old one: the running file is renamed aside and deleted by a later build.

A desktop build's first configure downloads GLFW, pinned (see `cmake/GLFW.cmake`); on Linux it builds for X11, whose development headers it needs (libx11, libxrandr, libxinerama, libxcursor, libxi), and loads X11 and OpenGL at run time, so games link neither. Web and Android builds download nothing for the platform layer. Configure with `-DTIDE_PLATFORM=OFF` to build without the platform layer and what needs it (the demo, the sandbox and the benchmarks), for example offline.

Node runs many of the tests (`cmake/run_wasi.mjs`, the relay's, the build service's, the scripts under `platform/tests/`), and on Windows it has to be 24.16 or newer. Before that, and in every 22 so far, a process that starts a TCP connection ends, about one launch in 500, with exit code 3221226505 (0xC0000409) and nothing on stderr, however idle the machine is:

- It's libuv's (`uv__is_fast_loopback_fail_supported` in its `src/win/tcp.c`, which `uv_tcp_connect` goes through; fixed by libuv's #5107, in its 1.53, which Node carries from 24.16): it hands `RtlGetVersion` a struct whose size it never set, right under the function's stack cookie. Where the bytes left there say 284, the size of the longer struct, Windows writes 8 bytes more, over the cookie, and the function stops the process as it returns. In a test file's process those bytes are half of a heap's address, which is 284 once in about 500 launches.
- `node --test` then reports the file as failed with no test named, its process gone before its first test ran; `--test-reporter=tap` shows the exit code. It's never the test's: nothing is loosened or run again for it. The Node is replaced.
- CI's Build workflow installs Node 24 on every platform (`actions/setup-node`), as the docs' does: the runners' own is 22.
- A crash of Node's own is found by running the process under lldb, which leaves its streams pipes (`lldb -b -o run -k "thread backtrace all" -k quit -- node <file>`, with `NODE_TEST_CONTEXT=child-v8` in the environment for a test file as `node --test` runs it), and `llvm-objdump -d` reads a frame of `node.exe` without its symbols.

### Testing and merging

Tests are for finding what a change broke, not a ritual before every push. With several sessions working at once, `dev` moves while suites run, and running everything again after each merge takes hours for nothing (agreed).

- A change is tested on this machine once, before it's merged, with what it can reach:
  - The compiler, the engine, the platform layer or the build: the native suite (`ctest --preset debug`) and the web suite (`ctest --preset web-debug`). Everything depends on them.
  - A game of the repo (`examples/`, `demo/`, `sandbox/`, a benchmark's): its own targets and tests, native and web.
  - `docs/` alone: the site's build (`npm run build` in `docs/`). `relay/` alone: `node --test relay/relay.test.mjs`. `builds/` alone: `node --test builds/builds.test.mjs`, and when the builder or what it runs changed, `builds/page.test.mjs` with a tide that builds web games (see Modding). `tools/` alone: that tool's tests. A text file nothing builds, like this one: nothing.
- Android isn't tested on this machine. Its tests need the emulator, and they're CI's job, as Linux, macOS and MinGW are: nobody boots the emulator to merge. The exception is work on Android itself, when the owner asks for it.
- Merging is: fetch, merge `origin/dev` into the branch, push `HEAD:dev`. What's tested again after that merge depends on what came in (`git diff --stat ORIG_HEAD HEAD`), and it's never "everything again" by default:
  - It merged cleanly and touches nothing the change touches or leans on: nothing is run again. Push.
  - It changed something the change is built on (a header it includes, tidec under a game, a function it calls): build what the change touches, run its own tests, push.
  - It touches the same files or the same subsystem, or there were conflicts: run the tests for that overlap (`ctest --preset debug -R <pattern>`, or a label), on native or the web as the overlap calls for. Both suites whole only when the overlap is that wide.
  - One round. When `dev` moved again meanwhile and what came in is unrelated again, merge and push; don't start over.
- CI is the net under this. Every push to `dev` runs every platform (see Packaging and releases), a failure there publishes nothing, and that's where it's reported. A session that pushed looks at its push's run when it has finished (`gh run list --branch dev`), and whoever's change broke `dev` fixes it there first, ahead of anything else.

### Web builds

- The `web-debug` and `web-release` presets build everything as WebAssembly with clang's own wasm target and wasi-libc, not Emscripten: `cmake --workflow --preset web-debug` (see `cmake/wasi-toolchain.cmake`). They need clang with `wasm-ld` (LLVM's releases have it; on Linux, the distribution's `lld`) and Node. wasi-sdk's C library is downloaded once into `build/wasi-sdk-<version>`, pinned.
- Tests run under Node's WASI through CTest (`cmake/run_wasi.mjs`), so the determinism hashes cover exactly what ships. Games generate their C with a native tidec, which web builds build first in `<build>/host` (`cmake/HostTidec.cmake`), with the same `TIDE_VERSION`, which `#if TIDE_0_3_OR_NEWER` reads (`compiler/src/version.c`).
- In the browser, `platform/web/tide.js` runs the program: the canvas, input and frame loop (`platform/web/tide_web.h`), what the renderer draws with (WebGPU, or the OpenGL ES 3 functions of `platform/src/gl.h` on WebGL 2: see Rendering and platform), and the few WASI functions wasi-libc needs. The platform layer's window there is the page's canvas (`platform/web/canvas.c`). A web page is one self-contained `.html` with the program inside (`cmake/web_page.mjs`, or tide).
- A page's address says a few of the things a command line does (`tide.js`, where it makes the program's arguments): `debug-views` is `--debug-views`, and `host` and `join=<code>` are `--host` and `--join <code>`, unless the page's own `Tide.arguments` say which match; so a link can be an invitation, and a page that shows games in frames can put them in one match (the docs' examples do: see Docs site). For such a page, `Tide.room` is the code of the room the program hosts or joined, `""` for none, read as it is at that moment. `Tide.lag`, or `lag=<ms>` in the address, is the round trip to its match's server the page's player is to have (2 seconds at most), which the page can change as the game runs: latency to look at with both players at one desk, since nothing else gives a page any. These three are Provisional: picks of the docs' examples' that the owner hasn't confirmed, but for what a lag means (below).
  - A lag is a ping (agreed 2026-10-05): the session's, the network's whole round trip to the match's server (see Networking), with what the network takes already in it. A lag of 100 reads as a ping of 100: not 100 each way, and not 100 more than the player had.
  - So the page has to know the ping. The session measures it, and a host says it every frame: `tide_platform_room_ping(ping_ms, answer_ms)` (`platform/src/rooms.c`; nothing on desktop), which `tide/host.h` calls with its client's `ping_ms` and `answer_ms`, the ping -1 (none) for a machine that runs the server and for one not in the match yet: the round trips of joining aren't like a match's. A host that never says gets the lag on top of its ping.
  - The page adds what's missing (`added` in `tide.js`: the lag less `rest`, what the ping is with nothing added), half to what it sends and half to what it receives, so each way is late by as much. What it holds back arrives, to the program, when it's let go: the datagram's arrival, which the ping is measured to (`room_arrived`), is noted then.
  - A ping less what's added is what it is by itself only if all of its trip went under what's added now, so only trips that set out after that last changed count (`room_ping`: `answer_ms` ago, which is by the program's frames, a frame's work behind the page's clock, so not within 50 ms of the change), and never one said again with nothing heard since. The page's timers fire a little late, so `rest` is what's left on the whole (a moving mean).
  - A page that hosts adds nothing (a pick): its machine runs the server, so it has no trip, and each player who joined says its own. Every page of a match can then be told the same lag, whoever hosts, after a host migration too.
  - `Tide.minLag` is the least a lag can make the ping, for the page around the game (the owner asked for the least to be shown, 2026-10-05; the name is a pick): the pings while the page added nothing (`least`: their mean, of the last 32 or so, as it's there to be read), `undefined` until 8 were measured so and on a page that hosts. So a page that wants it starts with no lag. With both players in one page it's next to nothing (measured: 0.6 ms), as a ping is.
  - `tide_platform_web_lag` (`platform/tests/web_lag.c`) checks it in the web tests' virtual time, the page standing in for the relay and for WebRTC with an other end that sends back what it's sent, and the program measuring as a session does, by the room's clock: that a ping is the network's time and an answer takes a frame longer, then a lag untold and told, changed, on a network that got slower, shorter than the ping (where the least lag is known), and on a page that hosts.
- Two more are for a game shown in a frame of a page that scrolls, and Provisional the same way (the owner asked for what they do, 2026-10-05: demos that come up at once, and a page that scrolls over them, on a phone too; the names and the rules are picks):
  - `Tide.wait`, or `wait` in the address: the program loads (its bytes, its compile, its GPU device, its files) and starts when the page calls `Tide.start()`, so a page loads a game before it shows it. `Tide.start()` gives a promise of the program's first frame, with `wait` or without, which a program that stopped before one breaks: that's when the canvas has something to show.
  - `Tide.embedded`, or `embedded` in the address, which the page can change as the game runs: the page keeps its scrolling. The wheel is the page's, always (no game reads it yet; one that does needs a rule for when it's the game's). A finger that swipes up or down on the canvas scrolls the page (`touch-action: pan-y pinch-zoom`, and its touch events keep their defaults) until the player taps the game: from then every touch is the game's as it lands, as without `embedded`, until the frame loses the focus (a press on the page elsewhere). Before that tap the browser may still take a finger to scroll with, which it says with a pointercancel, so the program hears of a finger once it lifted, all at once, a tap, and never of one the page scrolled with: a swipe down a page presses no game it starts on. Nothing about it is timed.
  - `#download` after the address: the page is only being downloaded, and nothing in it runs (`tide.js` returns at its first line). It's how a page has the browser download a game before a frame shows it: browsers keep a frame's page apart in their cache from what a script fetches or a link prefetches (measured in Chrome: after `fetch()` or `<link rel="prefetch">` of the same address, the frame downloaded all of it again), so only a frame's load puts it where a frame finds it, and a frame that may run no script (`sandbox`) logs an error for each script it didn't run. It's after the `#` because that's no part of the address a cache goes by, where one more word in the query would make it another page.
  - The program's bytes load while the page waits to hear about its GPU (`Uint8Array.fromBase64` where the browser has it), and it starts once both are there. The canvas takes the focus without scrolling the page around it (`preventScroll`).
  - `tide_platform_web_embedded` (`platform/tests/web_embedded.c`, with `embedded` in its page's address) checks the wheel, a finger the page scrolled with, a tap, the fingers after it, the focus lost, and the page saying it's embedded no more; the docs' examples test checks both with a real browser's gestures (see Docs site).
- Web builds have threads: the target is `wasm32-wasip1-threads`, and programs import their memory (`--import-memory`, up to 4 GiB). A cross-origin isolated page (served with `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`) makes it shared, and each thread the program starts (`pthread_create`, through wasi-threads' `thread-spawn`) is a worker running the same program on it (`tide.js`). Browsers won't share memory with other pages, so there the page gives the program memory of its own, changing the flag in its import to match, and it runs on one thread (`tide_web_threads` says 1), with the same results. The page's main thread can never block, so the web's pool (`platform/src/jobs.c`) only spins there and wakes workers with atomics, and wasi-libc's `malloc` spins too (`sched_yield`); its workers sleep when they have nothing to do (below). Browsers won't take views of shared memory for some calls (`TextDecoder`, `crypto.getRandomValues`, data channels): copy out first. When one thread grows the memory, V8 (Node 24's, at least) lets the others use what was added only once they hear of it, so memcpy and memset into memory another thread's growth made trap until then: engine code that runs on threads allocates with `tide_alloc`, `tide_alloc_zeroed` and `tide_realloc` (`tide/page.h`), never calloc or realloc, and calls `tide_memory_sync` where it picks up what other threads made (tasks, settling, a system's finish, the end of a tick's threads). The engine's `sbrk` notes how far the memory grew, so that's a comparison until it did. A worker's crash ends the program under Node (`run_wasi.mjs`), where it would leave the main thread spinning. The pool makes its workers the first time a tick has enough work for them (about three times desktop's threshold, since waking a worker costs more), as each costs a page far more than a thread does. Node runs tests the same way (`cmake/run_wasi.mjs`, with `worker_threads`), and `tide_platform_web_threads` ticks on threads in a cross-origin isolated page in headless Chrome, against one thread. `tide run --web` serves its page isolated; pages made to ship need a host that sends those headers (itch.io's SharedArrayBuffer option does) to run on threads.
- A page's pool has a thread for each processor the browser says the machine has (`navigator.hardwareConcurrency`, through `tide_web_threads`): both threads of a core that runs two, where desktop's pool counts cores, as a browser says nothing else, and half as many would be too few where cores run one thread (Apple's, most phones'). So a page's worker gives up a processor it has had no work for (the owner, 2026-10-05: cheaper waiters before another count). WebAssembly has no instruction that tells a CPU a loop only waits, and a page can't yield, so a loop that waits takes a core, or half of one, from a thread with work; and with one on every processor, the system takes a processor from a thread with work to run whatever else the machine has, and everything that waits for that thread waits a time slice. A hint to the CPU (`Atomics.pause`, tried) changes nothing: it's the processors being taken, not what the loops do on them. How:
  - A worker that looks for something to do in a tick 256 times in a row and finds nothing leaves the tick: the work returns on it (`IDLE_LOOKS`, `work` in `engine/src/jobs.c`), and it sleeps on the pool's count of calls (`calls` in `platform/src/jobs.c`, with `memory.atomic.wait32`). The caller's thread stays: the tick is its to finish, and a page's own thread can't sleep.
  - Whatever makes work for more threads than are at it asks for them: `tide_jobs.more(self, count)`, which a pool has when its threads can sleep (the platform layer's, on the web and on desktop; NULL for a host's own pool that has none, whose threads then stay in a tick, with the CPU's pause and the system's yield), through `ask` in `engine/src/jobs.c`. A system's end asks for the tasks it lets start, less the one its own thread goes on to, so a chain of systems of one task each wakes nobody. A parallel loop asks for its tasks less its own share. C's jobs ask for one thread at the first of a run, and each thread that takes one asks for those still there (`help_task`), so C that starts 23 pays for one call.
  - Nothing waits for a sleeper to wake: what nobody came for, the threads that are there do. And no call is lost: it's counted before the caller looks for sleepers, and a sleeper counts itself before it looks at the calls, so one of the two sees the other (`more` and `worker`; `tide_job_sleep` and `tide_job_wake` the same way).
  - Waking costs, which is why a thread looks a while before it sleeps and why what's known to be needed is asked for in one call (measured under V8, on Windows): the caller pays 2 to 6 µs to wake one thread and 7 to 12 for 23 at once, and the last of 23 is awake 60 to 90 µs later.
  - C whose tasks wait for each other inside their work (a solver's workers, for each stage it gives them) has `tide_job_sleep(word, seen)` and `tide_job_wake(word)` for a wait that has gone on long (`tide/jobs.h`; see Language, jobs). Box2D's and Box3D's solvers use them.
  - Measured (2026-10-05, 12 cores of two threads each, web-release under Node, each number the least of several runs taken in turn with the code before): 2,400 crates moving, Box3D's tick takes 3.3 ms on one thread, and on 24 went from 4.4 to 2.4 (on 12, from 2.4 to 2.1); Box2D's takes 1.5 on one, and on 24 went from 3.8 to 1.7 (on 12, from 1.5 to 1.2). With four other busy threads on the machine, as a player's has something else going on: Box3D's on 24 from 8.3 to 2.7, Box2D's from 6.2 to 1.75, and of ticks with no C, `versus_particles`' from 0.51 to 0.31 and the median of `versus_life`'s from 0.61 to 0.42 (on a quiet machine those were no slower before). In headless Chrome, which gives a page the same 24 (a scratch page of the same match, before spare pages made every tick shorter): Box3D's from 4.0 to 2.7, Box2D's from 2.4 to 1.7.
  - What's left is the count's own, and it stays (decided 2026-10-05: the pool keeps a thread for each processor the browser counts, and the solvers a worker for each of the pool's threads; no smaller pool and no fewer workers): on that machine 12 threads are still quicker than 24 for the physics packages, by a seventh for Box3D's tick and by two fifths for Box2D's, which on 24 is no quicker than on one thread. Their solvers gain nothing from a core's second thread, and a tick with every processor at work has none to spare for the rest of the machine. Fewer workers for the solvers alone, on a pool of 24, gets about half of that back (Box2D's tick 1.4 with 6 or 8 workers, Box3D's 2.2 to 2.3 with 8 to 16): the rest is in the tick's other work, which is slower on the bigger pool too, and not for the threads woken as a tick starts (waking only as many as its first tasks need was tried, and changed nothing).
  - `TIDE_THREADS=<n>` tells a program under `cmake/run_wasi.mjs` the machine has that many, for measuring. Desktop's pool had the same cost in a smaller measure, and its workers leave a tick and sleep the same way (see Determinism, Systems that touch the same data: the tick runs on threads).
  - `jobs_threads_come_back` (`platform/tests/jobs.c`, where a pool has `more`: on desktop and under Node) runs a system until the other threads have left the tick, then sixteen tasks, and checks threads that had left ran some. `jobs_threads_change_nothing` and `tide_platform_web_threads` run C that works in stages (`stage_out` in `platform/tests/jobs_tasks.c`), whose workers sleep between them where they can: in a page, a wait on its own thread would stop the program.
- Games keep running where nobody sees them, so a match goes on for the other players when its host switches tabs or minimizes. Browsers stop a hidden page's animation frames and slow its timers to about one a second, so while the page is hidden, frames come from a worker's timers (`tide.js`). Desktop windows keep running while minimized, waiting between frames on GLFW's events (`glfwWaitEventsTimeout`), so a window restored or closed goes on at once. Either way, each frame comes when the host says it next has work (`tide_platform_next_frame`), which for `tide/host.h` is its match's next tick (`tide_session_until_tick`), so frames follow the tick rate; a host that doesn't say gets 60 a second. Neither draws meanwhile (`tide_platform_draw`). `tide_platform_web_rooms` hides the host's page past the players' timeout, with its own timers and animation frames stopped (stricter than browsers, which slow them), and the match has to go on, with frames never faster than its tick rate. Like every test, it can't rest on how fast the machine is: a flaky test is a broken test, fixed rather than loosened or skipped.
- `tide_platform_web_rooms` puts two players in a room: a relay on this machine (`relay/`), and WebRTC between two frames of one page in headless Chrome or Edge, in real time rather than the other web tests' virtual time (`platform/tests/web_rooms.mjs`); `tide_platform_web_rooms_handover` puts three there, whose host leaves, to check host migration: once the page tells it both players say they're in (a message into its frame, which the program asks about with `tide_web_eval`), never after a time; `tide_platform_web_rooms_ended` checks that a match its host ended stays ended for a player who missed the goodbye. With `TIDE_RELAY` set, like `wss://relay.tide-engine.dev`, that script checks a deployed relay instead, and with `TIDE_ICE_POLICY=relay` too, its TURN (every packet through it). The relay's own tests run wherever there's Node (`node --test relay/relay.test.mjs`).
- Desktop rooms have tests of their own in every native build:
  - `tide_platform_rtc` checks each piece of `platform/src/rtc/` (crypto against the RFCs' values).
  - `tide_platform_rtc_vectors` (`platform/tests/rtc_vectors.mjs`) checks the crypto against Node's (OpenSSL's) on random inputs every run, and Node checks our signatures.
  - `tide_platform_rtc_fuzz` feeds everything that reads other machines' messages (JSON, SDP, STUN and TURN, certificates, DTLS, SCTP, WebSocket frames) real messages broken at random, with checksums and signatures made right again. Configure with `-DTIDE_SANITIZE=ON` (Linux and macOS) for AddressSanitizer and UndefinedBehaviorSanitizer, and give it more rounds: `tide_platform_rtc_fuzz 20000 <seed>`.
  - `tide_platform_rooms` (`platform/tests/rooms.mjs`) puts two desktop players in a match through a relay on this machine, and three in one whose host leaves (host migration), then each browser it finds (headless Chrome or Edge, and Firefox) in a desktop room and a desktop player in that browser's room, with the browser showing its address and hiding it. The same `TIDE_RELAY` (like `wss://relay.tide-engine.dev`) and `TIDE_ICE_POLICY` check a deployed relay and its TURN.
  - On a relay on this machine, desktop players' sockets stay on loopback (`TIDE_RTC_LOCAL`), so Windows' firewall has nothing to ask; Firefox on Windows offers no loopback candidates, so its cases use ordinary sockets. `TIDE_RTC_DEBUG=1` has the desktop side say what it does.
  - A browser's `--user-data-dir` (or Firefox's `--profile`) must be an absolute folder that exists, or the browser shows a dialog, even headless. Firefox needs `--wait-for-browser`, or stopping it leaves the browser running, and `MOZ_DISABLE_SAFE_MODE_KEY`: on Windows, Shift held as it starts (anyone typing on the machine) puts it in safe mode, whose prompt nobody answers headless, so it never opens the page.
  - Chrome is stopped by asking it to close (`Browser.close` on `--remote-debugging-pipe`): killing its processes from outside can miss one it starts again meanwhile, which keeps the browser from going. Each case starts once the last browser is gone, and its deadlines start once the page says it loaded, since a browser's first start on a fresh machine (CI) can take most of a minute.
  - What a desktop player waits for, it's told on stdin once it happened, never given a time: the handover's host leaves once both players say they're in, and a host ends its match once it says the relay has its room (`TIDE_RTC_DEBUG`).
- What's tested before a change goes to `dev`, and what isn't tested again after a merge, is in Testing and merging.

### MinGW builds

- On Windows, the `mingw-release` preset builds everything for the MinGW-w64 target (`x86_64-w64-windows-gnu`, with the UCRT), which tide builds Windows games for (see Packaging and releases): `cmake --workflow --preset mingw-release`. Everyday Windows builds keep Visual Studio's target.
- Its headers, C runtime and compiler runtime come from llvm-mingw, downloaded once into `build/llvm-mingw-<version>`, pinned (`cmake/mingw-toolchain.cmake`). clang is the usual one, linking with lld.

### Android builds

- The `android-debug` and `android-release` presets build everything for Android on x86_64, the emulator's, and `android-arm64` for phones and tablets: `cmake --workflow --preset android-debug`. They're clang with Android's NDK (`cmake/android-toolchain.cmake`), whose C library, headers and compiler runtime Google's license keeps out of this repo and the package: the build finds the NDK installed (ANDROID_NDK_HOME or ANDROID_NDK_ROOT, or the newest in the SDK: ANDROID_HOME, ANDROID_SDK_ROOT, or where Android Studio puts it). Programs run on Android 10 (API 29) and up, the first with thread-locals of its own, and with 16 KiB pages.
- Tests run on a device or emulator through adb (`cmake/run_android.mjs`): each program goes to a folder of its own under `/data/local/tmp`, so they run at once, with the `TIDE_` variables the test sets. The emulator runs x86_64 on x86_64 machines; arm64 needs a device (or an arm64 machine). Games generate their C with a native tidec, as web builds do.
- A game that opens a window (no `HOST`, or `HOST` with `WINDOW`) is an app: a shared library in `<target>.apk` (`tide_android_app`), which Android's own NativeActivity loads, so apps have no Java. The platform layer's window there is the activity's (`platform/android/activity.c`): the activity's callbacks run on Android's main thread, and the program's `main` on a thread of its own, which takes what changed (its window, its input queue) through its looper; a callback that takes something away waits until the program let it go. It draws with OpenGL ES 3 through EGL, in logical pixels (the window's over dpi / 160). Keys are by position, the back button is Escape (as in Unity), a mouse is the mouse, and fingers are touches. Its stdout and stderr go to the system's log (`adb logcat -s tide`).
- The renderer's pixel checks run as an app there too, `tide_platform_draw_app.apk` (`platform/tests/draw.c`, which keeps to the screen's top left corner whatever its size): installed and started by hand (`adb shell am start -n dev.tide.tide_platform_draw_app/android.app.NativeActivity`), it prints them to the log. The emulator's test run doesn't include it. `tide_platform_targets_app.apk` and `tide_platform_shaders_app.apk` are the targets' and the shaders' checks the same way (`targets.c`, and `shaders.c` with `shaders.tide`, whose frames are a window of their own size through `tide_platform_read_pixels_as`, whatever the screen's): OpenGL ES 3 compiles what tidec writes there, which is how the loop above was found.
- In the background an app has no window: frames come when the session asks and draw nothing (the frame loop's wait for a window nobody sees: `tide_window_unseen`, `tide_window_wait`), until Android freezes the app, as it does to apps in the background. Its match goes on through host migration, when the game has it (see Platforms).
- `tide_apk` (`compiler/cli/apk.c`, built natively like tidec) makes and signs apps with no tool of Google's: the binary manifest (Android's attribute IDs, from its SDK's `public-final.xml`), a resource table (`resources.arsc`) that only names the icon (the game's `icon.png`, or Tide's, `lib/android/icon.png` in the package), the libraries stored on 16 KiB pages, which Android maps from the APK, and APK Signature Scheme v2. Apps are made for Android 16 (API 36), as Google Play requires, and opt out of its predictive back (`enableOnBackInvokedCallback`), which would keep the back button from the game.
- Given a `.aab`, it makes an App Bundle for Google Play instead: the same files as bundletool lays them out, with the manifest and resource table as aapt2's protocol buffers (`Resources.proto`) and a `BundleConfig.pb` that keeps libraries stored on 16 KiB pages, signed as a JAR (`META-INF/TIDE.SF` and its PKCS #7 signature). `tide build --android --release` makes one beside the APK.
- Play takes upload keys of RSA only, so apps are signed with RSA of 2048 bits, PKCS #1 v1.5 (`compiler/cli/rsa.c`: keys, primes and signatures, from RFC 8017), and the key is a PEM file of a PKCS #8 key and its self-signed certificate (`compiler/cli/sign.c`), which OpenSSL and Java read. `tide_cli_tests` checks apps as Android does before installing one, bundles as Java checks a JAR, and RSA against a key and signature of OpenSSL's. Every build of this repo signs its apps with `build/android-debug.pem`, made once, so a new build installs over the last: `adb install -r build/android-debug/bench/sand.apk`.

### Cross-platform determinism tests

- `tests/test_crossplatform.c` and `compiler/tests/e2e/crossplatform` hash the exact bits of math results and of a full simulation. The hashes must be identical on every platform and in every configuration.
- If math or generated code changes the results on purpose, update the expected hashes from one platform, then confirm every other platform and configuration agrees.
- Random numbers have hashes of their own: `crossplatform_random` in `tests/test_crossplatform.c` (every function of `tide/random.h`) and `random_crossplatform_match` in `compiler/tests/e2e/random` (a match that rolls, from a seed).
- Test code must not depend on C's unspecified argument evaluation order: clang goes right to left on Windows and left to right on WebAssembly. Draw random inputs into locals first.
- The demo's smoke test (`demo --smoke`, or `demo.html?smoke`) plays a scripted session through the real platform layer. It checks a hash of the simulation (`SMOKE_HASH` in `demo/main.c`, the same on every platform) and pixels read back from the renderer. The native presets run it in a hidden window, so they need a desktop session with OpenGL; so does `tide_platform_draw`, which checks the renderer's pixels. Native tests like these have the `gpu` label, which CI leaves out (`ctest -LE gpu`): its Windows and Linux runners have no GPU, and on its macOS ones GLFW finds no OpenGL to open a window with (it was tried: the window isn't made). So nothing runs Tide's window and its OpenGL on a Mac; there, only the web tests draw, in Chrome, on WebGL and WebGPU. The web presets run both in headless Chrome or Edge, and skip them if neither browser is found: on the browser's software WebGL (`backend=webgl`, in virtual time, as every `tide_add_web_test`), and again on its software WebGPU (`demo_smoke_web_webgpu`, `tide_platform_draw_webgpu`: `tide_add_web_test(... WEBGPU)`, label `webgpu`). The browser only answers about its GPU in real time, so those pages are served (`cmake/run_web_served_test.mjs`), cross-origin isolated, so on threads too, and `backend=webgpu` fails rather than falls back. Chrome has no WebGPU when its own drawing runs on SwiftShader (`--use-angle=swiftshader`, the other web tests' flag), so these run it with `--enable-unsafe-webgpu --use-webgpu-adapter=swiftshader`, and on Windows `--use-angle=d3d11-warp`. CI runs them on Windows and macOS. On Linux's runners, which have no GPU, Chrome draws with WebGPU but gives nothing back when a test reads its pixels (through a 2D canvas, the only way that doesn't wait), whatever flags it's given, so CI leaves the label out there (`ctest -LE webgpu`), as it leaves `gpu` out everywhere. On Android it's the demo's app, started by hand with its argument in the intent (`adb shell am start -n dev.tide.demo/android.app.NativeActivity --es tide.args "--smoke"`), and it says how it went in the log. Its pixel checks hold whatever the screen's shape, a phone's upright included: the demo's camera fits the arena to the screen's narrower side (`DrawArena` in `demo/demo.tide`), so the player is on it wherever the script left it.

### Benchmarks

- `bench/` holds games that stress the engine, played by bots, as targets for what a general engine has to handle: `sand` (falling sand and water that every player paints into at once) and `gallery` (every player has a big canvas of their own, and players keep joining). A voxel world, endless, with blocks placed and broken, joins them once the engine can hold one.
- Each is a program, `bench_<name>` (`--help` lists its options), on a harness of its own (`bench/bench.h`): a dedicated server and bots, each a client of its own on the loopback network, with latency and loss, in made-up time, so a run goes as fast as the machine can take it and repeats exactly. It reports each machine's update times, what they spent simulating, hashing, snapshotting and packing worlds (through the game's `tide_game`), what each machine sends, how long joins take, and the world's size.
- Measure with the `release` preset. The machines run one after another, so a run takes about as long as all of them together.
- Runs are kept: measuring a change saves its runs (`--save <label>`, named for the change, with `-1024` for sand at that size) into `bench/results/`, a few of each so the noise shows, and commits them, so the files are a history of improvements, setbacks and noise. A comparison with an older build saves that build's runs too, under its own label. `node bench/compare.mjs [benchmark...] [--last <n>]` puts runs side by side.
- Tests run each one `--quick`, which fails when a client's world went wrong, a bot couldn't join, or the server's world ends with another hash than the one in `bench/CMakeLists.txt`, which every platform and thread count has to agree on. Timings aren't checked: machines differ too much.
- Sand is a game people play too: `sand` (`sand.html` on the web) is `sand/sand.tide` with `sand/play.tide`, its views, GUI and rooms, and the mouse through the input's `Sample`, which the benchmark's bots don't call. The docs site shows it (see Docs site).
- A benchmark holds its game as the engine can today, and says where that's not how it should be. It changes as the engine does (sand's cells were a list, then a grid that a chunk system stepped on threads, then 2 by 2 blocks that a parallel loop steps), and its expected hash with it.
- `bench/versus/` measures Tide against C: a concept written both ways, each as fast as its language allows, on the same work (`bench/versus/versus.h`). Each is a program, `versus_<concept>`: particles (an ECS system streaming through a component), sand (`sand/sand.tide` itself), life (a grid stencil), churn (spawning and destroying), events, and nbody (every pair, through a list). `cmake --build --preset release --target versus` runs them all.
  - Every way starts from nothing and runs the same ticks, the first of which sets it up, and has to end with the same result, bit for bit: the same work, so the times compare. A digest adds up a hash of each thing a way holds (`versus_item`), so ways keep things in any order. Tests run each one `--quick` and fail when the ways disagree.
  - The C is what someone who knows the machine writes: arrays rather than structs where that's faster, branches turned into selects for SIMD, arrays staggered so they don't share their addresses' low bits (4K aliasing), and threads on the same pool Tide ticks on (`versus_for`), only once there's enough work for them to pay (`versus_pieces`; `--split` and `--quick` always split). A way with a trick Tide can't do yet is a way of its own (`C, lookup`, `C, SIMD`). The C builds with the flags generated code does, so the results stay bit-identical.
  - It times each tick after the warm-up ones, on one thread and then on every core, and reports medians, and how many times as long Tide takes. `--save <label>` adds a run to `bench/results/versus.jsonl`.

### Tide programs

`tide_add_game(<target> [SOURCES <file.tide|file.c|file.cpp>...] [HOST <file.c>...] [WINDOW] [NAME <name>] [TITLE <title>] [STATS] [LAYOUT] [WARNINGS <text>...] [PACKAGES <Name> <file.tide>...])` builds a game as the program `<target>` (see `cmake/Tide.cmake`):

- The game is every `.tide` file in the current source folder and its subfolders; the next build picks up new files. `SOURCES` lists the files instead, for tests and folders that hold several games.
- The game's C (its `extern` functions') is every `.c` file there but the `HOST` ones and those in hidden folders or `build/`, or the `.c` files in `SOURCES`. Its C++ files (`.cpp`, `.cc`, `.cxx`) go the same way, with tide's flags for them (`TIDE_CPP_FLAGS`): the project stays C, so the C compiler compiles them and programs link as C. `compiler/tests/e2e/cpp` runs C++ with no runtime on every target. Unlike `tide`, it doesn't pick up prebuilt libraries.
- Without `HOST`, the game is the whole program and needs no C: a generated `main` runs it in a window through `tide/run.h`. On the web it's `<target>.html`.
- It doesn't read `tide.packages`: games with packages build with `tide`. `PACKAGES` is for tests of what packages do to a game: the files after each package's name are that package's, and compile before the game's (tidec's `--package`).
- With `HOST`, those C files are the program (tests, the demo's smoke test, custom hosts). They include `<name>.h`, where `NAME` defaults to `<target>`. `WINDOW` says the host opens a window, so on Android it's an app (see Android builds). They link the engine and `tide_font_bold`, the bold weight's file as a library of one object, which a linker only takes for a game that says `Font.Bold` (see Rendering and platform).
- `tidec` compiles all the files together, in order of their paths. The generated files regenerate whenever a `.tide` file or `tidec` changes. `tide_add_game` gives tidec the files as a list in a file (`@<file>`, a path a line; `tide/<target>.sources` in the target's build folder), since a big game's are more than a command line holds (32,767 characters on Windows), and tidec takes as many files as there are.
- tidec has to stay fast on big games (thousands of files, declarations and systems): with `TIDEC_TIMES` set in the environment, it says on stderr how long each phase of a compile took. Names are looked up through an index of the declarations by namespace and name, and by name in generated C (`decls_by` in `compiler/src/check.c`), never by going through them all.
- `node bench/compile.mjs --tide <installed tide> --save <label>` measures cold game caches, unchanged builds, a Tide body edit, a C body edit and a header edit, keeping repeated wall times, object reuse and machine/compiler/revision metadata in `bench/results/compile.jsonl`. `bench/README.md` lists native/web, debug/release and source-size options. Cold means an empty game cache, with the installed tools and filesystem caches still warm.
- A warning from `tidec` fails the build, unless part of its text is listed after `WARNINGS`; each of those has to be there (see Building).
- `<target>_schedule` is a build target that prints the game's schedule: which systems can run at the same time, and why the others wait.
- Every game's files are listed in `build/tools/games.txt`, one `<game>\t<path>` per line. A path ending in `/` is a folder: every `.tide` file in it and its subfolders, so editors see new files before the next build. A file of a package (`PACKAGES`) has the package's name after it, `<game>\t<path>\t<package>`. `tidels` reads it, and the one in `build/tools/` of any folder open in the editor, to analyze a game's files together, in `tidec`'s order. A file in no game belongs to the open folder it's in, as `tide run` would build that folder, unless a manifest lists games in that folder: then it's analyzed alone.

The generated header is the API between the game and the host. Namespaced declarations have their namespace in their C name: `Combat.Health` is `Combat_Health`, read with `tide_get_Combat_Health`.

- `tide_world`: the whole simulation state. Its data is in pages it shares with its snapshots (see ECS and simulation state), so a world starts zeroed (`{0}`, static or `calloc`), copying the struct isn't a snapshot (`tide_world_copy` is), and `tide_world_free(w)` lets it go. When fields hold text or lists, it has a `heap` they're kept in; hosts read a text field with `tide_text_read(&w->heap, field)`.
- `tide_world_init(w, dt)`: clears the world, sets `Time.dt` and singleton defaults, and loads the `Main` scene if it's the match's. `Time` is a singleton like the game's, in the world: `t` (`tick * dt`, which the tick sets from the tick, never by adding) and `tickRate` (1 / `dt` to the nearest, set here; 0 for a `dt` no rate fits) are stored fields, so views blend `t` and shaders get it as any float they read.
- `TIDE_MAIN_IS_LOCAL` is defined when `Main` is a local scene: the program starts outside any match.
- `tide_world_tick(w)`: runs every system once, then applies structural changes. With no scene left, it loads `Main` again if it's the match's; `tide_frame` does the same for a local `Main`. `tide_world_tick_events(w, jobs, events)` is the same tick, recording into a `tide_event_log` what it sent that the game's local handlers hear (see Networking); the world comes out the same.
- `tide_world_ended(w)`: whether the match is over: its last scene unloaded and `Main` is local, so it can't come back. The server stops ticking there and tells every player, who go offline with `TIDE_DISCONNECT_ENDED` (`Ended` in Tide).
- `tide_local`: this machine's local state, outside every world. `tide_local_init(local)` clears it and sets its singletons' defaults.
- `tide_frame(w, previous, alpha, verified, local, draw, gui)`: runs every view once, adding their Draw calls to a `tide_draw_list` and their widgets to a `tide_gui`, then applies the local changes they made. Views see the match's floats blended from `previous`, the tick before `w`, by `alpha` (0 to 1), so they're smooth at any tick rate; `tide_session_view` gives all three, and `verified`, the last world the server confirmed, which local fields are kept by (see ECS and simulation state). Pass NULL and 1 to draw `w` as it is, and NULL for `verified` where `w` is all there is. Call it once per frame, after `tide_draw_reset(draw)` and `tide_gui_begin(gui, devices, tide_platform_screen_size(), tide_platform_measure_text)`, then `tide_gui_end(gui, draw)` and render the list with `tide_platform_draw(draw)`. Outside a match `w` is NULL, and views that read the match don't run. A zeroed `tide_gui` is ready to use. Before it, `tide_local_events(local, events)` hands over what the match sent since the last frame (a session's `tide_session_events`, or the log a host gave `tide_world_tick_events`): the frame runs the local handlers of the match's events first, then lets go of local fields, then runs the views. `verified` parameters read `verified`, or `w` where it's NULL.
- Components are values, as a world keeps them in lanes (see ECS and simulation state): `tide_has_<Component>(w, entity)` says whether an entity has one, `tide_get_<Component>(w, entity)` gives a copy (zeros when it has none), and `tide_set_<Component>(w, entity, value)` puts one back (false when it has none, changing nothing), as its bytes: text and lists in it stay where they are in the heap. A local component's take the `tide_local`. A match component's local fields are a struct of their own, `<Component>_local`, with `tide_has_<Component>_local(local, entity)` (whether anything was written for it), `tide_get_<Component>_local` (the defaults when nothing was) and `tide_set_<Component>_local`; a singleton's are `local-><Singleton>_local`. The component's own struct and accessors are the match's part. `TIDE_AT(w, arch0_Body, Body, row)` (a copy too) and `TIDE_ENTITY_AT(w, arch0_Body, row)` read an archetype's rows, for tests and tools.
- `tide_world_player_joined(w, player)` and `tide_world_player_left(w, player)`: send `PlayerJoined` and `PlayerLeft`, handled at the end of the next tick. Every machine calls them before the same tick.
- `tide_world_entity_count(w)` and `tide_world_print(w)`: for debugging.
- `tide_world_copy(to, from)` and `tide_world_hash(w)`: snapshots and state hashes between ticks. `tide_world_pack(w, out, capacity)` and `tide_world_unpack(w, data, size)`: the world as bytes, which hot reloading carries over; the same for the local state (`tide_local_pack`, `tide_local_unpack`, `tide_local_free`).
- `tide_world_pack_delta(w, base, need, need_size, &size)` and `tide_world_unpack_delta(w, base, data, size)`: the world as a delta (`tide/delta.h`), which sessions send: page by page, what differs from `base` (a world the receiver has too: changed pages go XOR'd with the base's), or from the receiver's own world, which lacks the pages `need` says, or the whole world. `tide_world_hash_pages(w, &size)` lists the pages' hashes, and `tide_world_need_pages(base, hashes, size, out, capacity)` says which of them a world lacks. Unpacking shares the base's pages that are the same and checks the world's hash. Storage a world gains (like the tables of tasks) goes in all of these as it does in packing, copying and hashing: what's left out stays in the struct's bytes, pointers and all.
- `tide_world_start(w, dt, start)`: `tide_world_init`, starting the match in the scene `start` names (`tide_start`, from `Session.Start`), or `Main` for NULL.
- `tide_world_start_seeded(w, dt, start, seed)`: the same with the match's seed, `Time.seed` (its low 31 bits), only in a game that has one (see Random numbers, under Language). The two above start with seed 0. `tide_game.start` always takes the seed, and a game without one ignores it; `tide_game.seeded` says which.
- `tide_game_api`: the game as sessions run it (`tide_game` in `tide/session.h`): the world's size and functions, the input packed for the network, and its settings (`settings { ... }`): `tick_rate`, `title` and `stats` among them, 0, NULL and false where it sets none. They're in the generated `.c`, so they don't change `tide_game`'s hash, but for `max_players`, which is in the header too (`TIDE_GAME_PLAYERS`), as the world keeps an input for each. A session whose desc leaves `tick_rate` at 0 starts its matches at the game's rate, or 60; `tide_run_desc`'s `title` (`TITLE`, `--title`) goes over the game's, and `game_name` stands in when neither says.
- Local code's requests of the session (`Session.Start` and the like) wait in the local state: `tide_local_take_request(local, &request, &start)` takes them, in order. `Clipboard.Copy` goes the same way, as `TIDE_REQUEST_COPY`, after them, and hosts put its text on the clipboard (`tide_platform_copy`). Pasting is the platform's: Ctrl+V (Cmd+V) types the clipboard's text into `tide_devices.keyboard.text`, from the system's clipboard on desktop (GLFW's) and Android (Java's), and the browser's `paste` event on the web. Hosts tell local code where it stands with `tide_local_set_session(local, state, player, ping, server, open, room)` (`open` from `tide_session_status`, the room from `tide_platform_room_code`, `""` while the match is closed), `tide_local_connected(local)` and `tide_local_disconnected(local, reason, message)` (a kick's message, from `tide_session_event`). Before each `tide_frame`, hosts give the frame's length with `tide_local_frame_time(local, seconds)` (`tide_host_game.frame_time`), which local tasks' `Wait.Seconds` counts down and `Frame.dt` reads (`tide_local.tide_frame_seconds`, in every game's local state, 0 until a host gives one). `Frame.dt` is local code's: views, local handlers and tasks, and the functions they call, which are handed the local state as those that reach files are (`decl.frame_time`, `check_frame_time_use` in `compiler/src/check.c`, `takes_local` in `codegen.c`); the match is told to read `Time.dt`. Its name is a pick the owner hasn't confirmed (`docs/spec.md`, Local state), and there's no clock of seconds beside it on purpose: a float of seconds loses precision after hours. `gone.message`, like `Session.room`, is kept beside the local state rather than in a field, so neither costs a game a heap.
- If the game has an input (it declares one, or systems take `Devices`), `TIDE_HAS_INPUT` is defined and `tide_input` names its type. `TIDE_GAME_PLAYERS` is how many players the game's matches take (its `maxPlayers` setting), and `TIDE_SERVER_INPUT` the server's slot in `tide_world`'s `inputs`, after theirs. `tide_input_sample(devices, local)` runs the input's `Sample` on the client, with this machine's local state: give it a copy of the devices that `tide_gui_hide(gui, &copy)` took what the GUI is using and what views claimed out of, then call `tide_devices_consume(devices)` on the real ones. The input holds what match code reads of the devices (`tide_dev`), everything else zero. `tide_world_set_input(w, player, input)` sets a player's input for the next tick, and `tide_world_set_server_input(w, input)` the server's, which entities without an owner read. Both repair NaN and infinite floats, apply the fields' `[Clamp]`, `[Min]` and `[Max]`, then run the input's `Sanitize`, if it has one.

## Packaging and releases

Users get Tide as the `tide` command, not this repo: see README.md.

- `tide run [--host [port] | --join code | --connect address]`, `tide build [--release] [--web | --android]`, `tide schedule`, `tide shaders`, `tide add`, `tide update`, `tide fetch`, `tide publish`, `tide editors`, `tide upgrade` and `tide version` (`compiler/cli/`, owned by Claude). It runs tidec's front end in-process, compiles the generated C and the engine's sources with the determinism flags (as separate files, like the CMake build), and links the prebuilt platform layer. `tide run` reloads the game as its files change (see Hot reloading), but for a run with no window (`--capture`, `--frames`, `--script`: see Rendering and platform), which runs once: tide makes the files' paths whole from where it was run, since the game runs in its own folder.
- Packages have clang and lld built into tide (`TIDE_EMBED_LLVM`, `compiler/cli/llvm/cc.cpp`), so users need no compiler: `tide cc` is clang, whose compiles run in tide's process and whose links go to lld in it. tide links the static libraries of LLVM's own release, downloaded once into `build/llvm-<version>` and pinned (`cmake/LLVM.cmake`, which also builds the zlib and zstd they were built with, and on Windows libxml2; unpacking needs the `zstd` program). macOS's release holds them as LLVM bitcode, so tide links there with that release's lld. Builds of this repo without the option use an installed clang (`--web` needs `wasm-ld`, next to it or on `PATH`).
- Generated game and launcher objects are reused in `.tide` when their C contents, generated header, installed headers, compiler and flags are unchanged, in builds and within a hot-reload run. Tide still checks and generates the whole game and links each build; this is object reuse, not per-file incremental Tide analysis. Replacing installed headers requires restarting a running `tide run`.
- The package brings the C library for web games (wasi-libc) and for Windows games, which build for MinGW-w64 (see MinGW builds): Microsoft's C runtime can't ship with tide, and the UCRT is part of Windows, so players need nothing else. Linux games use the system's C development files, and macOS games the SDK of Apple's command-line tools (tide sets `SDKROOT`).
- A game is a folder of `.tide` files. tide keeps its work in `<folder>/.tide/` (hidden on Windows too, and it ignores itself in git) and puts `tide build` output in `<folder>/build/`.
- A game's packages are what its `tide.packages` lists (`docs/tools/packages.md`, `docs/spec.md`, Packages): git repositories, each pinned to a commit, folders, and the packages that come with tide (below). No lock file: the game's file lists every package it builds with, those its packages need included, and its line wins. `compiler/lsp/packages.c` reads the file and finds each package's folder (tide and tidels share it). `compiler/cli/fetch.c` downloads a commit as its host's archive, and reads branches and tags from git's `info/refs`, with curl and tar as `tide upgrade` does, so users need no git; commits are kept once for every game (`TIDE_PACKAGES`, or `%LOCALAPPDATA%/Tide/packages` and `~/.tide/packages`). A commit unpacks in a folder of that tide's own, and its files move into the commit's folder one by one, never as a folder (`fetch_place`): Windows renames no folder while a program has anything in it open, as antivirus has each new file for a moment, and a file such a program has open still moves. So a commit's folder is whole when it has `.tide-fetched` (`packages_fetched`), which goes in last, and one without it is downloaded again; a file that's there already is that commit's, so a download goes on from one that stopped and two tides can get a commit at once. `compiler/cli/packages_cmd.c` is `tide add` and `tide update`, which only change the file's commits and add what packages need. Packages' files compile first, each package after those it needs, then the game's (`compile_inputs`), and their C with the game's. A folder with a `tide.packages` is a game or a package of its own, never part of the one around it (`folder_find_own`). Tests stand in for git hosts with `TIDE_GIT_MIRROR` (`compiler/cli/tests/packages_test.cmake`).
- Packages that come with tide are in its installation, and a game opts into one with a line: one that doesn't list it compiles and links nothing of it. How the line is written and where the package is looked up are picks (Provisional in `docs/spec.md`, Packages, awaiting the owner). What's built, and what code relies on:
  - The line is a name alone, lower-case letters and digits after a letter (`packages_is_builtin` in `compiler/lsp/packages.c`): `box2d`. Nothing else in the file is written so, as a git source has a `/`, a folder starts with `.` or is absolute, and `package` and `tide` take a second word. It's `package_line.builtin`, apart from `local`: no commit and no `@ref`, each an error that says it's the version this tide came with.
  - The package is the folder `<name>/` of the one folder that holds them, which tide and tidels say as they start (`packages_set_builtin_folder`); until then no package comes with tide, as in tests that say nothing. In an installation that's `<root>/src/packages/`, beside `src/engine/`, as both are sources that compile with the game. tide says its own: `<root>` is the folder its `bin` is in (`install_root` in `compiler/cli/main.c`), as for `include/` and `src/engine/` (`build_setup`), so a tide built from this repo has them once `cmake --install` put them beside it, as it has the engine's files. tidels says its installation's (`installed_root` in `compiler/lsp/main.c`, the folder above its own with `include/tide/math.h`) or, in a build of the repo, the repo's `packages/` (`TIDE_SOURCE_DIR`), as its engine headers are the repo's then.
  - This repo's are in `packages/`, a folder each, which every tree installs as `src/packages/` (the top `CMakeLists.txt`; `OPTIONAL`, as there may be none), without what tide makes in a game's folder (`.tide/`, `build/`). Not as `packages/`: where the installers put tide, an installation's `packages/` is where packages from git are kept (`packages_cache`), and `tide upgrade` replaces every folder its release has, whole. So an upgrade replaces these with `src/`, and never touches that one.
  - Beyond that it's a folder's package: `packages_folder` gives its folder, so resolving, the build's Tide files, C and libraries, `tide run`'s watching (`game_stamp`) and tidels go as for a folder. Its `tide.packages` says `package Name` and lists what it needs, which the game's file lists too: by name, or from git, never a folder.
  - `tide add <name>` writes the name, in lower case however it was typed, and what the package needs. `tide update` leaves such lines alone and says nothing about them. A name no package has is an error that lists those there are (`packages_builtin_names`: the folders named as one that have a `tide.packages`) and the closest (`packages_builtin_unknown`, with `suggest_close` of `compiler/src/common.c`).
  - `tide_cli_tests` checks the lines and a folder of packages made up for the test (`compiler/cli/tests/packages_test.c`); `tide_cli_packages` puts tide in an installation of its own, with packages, and runs `tide add`, `update` and `schedule` there; `lsp_open_folder_with_a_package_that_comes_with_tide` checks tidels.
- A game's C is in its folder too, outside hidden folders and `build/`: every `.c` file compiles with the game's flags, and every `.cpp`, `.cc` and `.cxx` one as C++ with no runtime (see Language), each again only when it, a header there (`.h`, `.hpp`, `.hh`, `.hxx`, `.inl`) or the flags change, and every library (`.a`, `.lib`, `.so`, `.dll`, `.dylib`) links when its contents say it was built for the target's platform and CPU (`compiler/cli/libraries.c`), since `.a` is every platform's. `.so`, `.dll` and `.dylib` files are copied next to the program, and `.so`/`.dylib` ones found there through its rpath; a `.dll` links through its import library. Linux's libraries and Android's are both ELF, for the same CPUs: a shared one is Android's when it has Android's note (`.note.android.ident`, which the NDK's `crtbegin_so.o` puts in everything linked for Android, Go's libraries too), never by what it needs (musl's C library is `libc.so`, as Android's is). A static one has nothing that tells (clang makes the same objects for both), so an ELF archive is Linux's, and Android games bring shared libraries: no folder or name marks one as Android's. An Android build links the game's library for each CPU to that CPU's shared libraries, and they go in the APK and the bundle beside it (`lib/<abi>/`), stored on 16 KiB pages, each under the name the game's library asks for it by: its soname, or its file's name when it has none, which has to be `lib<name>.so`. tide warns about one whose segments are aligned for less than 16 KiB, as phones with those pages may not load it; when an Android link fails, it names the ELF libraries for that CPU it left out as Linux's. A web program may only leave undefined what the prebuilt platform layer does, which are GL's functions, from the page: tide lists them from that library's objects (`page_imports_flag`, `wasm_archive_imports`) for the linker, so any other function nothing defines fails the link, where allowing them all would leave it to fail when it's called. After a failed web link, tide says which of the game's extern functions nothing defines.
- The package is everything installed as the `tide` component: `bin/` (tide, tidels), `include/`, `src/engine/`, `src/packages/` (the packages that come with tide, as sources), `lib/native/`, `lib/web/` and `lib/android/<abi>/` (the prebuilt platform layer, one library each, with GLFW's objects inside the native one), `wasi/` (wasi-libc and the compiler runtime for wasm), `mingw/` (on Windows: MinGW-w64's headers, C runtime and compiler runtime), `lib/clang/` (clang's own headers), `web/` (the page and `tide.js`), `editors/` and `VERSION`. It comes from the `package` preset (clang and lld built in, static C runtime on Windows), the `web-package` preset, the `android-package-arm64` and `android-package-x86_64` presets and, on Windows, the `mingw-release` preset, put together by `cmake -DNAME=tide-windows-x64 -P cmake/package.cmake` into `build/dist`. Anything tide needs at build time must be installed into the package; a game build can't see this repo. The same goes for `tidels`, which reads the engine headers from the package's `include/`. Nothing else goes in: games are C, built for this machine's CPU, Android's and the web, so the package leaves out C++ headers, Windows' interface definitions (`.idl`) and type libraries, and clang's headers for other CPUs, GPUs and the runtimes it doesn't ship (`cmake/LLVM.cmake`, `platform/CMakeLists.txt`). Every C header of the C libraries stays, since a game's C can include any of them.
- `editors/tide.vsix` is the VS Code extension (`tools/tide-vscode`), for VS Code, Cursor, VSCodium and Windsurf. Only the `package` preset builds it (`TIDE_EDITOR_EXTENSIONS`), since it needs Node's npm. The installers run `tide editors`, which installs it into every one of those editors it finds, and `tide upgrade` updates it in the editors that have it.
- The JetBrains plugin (`tools/tide-jetbrains`, Gradle and Java; on Marketplace as `io.github.blenminer.tide`) isn't in the package: CI builds it and checks it with the plugin verifier on every run, attaches it to each release, and publishes stable releases to JetBrains Marketplace with the `JETBRAINS_MARKETPLACE_TOKEN` secret. Marketplace installs LSP4IJ, which it needs, along with it.
- Users install with `install.ps1` or `install.sh` into `%LOCALAPPDATA%\Tide` or `~/.tide`, with `bin` on `PATH`, and `tide upgrade` replaces the installation from GitHub Releases. It checks each download against the release's `SHA256SUMS`, and renames running programs aside instead of overwriting them. Once a day, tide says when a newer version is out. tide and the installers pick a channel's highest version by semantic versioning (`compiler/cli/release.c`), never the last one published, of those with this platform's package (some old nightlies went out without macOS's, back when its failures didn't hold releases back), and stable also asks GitHub for its latest release, which nightly ones push out of the list. `tide upgrade` only goes forward, except to an exact `--version` or when switching channels. Builds made from this repo are versioned `<VERSION>-dev` and never look for updates.
- An upgrade never loses what's installed, and one that stopped says so (`compiler/cli/install.c`):
  - The package's `VERSION` is the installation's version, and an installation is whole when that's its tide's own (`tide_installation_whole`). `cmake/package.cmake` takes it from the native tree, whose tide it is: the other trees install one too, and aren't all configured with the version.
  - `VERSION` goes before anything of the installation changes and comes back last, and tide and tidels go just before it, after everything they build with. So an upgrade that stopped leaves the old tide, which still sees a newer version, or an installation without its `VERSION`. tide builds nothing with one that isn't whole (`build_setup`), `tide version` says so, and `tide upgrade` installs the version again even when it's the newest already. The installers run `tide upgrade` on an installation that's there, so running one again finishes it too.
  - Nothing goes before what replaces it is in its place: a folder moves to `.upgrade/old`, and back when the new one can't take its place.
  - Windows moves no folder while a program has anything in it open (an editor that shows an engine header watches the header's folder, a terminal is in one), so what's in such a folder is replaced one by one, and what the package has none of there goes. Only a file a program has open without sharing stops an upgrade, which names it and stops there. No retries, and nothing timed.
  - `tide_cli_tests` holds folders and files open as editors and compilers do (`compiler/cli/tests/install_test.c`, those cases on Windows only), and `tide_cli_upgrade` (`compiler/cli/tests/upgrade_test.cmake`) runs `tide upgrade` against releases in a folder (`TIDE_RELEASES_URL`), where the tide that upgrades replaces its own program.
- An upgrade that went well says one line, the version it had and the one it has now, and nothing else (agreed): not which editors it updated, nor where the release's notes are. In a terminal, a bar each for the download and the unpacking is drawn over itself above that line (`run_step` in `compiler/cli/upgrade.c`), so nothing waits unseen:
  - curl and tar run in the background, and what they say waits in a log until the bar is done with its line. One curl gets the checksums and then the package, so the download's bar, which follows the package's file as it grows, ends when both are there.
  - The unpacking's bar follows the bytes of the files unpacked so far, against what the package unpacks to: a zip's directory says (`unzip_size`), and a gzip's last four bytes, the size of its tar.
  - `tide editors --update`, which the new tide runs, says nothing unless an editor refuses the update, and that waits for the upgrade's line. While editors take it, a terminal says so on the line the upgrade's own then takes.
  - `tide_cli_upgrade` checks the line is all there is, where there's no terminal.
- `tide build --android` (`compiler/cli/build.c`, `android.c`) builds the game for both of Android's CPUs, as `libgame.so` with `lib/android/<abi>/`'s platform layer, and makes the app with `apk.c`, signed with `~/.android/tide.pem`, or the key `TIDE_ANDROID_KEY` names (made once: a phone only updates an app with the key it was installed with, and it's the user's upload key on Play); `--release` makes the bundle too. The ID is the game's `appId` setting, or `dev.tide.<name>`, which `--release` refuses, and the version people see its `version` setting (1.0 without it). The version code is the minutes from 2020 to now (`SOURCE_DATE_EPOCH`, where it's set), so every build updates the last with no number to keep. `tide run --android` installs it with adb, starts it with the session's flags (the intent's `tide.args`, which the backend gives `main`), and shows what it prints (`adb logcat -s tide`) until it ends. Saving a game's file builds the app again, installs it and starts it over (the match with it: no code is swapped into a running app yet). The NDK and adb are the ones Android's tools installed (ANDROID_NDK_HOME, ANDROID_NDK_ROOT, ANDROID_HOME, ANDROID_SDK_ROOT, or where Android Studio puts them), or else tide fetches them once from Google, pinned and checked against Google's SHA-1s, after the user accepts Google's license (or `TIDE_ACCEPT_ANDROID_LICENSE` is set; editors' runs pass on what's typed, and set `TIDE_INTERACTIVE` so tide asks there though its input isn't a terminal), into `<root>/android/`: only the NDK's C headers, its libraries for Android 10 and its compiler runtime, unpacked by tide's own unzip (`unzip.c`: Linux's tar can't read zips). tide's built-in clang has X86, AArch64 and WebAssembly, and lld's ELF driver, on every host.
- `.github/workflows/build.yml` tests and packages Windows, Linux and macOS on pushes to `dev` and `release` and on pull requests, tests the MinGW target on Windows, runs the Android tests on the emulator on Linux (KVM), whose image comes through the runner's SDK manager, and runs the suite once more on Linux under AddressSanitizer and UndefinedBehaviorSanitizer (the `sanitize` preset: see Language, no Tide code can corrupt memory). That job leaves two tests to the others: the relay's, which is Node's, and rooms with the runner's browsers, which nobody has run under sanitizers yet (without browsers it passes). Windows and Linux build with the LLVM tide's built-in clang comes from (`TIDE_LLVM_VERSION`): LLVM's own release on Windows, and LLVM's apt packages of that major version on Linux. macOS builds native code with Apple's clang and web code with Homebrew's LLVM. Every platform's Node is 24 (`actions/setup-node`; see Building for why the runners' own won't do on Windows). Pushes to `dev` publish nightly pre-releases (`0.3.0-nightly.48`); pushes to `release` publish stable releases, and semantic-release commits the new `VERSION` there. A failure on any platform fails the run and publishes nothing, so every release has every platform's package; nothing in CI may swallow a failure (no `continue-on-error`). Native tests that need a GPU (label `gpu`) are skipped in CI: no runner can open their window.

### Box2D

An experiment the owner asked for (2026-10-05: "we can always remove it"), written as a user's package would be: Tide and C in `packages/box2d/`. What it needed of the engine is general, and noted where it is: jobs, `out List<T>`, systems written in C and `world.Set<T>(this, ...)` beside a read parameter (see Language and Determinism), and how a big list goes to C (`tide_list_flatten`). Its names and its shape aren't agreed, and its `README.md` says what it has and hasn't, and what it costs. Its page for users is `docs/physics/box2d.md`, with a live example (see Docs site).

- `packages/box2d/box2d/src/` is Box2D as it came (`main` at `ac7c751`, MIT, so a game that lists the package ships Box2D's notice), its public headers in `src/box2d/` beside the sources so they're found with no include path, and the changes `box2d/TIDE.md` lists, each marked `Tide:`. `box2d.tide` (namespace `Box2D`) is the components, events and systems, and `bridge.c` their C, whose functions are `b2t_`: tidec keeps `tide_` for the engine, in a package too.
- **Box2D's state rides in the match.** Its world is in C's memory, where rollbacks, joins, host migration and reloads don't reach, so after each step its whole state goes into the match: Box2D's own image of its world into `Physics.image`, a `List<byte>`, with `Physics.stamp`, which names it. C's worlds (`worlds` in `bridge.c`, four) are only where a state is stepped: a tick's first system finds the one at its match's stamp (`b2t_open`) or has one made from the image (`b2t_restore`). Two matches at one stamp are at one state, so either's world serves both, as the server's and the client's in one program are. Nothing else is needed for any of it, and nothing in the engine knows.
- **A stamp is the stamp before it and everything done to the world since, hashed** (`note` in `bridge.c`): Box2D's next state is its last and what's done to it. So the image is never read to name it, and everything that changes C's world has to say so there, or two worlds that differ would go by one stamp.
- **Everything that changes Box2D's world happens in the package's systems, from what the match says.** Code moves a body by writing its component: `Enter` compares each with where the last step left it (the `step` fields, which `Leave` writes) and syncs the ones that differ, and a destroyed entity's body is listed (`Physics.gone`) and goes at the next step. A call into Box2D from anywhere else would change C's world after its image was taken, and a machine that then restored would have another world.
- **The image is in the match's hash, so it's the same bytes on every machine for the same state**, which Box2D doesn't promise by itself: its own determinism check is of bodies. The changes for that: `userData` as wide on 32-bit platforms, a layout hash that doesn't name the pointer's width, a tree's capacity as a restore would leave it, and a contact point's `normalVelocity` decided per contact, where upstream decides per block of 4 or 8 by the CPU's SIMD width (the same simulation, other bytes on an AVX2 machine than on the web).
- **The image is in sections that keep their place** (`b2World_GetSnapshotAt`, `place` in `bridge.c`): a table after its header says where each of 17 starts, and each stays where it was while the one before it leaves it between none and a quarter of itself to spare. Upstream's image is one run of bytes that starts with its parts of changing size, so a contact that starts or ends moved every byte after it. Where the sections go is part of the state: a restore takes it from the image's table. It's what makes a tick's image differ from the last where the world does, which is what the match's snapshots can share and what's hashed again.
- **A world at rest isn't stepped**: nothing awake, and nothing noted since the last stamp, and `b2t_step` returns that stamp, which tells the systems after it there's nothing to read (`Physics.moved`).
- **`Enter` and `Leave` are systems written in C** (`extern system`, see Language), the first to be: every body is looked at every tick, most ticks most have nothing written, and a system written in Tide copies each one out to look at it (and, taking it `mut`, compares and copies it for every entity once a snapshot shares the world's pages, which a client's do every tick). They go through the bodies' fields as arrays, and ask for the fields to write only once a body has something to write. What code relies on:
  - `Enter` (`b2t_enter`, `mut Body`, `mut Physics`) makes new bodies and syncs the ones code wrote, in the order of its rows: `mut Physics` keeps it on one thread, as everything done to C's world is noted into the stamp in that order (C doesn't touch the singleton). The bytes it notes of a body are the component's as a row has them (`tide_rows_get`), padding and all, as they were when Tide passed its copy.
  - **Whose each body is stays Tide's to write**, as it's a map: `Own` (per entity, `with Body`, no component) runs for the bodies `Enter` ran for, in its order, and asks C of each whether it was made (`b2t_made`, which only looks at the next one made; a tick that left one untaken stops the program at the next). It's per entity, and not a loop over what was made, on purpose: the match's heap frees what a map let go of after each entity a system runs for, so the map's blocks are where they were when `Enter` was written in Tide, and the match's hash with them. A loop gave another heap for the same map, and another hash.
  - `Leave` (`b2t_leave`, `mut Body`, `Physics`) writes where the step left the bodies it moved, 12 of a body's 22 fields. `b2t_step` notes those once, right after the step, from Box2D's move events (`note_left`: the bodies that were awake for it, each found by its index, with its speeds read for the ones still awake), so `Leave` asks Box2D nothing for them. A body with no such note wasn't awake: where its component says it's where the last step left it, and still, it's skipped unasked, and otherwise (code moved a body the step then left alone, or it just fell asleep) its component gets what Box2D has, asked for that body, so the next `Enter` finds nothing written and the world comes to rest. It splits across threads: each run reads the notes and writes its own rows.
  - Shapes that are on their body have a sparse tag and aren't visited.
- Its step runs on the tick's threads through jobs, once 2,048 bodies are awake, 4,096 on the web (`SHARED_BODIES`, measured: a tick whose C starts jobs runs its systems on threads too, so with fewer the whole tick was slower shared though the step was quicker; `b2t_share_from` lowers it for the test of threads); Box2D gives the same world on any number of workers. On the web it's Box2D's scalar path, as upstream only knows Emscripten's WebAssembly. Its workers there sleep when a wait for the next stage has gone on long, as upstream's pause and yield do nothing on the web (`b2t_stage_sleep`, `b2t_stage_wake`: see Box3D, which has the same change, and Web builds).
- `tide_box2d_stack` (`packages/box2d/test/`, a game of its own that lists `..`) pins the world's hash and a hash of every tick's world, the same in debug, release and on the web; goes on from a snapshot three times over; makes C's world from its image before every tick against one that never was; packs and unpacks a world with C's forgotten; ticks on threads against one; and says what a tick costs with everything moving, with one crate pushed and at rest (`box2d_costs`, which only checks that rest steps nothing). The library its tests share is built with `tide_flags`: without them clang fuses multiplies and adds on ARM, and Box2D steps another world there. A new Box2D steps differently, so its pins change with it, and so do games' matches.
- What it costs, on a release build, 2,400 crates (an image of 2.5 MB), with the world kept and hashed each tick: 0.6 ms a tick with everything moving (Box2D's step is 0.31 of it), 0.21 with one crate pushed, 0.017 at rest. The image goes into the match through `out List<byte>` (`b2t_image`): Box2D writes it once into room for a little more than the last one took, and the list is then exactly it. It was 1.4 with everything moving until pages a snapshot let go of were handed out again (see ECS and simulation state): most of what the package added to the step was the system's memory, a page fault for each 4 KiB of each chunk that changed. And 0.75 (0.26, and 0.031 at rest) until `Enter` and `Leave` were written in C: each body read back took 0.17 of it through a system written in Tide, a call, a copy and a `world.Set` for each, and takes 0.015 now; looking at each for what code wrote took 0.034, and 0.024 at rest, and takes 0.015 and 0.006; `Own` takes 0.009 to 0.012. What's left is the image written (0.14), compared and copied into the match's chunks, and the changed pages hashed.
- **What the tests say a tick costs leaves the measuring out** (`b2t_measure_blocks`' `took`): counting how much of the image changed keeps a copy of each and compares the next with it, inside the tick, which no match does.
- What the language still makes awkward: a package's extern functions are as public as its components.
- Box3D is the same package for 3D (below).

### Box3D

The Box2D package again, for Erin Catto's Box3D: `packages/box3d/`, namespace `Box3D`, its C functions `b3t_`, the same experiment on the same terms. Everything the Box2D section says of how a match holds the physics is so here too, as it's written there: the state in the match as an image and a stamp, the stamp as a hash of what was done, every change made by the package's systems from components, a world at rest not stepped, the step on the tick's threads through jobs, and the same six tests. Its page for users is `docs/physics/box3d.md`. What differs:

- **Its `Enter` and `Leave` are systems written in C too** (`b3t_enter`, `b3t_leave`), as the Box2D section says of its own, `Own` and `b3t_made` included. What a wider component asked for, a `Body` being 160 bytes in 40 lanes, of which `Enter` reads 34 and `Leave` writes 26:
  - The fields are found by where they are, not one by one: the 13 floats of a body's place and speeds (`PLACE`: its position, rotation, velocity and angular velocity) are side by side from `position` (`NOW`), the same 13 as the last step left them from `stepPosition` (`STEP`), and the 6 of its impulses between them (`PUSHES`), each an array of pointers a loop fills (`fields_of`, `places_of`). A `_Static_assert` on the offsets holds that, so a field that goes between them stops the build, not a match.
  - What `Enter` asks of every body is asked a field after another over a chunk's worth of rows, into a byte a body (`written`, `AT_ONCE`), which the C compiler runs with SIMD. A row at a time through 34 arrays, it took 0.014 ms at rest, and takes 0.006.
  - `Enter` asks for its arrays once and never again, though a row it writes (`tide_rows_set`) may give the match other memory for a field than what was read: a body is looked at before it's written and never after, and the rows not yet written are the same in both. Box2D's asks again after each write.
  - **`Leave` goes by what the step noted, and reads nothing else of a body**, where Box2D's looks at every body's fields. `b3t_step` notes, right after the step (`note_left`, into `lefts`, each body by its index): the bodies that were awake for it, with where each is and how fast (Box3D's move events, and its speeds asked there); the ones that fell asleep in it (the same events say), marked; and the ones `Enter` told Box3D something of (`synced`) that the step then left alone, a static body that code moved, marked too. `Leave` writes the first from the note, and asks Box3D for a marked one, unless its component says it's where the last step left it and still. Which step noted a body is apart from the note (`left_steps`, four bytes a body), and that with the two lanes of a body's id is all `Leave` reads of any other: 0.009 ms with one crate pushed among 2,400, where looking at each body's fields took 0.014 a field after another and 0.026 a row at a time.
  - **Passing the others by rests on Box3D**, and a new one has to be read for it again: every body that's awake for a step has a move event (`b3FinalizeBodies`, `solver.c`), one that leaves the awake set in a step has its event say so (`b3TrySleepIsland`, the only way out of it in a step), a body that isn't awake has no speed (`b3Body_GetLinearVelocity`), and nothing code writes reaches Box3D but through `Enter`. So a body the step notes nothing of is as the last step that noted it left it, which its component says since that tick's `Leave`. While it was built, every body passed by was also looked at as before (its fields against each other and against what Box3D has for it), through all of `tide_box3d_stack` and `tide_box3d_parts`, whose `yard.tide` does to sleeping and static bodies what the step doesn't: none had anything to write, and in four of those tests the marked ones were asked for 366 times and found at rest 18.
  - **Nothing it does to Box3D's world is new**: `sync_body` is what the Tide system called for each body (`b3t_body`), with the same calls, the same notes into the stamp and the same order, its rows', so the stamps, the images and which of them go in parts are what they were (23 and 265 written whole of the pinned match's 300, either way). What's new is asked, never done: the step's move events (`b3World_GetBodyEvents`) and a body's speeds. Bodies have no user data, and `Physics` and the components are as they were.
- `packages/box3d/box3d/src/` is Box3D at `e77352c` (3 October 2026, version 0.1, an alpha, MIT), laid out as Box2D's is, with the changes `box3d/TIDE.md` lists, each marked `Tide:`. There are more of them than Box2D needed, and Box3D is younger: an update is more work, and its pins change with it.
- **Box3D had no call to take an image or to restore one**: both were inside its recording. `b3World_GetSnapshotAt`, `b3World_Restore`, `b3GetSnapshotBases`, `b3GetSnapshotHead` and `b3World_GetSnapshotGeometry` (`world_snapshot.c`, `box3d.h`) are ours, around its own writer and reader, which its recordings still go through. A restore is in place, and leaves nothing of the world it was done to: the image's names replace the world's, and the last step's events go.
- **What a box is made of isn't in the image.** Box3D keeps a box as a hull, and its image names a hull, a mesh or a height field by a number, with the bytes kept elsewhere (upstream, in the recording). Here a world keeps them itself, each once, in the order its images first named them (`b3SnapGeometry`), and they're in the match as a second list, `Physics.geometry`, beside `Physics.image`. Not in the image, as they're the part of the state that almost never changes: the list is written when a shape of new geometry is made (`b3t_geometry`, when its size isn't the list's), and it's only ever added to, so no byte of it moves and a tick's image has none of it. A restore takes both (`b3t_restore`). It's the same bytes everywhere because images are taken of the same worlds at the same ticks. Geometry no shape has any more stays, and a world with a compound has no image (a compound's bytes hold pointers).
- **The same bytes on every machine took more.** Pointers of 8 bytes in a body, a joint, a shape and a contact; a shape's geometry written in the 32 bytes it takes in the shape; zeros for every byte of a struct that no field owns, at offsets a `_Static_assert` checks on each platform (they were zeros already in the tests, which the image doesn't rest on); a layout hash that doesn't name the pointer's width. And two that weren't layout:
  - `b3MinW4`, `b3MaxW4` and `b3SymClampW4` gave another of 0 and -0 on each of the scalar, SSE2 and Neon paths, so friction clamped to nothing left -0 on the web and 0 on x64: the same simulation, one byte of a manifold apart. All three are SSE2's now (`simd_scalar.h`, `simd_neon.h`).
  - Box3D's lock does nothing on a platform it doesn't know, and it only knows Emscripten's web: on ours, with threads, two workers took the same manifold and a world stepped on threads was another than on one. It's a lock that spins now (`timer.c`).
- **Every shape and every contact takes the same room in the image**, beside its sections keeping their place (17, as Box2D's): the shapes together and then the few material arrays, the contacts together and then a manifold each, zeros for a contact that has none. Upstream writes what a shape or a contact owns right after it, so a contact that started touching moved every one after it.
- **An image is written as what changed of the last one, where Box3D can say** (`b3World_GetSnapshotParts`, `world_snapshot.c`; `b3t_image`, `bridge.c`), so what the package adds to a tick goes by what's awake, where the image written whole goes by how big the world is. The match's list keeps the rest (`tide_list_out_keep`, `tide_list_out_part`: see Language), and C keeps no copy of the image. **The image the parts make is, byte for byte, the image written whole**, which is in the match's hash and what a player who joins makes their world from: the pins of `tide_box3d_stack` are of images written both ways. How:
  - One writer writes both (`b3SerializeWorld`): a body, a shape or a contact is written by the same lines either way, as a run of them that's all of them or a stretch that may have changed (`b3SerBodyRun` and the like), and what it appends goes into the image or into parts of the world's own (`b3RecBuffer.parts`). So there's no second description of the image to fall out of step with the first.
  - **Which bodies, shapes and contacts may have changed** is three sets of bits in the world (`b3SnapTrack`, `physics_world.h`). One has changed between two images only if its body was awake at the first, at the second or between, as the step writes those on its worker threads and nothing says which (so everything awake goes in when an image is taken, `b3SnapCommit`, and again at the next, `b3SnapSeed`); or if it was written from outside the step's workers, which is said where it's done (`b3SnapTouchBody` and the like, each marked `Tide:`): a contact that starts or ends changes the lists of both its bodies and its neighbors in them, the floor's too; an element taken out of an array moves the last into its place (from the disabled set, that's any contact between two sleeping bodies); a body that wakes or falls asleep; and what a few calls do to a body that may be asleep or static (made, destroyed, moved, a shape added). They all run on one thread. `box3d/TIDE.md` lists them.
  - **A call nobody looked at writes the next image whole, and can't make a wrong one**: every call that changes a world goes through Box3D's recording macros, which now say which call it is (`b3SnapNoteOp`), and only the ones whose writes are followed are let through (the step, making and destroying a body, its transform, speeds, forces and impulses, and making a sphere, a capsule or a hull). A body's type, joints, shapes' settings and whatever a new Box3D adds cost one whole image. So do a restore, a world with more bodies, shapes or contacts than its last image had room for, a section that has to move (`place`), and a world with more than half of its bodies awake (`B3_SNAP_AWAKE_SHARE`), where the image written whole costs no more.
  - The other sections are written whole, the big ones (a solver set's bodies, a tree's nodes) as parts that point at Box3D's own arrays, which the list compares where they are: no copy. The sleeping sets and the pairs are left out when nothing was done to them, which is the choice for the sleeping sets: nothing writes one but a handful of places that say so (`b3SnapTouchSleepingSet`), and giving each set room of its own would have changed the image's bytes, and the pins with them.
  - `b3t_check` has every image in parts compared with the image written whole (`b3World_CheckSnapshotAt`, which the world doesn't take for its last image), and the program ends at the first byte apart, saying which section, and which body, shape or contact. It's on in the package's tests but the timed ones.
  - `tide_box3d_parts` (`packages/box3d/test/parts_test.c`) is the tests of it. A match of its own, `yard.tide`, so that the first keeps its pins, does to sleeping and static bodies what the step doesn't (one moved, destroyed, given a shape, a speed, a turn; a static body that comes and goes; a ball that passes sleeping crates without touching; one island waking another): with images in parts whenever and as a match has them, against a world made from its image before every tick (so the list's own bytes), through rollbacks, and with the step shared out over threads (`b3t_share_from`). And Box3D by itself, with whatever a game might call at random, joints, sensors, meshes, height fields and restores among them, a mesh made late in places that others left, and a recording taken meanwhile, which replays.
  - Taking each of the lines that say something changed out of Box3D in turn, and running `tide_box3d_parts`, says which the tests would notice the lack of: 36 of 60 by themselves. The other 24 say again what another line says or what being awake says (waking, falling asleep, an element moved within the awake set, a sleeping set that's destroyed right after it loses a contact), on purpose: four such pairs taken out together were noticed, and the rest weren't tried together.
  - What it found beside: `b3Body_SetAwake(false)` right after a restore reads the last step's events, which the restore cleared (an assert in debug); and upstream's `b3Body_SetType` leaves the world locked for a body with a height field. The package calls neither, `box3d/TIDE.md` says both, and neither is fixed.
  - Not done: a section of the image that moves has all of it written again, as before (one image in twenty with one crate pushed among 2,400: the awake set grows or shrinks as a stack wakes or falls asleep, and the sleeping sets after it move). Where the sections go is in the image, so another way of placing them is other bytes and other pins.
- Its shapes are `Box`, `Sphere` and `Capsule` (along its body's y, `height` from end to end, as Unity's), with density in kilograms a cubic meter, 1000 unless a shape says. A body's `rotation` is a quaternion, and one that isn't of length 1 is made so on its way in.
- Its step is shared out once 512 bodies are awake (`SHARED_BODIES`), where Box2D's, a far smaller step, is at 2,048: the step alone is quicker shared from a couple of hundred, but a tick whose C starts jobs runs its systems on threads too, which costs more than that saves below about 500.
- `tide_box3d_stack` is `tide_box2d_stack` in 3D, with one thing more: its pinned match runs twice, as the CPU solves contacts (8 at a time with AVX2) and 4 at a time (`b3t_narrow`), and a web build is the third way. The first of the two has its images in parts whenever they can be (277 of 300) and the second as a match has them, whole while most of it is awake (35 of 300): the same pins. Its pins are the same in debug and release, for MinGW, and on the web in both.
- ARM runs it on CI's Macs, whose Neon path gives the pins x64 and the web do. Nothing here runs it on Android's arm64, which builds.
- What it costs, on a release build, 2,400 crates (an image of 3.5 MB, and 1.4 KB of geometry), with the world kept and hashed each tick: 1.44 ms a tick with everything moving (Box3D's step is 1.0 of it), 0.10 with one crate pushed, 0.017 at rest (2.6 and 0.6 before spare pages, as Box2D's above, and 0.37 with one crate pushed before the image was written in parts). It was 1.70, 0.17 and 0.039 until `Enter` and `Leave` were written in C: each body read back took 0.29 of it with everything moving through a system written in Tide, a call, a copy and a `world.Set` for each, and takes 0.04 (0.060 and 0.009 with one crate pushed); looking at each for what code wrote took 0.045, and 0.033 at rest, and takes 0.020 and 0.006; `Own` takes 0.009 to 0.013. With one crate pushed the image is 0.02 ms to write and 0.02 to put in the match, where it was 0.17 and 0.07; with everything moving it's written whole as it was, a little quicker (0.17 from 0.21: the islands are written into room asked for once, `b3SerIslands`). What's left of a tick with little moving is spread thin: the step (0.03), the image (0.04), the bodies in and out (0.03: `Enter` 0.007, `Own` 0.009, `Leave` 0.009), and the hash of the world, which is of every 16 KiB of the image that has a byte changed (a tenth of it with one crate moving: 0.09 ms, outside the tick). With everything moving, about 0.016 of `Leave`'s 0.04 is asking for its 26 lanes to write (timed around the asking): each is a page a snapshot shares, so the table takes one of its own and the lane is copied into it, and every row of it is then written over. A run that writes every row has no way to say so: `tide/rows.h` has no lane asked for to write only. On the web it has no SIMD, as upstream only knows Emscripten's, and the same step is about 2.2 ms on one thread.
- **On the web, the solver's workers sleep when a wait for the next stage has gone on long, in Box2D's as in this one** (`solver.c`, marked `Tide:`, through the bridge's `b3t_stage_sleep` and `b3t_stage_wake`, which are `tide_job_sleep` and `tide_job_wake`: see Language, jobs, and Web builds). A step's workers wait for each stage in a loop, which upstream gives the CPU's pause and, every few rounds, the system's yield; the web has neither, so with a worker on every processor a page has, the system took one from a worker with a block to run whatever else the machine had, and the stage waited a time slice for it: a shared step took 1.9 ms or more on that page's 24 threads against 0.7 on 12 (measured under Node, 12 cores of two threads each), and 5.5 with four other busy threads on the machine. After 4096 rounds of the wait (`B3_TIDE_WAIT_ROUNDS`, about what waking a worker takes, so the waits between stages go as they did: at a tenth of that a step on 12 threads was a quarter slower, and ten times as many changed nothing), a worker sleeps until the main thread gives the next stage, which frees its processor: 0.85 ms on 24, busy machine or not. On a page's own thread it can't, and goes on with its loop. A hint to the CPU instead (`Atomics.pause`) changed nothing. What's left is the count's own: the solvers gain nothing from a core's second thread (on a pool of 24, 0.76 ms with 8 workers, 0.71 with 12 or 16, 0.85 with 24), so 12 are still quicker than 24, Box2D's step by more (0.34 against 0.54) as its stages are shorter. The solvers keep a worker for each of the tick's threads all the same (decided 2026-10-05, with the pool's count: see Web builds).

### Hot reloading

It's for quick iteration, and only under `tide run`, native and web: `tide build` output has none of it.

- `tide run` builds the game as a library (`game-<n>.dll`, `.so` or `.dylib`) and a small host that loads it (`tide_host_run_library`, in `platform/src/reload.c`). tide watches the game's `.tide` files, and its C and C++ files, headers and libraries, and builds again once a change has settled. The game's C is part of its library, so the state C keeps starts over at each reload, and C++ globals are constructed again. Each build is linked under another name and renamed into place when it's whole; between two frames, the host swaps in the newest.
- A build with the same data layout keeps the match and the local state where they are (`tide_session_set_game`). The layout is `tide_game`'s hash: the generated header but for its first line.
- A build with another layout gets the match and the local state carried over by name (`tide/migrate.h`, `tide_session_migrate`). Keep as much state as possible, and when a big change breaks it, starting over is fine. No attribute for renamed fields, like Unity's `[FormerlySerializedAs]`, and no save files. The rules:
  - Fields of the same name keep their values. `int` to `float` or `long` and int vectors to float vectors of the same size convert, as Tide converts them implicitly, and so does `long` to `float`; enums keep their member by name. Other fields, and new ones, get their declared default; new text and lists start empty. A changed default doesn't touch existing values.
  - Entities keep their IDs. Without a removed component, an entity goes to the storage for the rest of its components. It's dropped when there's none.
  - A world whose scene is gone starts over.
  - Local fields carry over with the local state: a component's as rows of a type of their own, "<Component> local" (`tide_layout_world.attached`), field by field, and a singleton's as the local singleton they are.
  - The host says what didn't carry over: fields reset and entities dropped.
- tidec describes a game's layout for this only when asked (`--layout`, `codegen_options.layout`, `tide_add_game(... LAYOUT)`): `tide_game_layout` in the generated `.c`, not the header, so `tide_game`'s hash doesn't change. The migration is in the platform layer's static library (`platform/src/migrate.c`), so only programs that call it link it.
- In a match, the server's machine carries its world over, and its own player takes that world. A client of another machine carries its last verified world over, and the server sends what it lacks if it comes out different. Inputs sent for ticks to come are dropped: players' last inputs stand in until new ones arrive.
- A waiting task carries over to a build where its code and its frame's layout are the same: each table of tasks in `tide_game_layout` is named with a fingerprint of both, and the header says each one's code, so a change to async code changes the layout. Other waiting tasks are dropped, and the host says how many. A world's task order and the local world's frame count go on.
- A build that fails leaves the game running its last one. `r` and Enter in tide's terminal starts the game over (through a `restart` file in the run's folder). The host says what each reload did, so under `tide run` it's a console program even with `--release`.
- A game started with `--join` or `--connect` joins again a second after its match ends without it leaving: when the server starts over, or still runs an older layout.
- Each run has its own folder, `.tide/<configuration>/run/<tide's process ID>`, so a server and a client run from one folder never build over each other. It keeps the last two builds, and it's deleted when the run ends, or by a later run once its tide is gone.
- A game's library has its own copy of the engine code it uses. So everything the host and the library share is data: worlds and local state (with their pages, from the C library's heap, which every build of the game shares), devices, the draw list and the GUI. Render targets are what a library keeps track of itself, so the new build takes over those the local state holds (`tide_host_game.rebind_resources`, the generated `tide_local_rebind_resources`). The library frees its scratch area and what's left of its targets' bookkeeping before it's unloaded (`tide_host_game.unload`).
- On Linux, a library's objects are compiled with `-fPIC`. The engine's are kept apart in `engine-pic`, so running and building don't rebuild each other's.
- On the web, each build is a WebAssembly program of its own. `tide run --web` serves the page on 127.0.0.1 (`compiler/cli/serve.c`), opens it (unless `--no-open`), and keeps running until it's stopped. The editors run it with `--no-open` and show the page themselves, at the address tide prints (`tide: the game is at ...`): VS Code's **Tide: Run on the Web** in its browser, and the JetBrains plugin's Tide run configurations in the Tide Game tool window. The page asks tide for the newest build 4 times a second (`/build`: the build and restart numbers; `/game-<n>.wasm`).
- The page starts each new build in the running one's place (`platform/web/tide.js`, between its `tide run` markers): it asks the running one for its state (`tide_reload_save`), deletes what it made in WebGL or WebGPU, and starts the new one, which carries that state over (`tide_host_run_web` in `platform/src/reload.c`). The state is the old layout, packed with offsets for pointers (`tide_layout_pack`), the server's world and the local state as bytes (`tide_world_pack`, `tide_local_pack`), the GUI, and what the host keeps of its own: whether the stats' drawer is open. The new session goes on from the world with this machine's player in it already (`tide_session_start_from`), so there's no second `PlayerJoined`. A room closes at a reload, for now: the new build goes on with the match closed, and the other players drop out.
- Pages made to ship (`tide build --web`, `cmake/web_page.mjs`) leave out the lines between tide.js's `tide run` markers, and web programs only link reload code when tide run's `main.c` calls it.

## Layout

- `engine/`: the engine library (`tide`). Public headers go in `engine/include/tide/`, sources in `engine/src/`. New `.c` files are picked up automatically.
- `compiler/`: `tidec`, the Tide transpiler (owned by Claude). `compiler/tests/e2e/` holds programs compiled and run as tests. `compiler/tests/errors/` holds programs that must fail with the message on their first line (and say each `// expect:` line right after it, an error's note), and `compiler/tests/warnings/` programs that must compile with as many warnings as their first line says, and the texts on their `// expect:` lines (warnings' and notes'). `compiler/tests/shaders/` pins the GLSL and WGSL tidec writes for a program's frags and verts (`tidec --shaders`), as `compiler/tests/schedule/` pins a schedule. A test's packages are folders named as the packages are: `errors/<name>/<Package>/*.tide`, and `<name>/<Package>/*.tide` beside a schedule's, a shaders' or a warnings' `<name>.tide`. `compiler/tests/scale/` makes up a big game of many namespaces at test time, which tidec has to compile within a generous time: codegen names every declaration once (`name_program`), as a compile that made each name again at every use grew with the game's size squared. tidec reads files with Windows line endings (CRLF) exactly as LF ones: `e2e/crlf.tide` and `errors/*_crlf.tide` test it, and `.gitattributes` keeps them CRLF on every checkout.
- `compiler/cli/`: `tide`, the command users run (owned by Claude; see Packaging and releases). `compiler/cli/tests/` tests what it can without a network or a compiler: versions and releases, upgrades (see Packaging and releases), packages, which platform a library is for, apps and bundles and their RSA signatures, zips, `tide editors`, and `tide publish` against the build service run on this machine (`publish_test.mjs`, `tide_cli_publish`: see Modding). `cpp_test.cmake` there builds games with C++ and checks what tide says when one can't build, so it needs a tide that builds games: CI runs it on the package it made (`cmake -DTIDE=<tide> -DWORK=<folder> -P compiler/cli/tests/cpp_test.cmake`).
- `compiler/lsp/`: `tidels`, the Tide language server (owned by Claude). It reuses tidec's front end, with error recovery, to give editors completion, diagnostics, quick fixes (the checker's "did you mean" suggestions among them, as data: `diag_set_suggestion_sink`), hovers, go to definition, type definition and implementation, find usages, highlights, rename, the call hierarchy, formatting (of a range too), parameter hints, inlay hints, code lenses (each system's stage and waits, and what each local handler of a match event hears), the outline, workspace symbols, folding, selection ranges, semantic highlighting, and moving a declaration to a file of its own. It watches the game's files through the editor (dynamic registration), so files changed outside it are seen. It reads ahead of the message it handles (`compiler/lsp/main.c`), since an editor sends a change at every key and a big game takes a while to analyse: changes that arrived together are analysed once, as the last left the text, when a request needs them or nothing more has arrived (`lsp_settle`), and a request that a later message cancels (`$/cancelRequest`) is answered as cancelled without its work (`lsp_handle_ahead`). Nothing there is timed. Native builds only.
- `tools/`: editor support. `tide-vscode` is the VS Code extension and `tide-jetbrains` the JetBrains plugin: each is the grammar, a client that runs `tidels`, and running the game with `tide run`, natively, on the web or on Android. `tide-syntax` is the TextMate grammar they both include, which the package also ships as a bundle for other editors. An editor feature goes to every integration that can have it, each in its own editor's way.
- `docs/`: the docs site (see Docs site). `docs/spec.md` is the language spec; `guide/`, `game/`, `physics/`, `multiplayer/`, `language/`, `tools/` and `c/` are the pages for users, written from it and from this file (see Docs site for what goes where).
- `platform/`: the platform layer (`tide_platform`): window, frame loop, input devices and the renderer (see Rendering and platform), and rooms (`src/rooms.c`, with desktop WebRTC in `src/rtc/`), and runs with no window (`src/script.c`, `src/png.c`). Public headers in `platform/include/tide/`: `platform.h`, and the hosts' `run.h`, `host.h` and `migrate.h`. `desktop/`, `web/` and `android/` hold what's each one's own: its window (`src/window.h`) and, on the web, the page (`tide.js`) and the WebGPU backend; `font/` holds the font text is drawn in, and `third_party/` what's vendored (`stb_truetype.h`).
- `demo/`: a small game on the platform layer. `demo.tide` is the simulation and the views that draw it, and `main.c` is the host. It builds as `demo.html` on the web.
- `sandbox/`: the owner's experiments: a game with no C, built by `tide_add_game`.
- `bench/`: benchmarks, games played by bots on one machine (see Benchmarks).
- `packages/`: the packages that come with tide (see Packaging and releases), a folder each, named as a game's `tide.packages` names it, with a `tide.packages` of its own that says `package Name`. They install into the package as they are, in `src/packages/`, but for what's this repo's own: `packages/CMakeLists.txt`, which builds their tests the way tide would build the package, and each one's `test/`. `box2d` and `box3d` are the two so far (see Box2D and Box3D, under Packaging and releases).
- `relay/`: the relay, which introduces players in rooms (see Networking): Node, with a WebSocket server of its own and no dependencies. It runs on Fly.io as `purrengine-relay`, one machine in `fra` (`relay/fly.toml`; deploy with `fly deploy --ha=false` from `relay/`). Games reach it as `wss://relay.tide-engine.dev`, a CNAME to the Fly app in the domain's DNS on Cloudflare, so it can move without them changing: `platform/src/rooms.c` connects there unless `TIDE_RELAY` says otherwise, and `platform/web/tide.js` unless the page's `Tide.relay` does. All of a relay's time comes from its `clock` (`createRelay`'s option: `now` and `wait`), never from `Date.now()` or a timer of its own: the system's is a clock that only goes forward, as the time of day gets set back (WSL's by seconds at a time under load, which is how a room's hold outlasted a test's sleep), and its tests (`relay/relay.test.mjs`) bring one that only moves when a test says (`clock.pass`), with what the relay does when its time is up done inside that call. So no test there sleeps until a time must have passed: what a test waits for, it asks the relay's own state about (`until`).

It's reached as `https://builds.tide-engine.dev`, a CNAME to the Fly app in the domain's DNS on Cloudflare, as the relay's name is: `tide publish` sends there unless `TIDE_BUILDS_URL` says otherwise.

- `.github/workflows/`, `.releaserc.json`, `install.ps1`, `install.sh`: releases and installing (see Packaging and releases), and the docs site.
- `cmake/`: shared compiler flags (`TideFlags.cmake`), the package (`package.cmake`), the file that locates clang (`clang-toolchain.cmake`), the web, MinGW and Android toolchains (`wasi-toolchain.cmake`, `mingw-toolchain.cmake`, `android-toolchain.cmake`), tide's built-in clang (`LLVM.cmake`), `tide_add_game` (`Tide.cmake`), the GLFW download (`GLFW.cmake`), files as C arrays (`embed.cmake`), and `tide_add_web_test` (`WebTest.cmake`), which runs a web page in headless Chrome or Edge as a test, and with `WEBGPU`, again on WebGPU.

GLFW has no touch, so other desktops have none yet.
  - A finger keeps its slot while it touches, and once it lifted, until a sample cleared it (`tide_devices_consume`), so the next sample reads a tap that came and went between two. No finger is left out for that: one that touches with no slot free takes the slot of the finger that lifted longest ago (`free_slot` in `engine/src/devices.c`, by `tide_touch.rested`, the polls since it lifted, so a finger that lifted in the same poll is the last to go), whose lift the next sample then doesn't see. That's every touch past the tenth in a host that never consumes: a touchscreen stopped answering after ten taps in a game with no input and outside a match, before the standard host cleared the devices there itself. A finger is only left out while ten still touch. `devices_fingers_keep_coming_where_nothing_samples` and its neighbors in `tests/test_devices.c` check the slots, `gui_buttons_answer_every_tap_where_nothing_samples` in `tests/test_gui.c` the GUI's buttons, and `platform/tests/web_touch.c` ends with 25 taps that nothing samples.
  - The pointer (`tide_pointer_poll`) follows the mouse or the primary touch, whichever was used last, as Unity's `Pointer.current`, and the GUI follows the pointer. A host that fills the devices itself calls it, or the GUI sees no mouse.
  - The cursor's lock (`Cursor.Lock()`, `Cursor.locked`) is asked for frame by frame and read back, never assumed (agreed). The GUI collects the frame's ask (`tide_gui_lock_cursor`, as `GUI.ShowKeyboard`'s), a host passes it on every frame (`tide_platform_cursor_lock(tide_gui_cursor_lock(gui))`), and the next poll says whether the window holds the cursor: `tide_devices.mouse.locked`, platform state like `poll_delta`, which `Cursor.locked` reads (the match never: `tide_keep_devices` leaves it zero). There's no unlock: a frame that doesn't ask lets the cursor go. While it's locked, the window says the position it had when it was locked, and what the mouse itself moved (`tide_window_mouse.moved_x`, `moved_y`), which is the delta; a mouse whose cursor is locked is on no widget (`cursor_hidden` in `engine/src/gui.c`), so nothing hovers, a click is the game's, and a button still held as the cursor comes back presses nothing. A finger isn't the mouse, and still presses what it touches. What each system does is its own, and none of it is worked around with a timer:
    - The web (`platform/web/tide.js`): a browser only gives the lock when it's asked from a click or a key press, so the page asks at the next one on the canvas while the game wants it, and at once when the game starts wanting it if one still counts (`navigator.userActivation`), as after a Resume button's click. The browser takes the lock back when the player presses Escape, which the page can't prevent and may never see the key of (so Escape never asks, nor a held key's repeats), and when the page loses the focus or is hidden, and for a moment after Escape it refuses. The page says what the browser says (`pointerlockchange`, `pointerlockerror`) and never asks again on its own: a lock refused or taken back waits for the next click or key press. It asks for the mouse's own movement (`unadjustedMovement`), and for the usual kind where the system has none. Locked, movement is the events' `movementX` and `movementY`, as positions stop changing. A hot reload keeps the canvas and the page's state, so the new build reads it. `tide_platform_web_cursor` stands in for the browser, which gives a script's events no lock, and checks all of this.
    - Desktop (`platform/desktop/glfw.c`): GLFW's disabled cursor, with raw motion where the system supports it. Only a window with the focus holds the cursor: Alt+Tab lets it go (`Cursor.locked` is false meanwhile), and coming back takes it again while the game still asks (`follow_lock`, at every poll and every ask). Escape gives the cursor back to the player, as a browser does (agreed), though the game still asks and still gets the key: the player's next click on the window, or press of another key (not one still held, repeating), takes it again, and Escape never does. A game that stops asking starts over, so one whose Escape is its pause menu holds the cursor at once when it asks again (Resume, or Escape once more): a browser's wait for a click isn't copied. When the window holds the cursor is `platform/desktop/cursor.h`, apart from GLFW, so `tide_platform_cursor_rules` checks it with no window. A test's window is hidden and never has the focus, so `tide_platform_cursor` (label `gpu`) only checks that side; nothing checks GLFW's part of a held lock without taking the screen and the mouse.
    - Android never locks it, yet: NativeActivity has no view to capture the pointer with.
  - Phones show their keyboard while the player types into the GUI, or into what a view said shows it, `GUI.ShowKeyboard()` (`tide_platform_typing(tide_gui_typing(gui))`, once a frame). On the web, the page focuses a hidden field of its own, whose input comes as characters typed and its deletions as Backspace, as phones' keyboards say no key positions (`platform/tests/web_keys.c`). On Android, NativeActivity's view can't take the focus, so the window's view takes it, on Android's main thread, which the program reaches through a pipe on that thread's looper; the keyboard's keys still come to the input queue, and Java's `KeyEvent` says the character each types.
  - Pixels (the window's size, the mouse, what's drawn) are the display's logical pixels, as a browser's CSS pixels are, and rendering is at the display's full resolution: on desktop the window's framebuffer, as many times its logical size as GLFW says its contents are scaled (`GLFW_SCALE_TO_MONITOR`), and on the web a canvas `devicePixelRatio` times its CSS size. Render targets are the same: sized in logical pixels, with the display's pixels in each unless they say otherwise (see Rendering and platform).
  - `tide_platform_run` never returns (on the web, the browser drives the frames), so hosts do all their work in the frame function.

## Language

The language shares the engine's name, Tide. Its syntax and semantics are specified in `docs/spec.md`. The docs site explains it to users: a change to the language, `tide` or the editors updates the site's pages too (the folders of `docs/` beside `spec.md`).

- Derive as much as possible from the language.
- It should be as explicit as our needs require, while staying friendly.
- Dependency trees are static: known at compile time, not discovered at runtime.
- Named ordering phases are ordinary enum members. `[Stage(Stages.Objects[, offset])]` assigns a system, view or event handler to one phase; the offset is a constant int, 0 when left out, and orders only within that phase. The enum's declaration order decides the phases' order, not its members' values. `[Before]` and `[After]` take whole phases as well as declarations. Systems, views and each event's handlers are scheduled apart; a system in a later phase waits for every system of the earlier ones, even with no data between them, and empty phases keep their place.
- Explicit is the default. Systems declare which components they read and write in their signatures.
- Ordinary functions and methods can take explicit singleton parameters, with the same read-only copy and `mut` caller-variable rules as components. They gain no implicit singleton lookup, ECS binding or world access. Caller capabilities remain decisive through helper chains: match systems and handlers write match state, views read the match and write local state, and `Sample` stays read-only; helper reads and writes remain part of access analysis and scheduling. Only ordinary function helpers carry a bound component's or singleton's local fields; plain copies and methods have none. Match code can't call local-field helpers, local code can't call match-writing helpers, and a helper can't do both through the same parameter. Engine-owned singleton instances stay read-only, and passing `Session` grants no session operations. Singleton returns stay unsupported, as do the existing unsupported copies and resource arguments; this adds no extern ABI. World access is a `World` parameter's, which a function's caller passes its own (below).
- A system's access (which components it reads or writes) is declared separately from its filters (which components an entity must have or lack). Filters don't create data dependencies.
- The language is built around the ECS. It should use syntax sugar to hide the ECS's pain points.
- When nothing else decides a convention (names, axes, units, orderings), follow Unity: Unity.Mathematics for math, the Input System for input. Tide's own rules, such as PascalCase methods, still win.
- Games call C through `extern` functions, and C is trusted: what it does (determinism, state outside the world, thread safety) is the game's responsibility. The language adds no markers or checks for it, and the compiler takes a C call as touching nothing it tracks. tidec declares each one in the generated `.c` from its signature, never in the header (which would change `tide_game`'s hash) and never by including the library's header. Calls to C, and to functions and methods that call it (`decl.calls_c`), are side effects that codegen keeps in source order, as it does spawns. C makes no system wait, and systems that call it split across threads like any other: what C does on several threads at once is the game's to get right.
- An extern function's `out List<T>` is a list C makes (built for C that fills big lists, like Box2D's image, without a copy of what they held; Provisional: its C API awaits the owner, `docs/spec.md`, C functions). It's an `out` parameter like any other (below) to everything but C. What's built, and what code relies on:
  - `out` is a word before a type and a name in a routine's parameters, parsed as `in` is (`parse_routine_params` in `compiler/src/parser.c`), and a name anywhere else. The parameter is `PARAM_MUT` with `param.is_out`, so to the schedule, evaluation order and generated code it's a `mut` list the call changes, with no code of its own; only what C gets differs. The call says `out` (`WriteImage(out physics.image)`), as for every `out` parameter.
  - C gets a `tide_list_out *` (`tide/list.h`). `tide_list_out_room(out, count)` is memory for `count` elements, with whatever was there in it, from the buffer the engine keeps between calls (`flat_take` in `engine/src/list.c`, see ECS and simulation state), so a call every tick allocates nothing; asking again gives the buffer back and takes one for the new count. `tide_list_out_count(out, count)` says how many of them the list gets, at most the room: none when it's never called.
  - tidec calls an extern that takes lists through a wrapper (`gen_extern_lists`, `tide_c_<name>`), which takes an `out` list by address with its `where` after it (`place_where` at the call, as a list's methods get it: an empty list's handle doesn't say whose heap it's in) and brackets the call with `tide_list_out_begin` and `tide_list_out_end`. The end makes the list exactly what C said: it takes elements off (`cut`) or makes room (`reserve`), then writes run by run, only where the bytes differ (`put_elements`), so chunks that come out the same stay shared with the world's snapshots and keep their hashes. A list that borrows another's block gets one of its own. No copy of what the list held is ever made.
  - C that knows which elements changed says only those (built for Box3D's image, of which a tick changes a few records; Provisional with the rest). `tide_list_out_keep(out, count)`: the list keeps what it holds and is `count` long, zeros where it grows. `tide_list_out_part(out, first, elements, count)`: these elements go over the ones from `first` on. The parts are kept in the `tide_list_out` (an array from `flat_take` too) and written by `tide_list_out_end`, each compared with the elements it goes over (`put_elements_at`: a part that starts a chunk makes a shared one the list's own without copying what it's about to write, `tide_heap_write_over`; one in the middle copies the chunk). So what a call costs goes by what C gave, never by the list: nothing else of it is read. A part's elements are C's memory, read after C returned, so never the function's own variables, and nothing may change them meanwhile. Of `keep` and `room`, what C said last stands, so C that finds too much changed asks for room and fills it. Generated code is as it was: `tide_list_out` grew, and tidec only names the type.
  - A program with no `out` generates the C it did, byte for byte: checked by running old and new tidec over every game's source list.
  - `compiler/tests/e2e/lists_out` checks it in the match, the local world and locals, and `tests/test_list.c` the runtime's part, natively and on the web (`list_out_keeps_what_it_holds` for parts: which chunks become the list's own, growing, shrinking, the scratch area, a list that names another's).
- C that shares its own work out does it on the tick's threads, through jobs (agreed 2026-10-05; `tide/jobs.h`, `engine/src/jobs.c`): `tide_job_start(work, context)` hands a task to another thread and returns at once, and `tide_job_wait` returns once it ran. It's what a library with a task interface of its own needs (Box2D's solver starts its workers and then works beside them), which `tide_parallel_for`, a loop that returns once it's done, can't serve. How:
  - A job is a slot in the running tick (`task_slot`, 64 of them), which a thread with nothing else takes before loops and systems (`help_task`). One nobody took by the time it's waited for runs in the wait, so each runs exactly once whatever the threads do; with no other thread (a tick on one thread, no pool, code outside a tick) it runs inside `tide_job_start`, which returns 0.
  - tidec can't tell how much work C is, so a tick whose C started jobs runs on threads the next time whatever its systems look like (`tasks_wanted`), until a tick that had threads to use starts none. So C with little to do starts none: Box2D's bridge only shares a step out past a number of bodies awake.
  - `tide_job_threads` is how many threads the tick can have at work, in a tick that runs on one too, for a library that sizes its workers once.
  - Jobs have to come out the same however many threads take them, as everything C does on threads: that's the caller's to get right.
  - Jobs that wait for each other inside their work, as a solver's workers wait for each stage it gives them, wait in a loop, since such a wait is mostly shorter than a sleep and a wake. On the web a loop holds its processor for as long as it goes on (see Web builds), so for a wait that has gone on long there's `tide_job_sleep(word, seen)`, which sleeps until `tide_job_wake(word)` unless the 4 bytes at `word` aren't `seen` any more, and `tide_job_wake(word)`, which whoever changes the word calls after, for a comparison while nobody sleeps (Provisional: the names and the shape are Claude's, built for Box2D and Box3D, and await the owner). It sleeps on a thread of a pool whose threads can, in a tick (`may_sleep` in `engine/src/jobs.c`, said where a thread can leave a tick); on a page's own thread, which can't, and everywhere but the web, where the pause and the yield are there for the wait, it returns false at once and the caller goes on with its loop. How long a wait is before it sleeps is the caller's: about as long as a wake takes, or every wait pays for one.
  - `tide_platform_jobs` (`platform/tests/jobs_tasks.c`, a C function `jobs.tide` calls) checks each ran once, with the same world as on one thread, and that other threads took some, and that work in stages whose workers sleep between them comes out the same; `tide_platform_web_threads` runs the same game in a browser.
  - `tide_task` is the async tasks' type in generated C, so these are jobs.
- A system can be written in C: `extern system Move(mut Position position, Velocity velocity, Time time, without Frozen);`, whose C function is handed its entities' components as the arrays the match keeps them in, where an extern function gets one entity's at a time (the owner approved the direction, 2026-10-05: "in a way that lets others use this too for their own situations"; Provisional: the syntax, the semantics and the C API are Claude's picks, in `docs/spec.md`, C functions). What's built, and what code relies on:
  - It's a `DECL_SYSTEM` with `decl.extern_system`, no body (`body` is NULL, as an extern function's) and a `c_name`, from `[NativeName]` or its own name (`parse_extern_system` in `compiler/src/parser.c`, `check_extern_system` and `check_extern_c_name` in `check.c`). Everything that goes by a system's signature takes it as that system: `check_params`, the schedule (`compiler/src/parallel.c`: what it takes `mut` is written, the rest read), `system_splits`, `[Stage]`, `[Before]` and `[After]`, the language server. Nothing warns about access it doesn't use, and `tidec --schedule` and the lens say `in C`. Code that walks a system's body has to stand a NULL one.
  - v1 takes components (read or `mut`), `with` and `without`, and singletons (read or `mut`). Errors that say what to write instead: a sparse component or a filter by one (`check_extern_sparse`, once the archetypes are derived, which is when a tag's sparseness is known), the `World`, a query, `Devices`, the input, an `Entity` parameter, a component with no fields. A component or singleton that holds text or lists is allowed: its handles are C's to leave alone.
  - C is called once for each run of rows, a chunk of an archetype the filters admit or the task's piece of one, never with none, in the order a Tide system goes through them on one thread: `void name(tide_rows *, <singletons, each by address, in order>)`, declared in the generated `.c` (`gen_routines`), never the header. A system with no component or filter is called once a tick with a run of no rows. `gen_extern_system_run` (`compiler/src/codegen.c`) writes its `tide_tasks_` and `tide_task_` as any system's, a `tide_rows_component` table for each archetype it runs on (each component parameter's first lane, size and where its lanes' pages are held), and the call between `tide_rows_begin` and `tide_rows_end`; it has the same `tide_own_` a Tide system has when it splits.
  - `tide/rows.h` (`engine/src/rows.c`) is what C reads the run through: `tide_rows_count`, `tide_rows_entities`, `tide_rows_floats` and `tide_rows_ints` (the lane of a 4-byte field, by the component's number among the system's component parameters and the field's `offsetof`), their `_mut`, and `tide_rows_get` and `tide_rows_set` for a row's whole component. **Nothing is copied to read, and writes are on demand, a lane at a time**: the first `_mut` or differing `set` of a lane a snapshot shares takes a page (`tide_page_take`), copies the chunk's rows into it, puts it in the table and keeps the shared one in the run's `held`; `tide_rows_end` puts the shared one back where the bytes came out the same (its hash intact), and else zeroes past the rows and lets the snapshot keep it. A page the table alone has is written in place. So C that writes nothing costs nothing, which matters as a client's every tick starts with every page shared. A read array asked for before a `_mut` of the same lane may be the snapshot's page: C reads through the one it writes.
  - The pieces of a chunk write the same pages at once, so a run that isn't its chunk's whole (`tide_rows.whole`, `tide_pieces == 1u`) never takes a page: `tide_own_` made them the table's before the pieces started, and a shared one found there stops the program.
  - A row counts as 256 operations (`EXTERN_ROW_COST`) where a tick's work is reckoned, as its code can't be read: enough for a full chunk to go in two pieces.
  - What C gets wrong stops the program, naming the function, the system and what to write (`stop` in `rows.c`): `tide_rows_stops` (`tests/stops/`) makes each call and CTest reads what it says.
  - A program with no `extern system` generates the C it did, byte for byte: checked by running old and new tidec over every game's source list.
  - `compiler/tests/e2e/extern_system` checks it natively and on the web: arrays, rows at a time, entities, singletons, filters, runs of several archetypes in a Tide system's order, what stays shared with a snapshot lane by lane, chunks in pieces (a pool of one thread that says it has four) and on the platform layer's threads against one thread, `[Before]` and `[After]` against Tide systems, and a world packed and unpacked between. `tests/test_rows.c` checks the runtime without the compiler, `compiler/tests/schedule/extern_system` the schedule, `compiler/tests/errors/extern_system_*` each error, and `lsp_extern_systems` the language server.
- Expressions evaluate left to right on every platform and at every optimization level, whatever order C would pick for a call's arguments, an operator's operands or an initializer's fields (`docs/spec.md`, Evaluation order). Codegen runs what has side effects in a statement before it, into temporaries, in source order (`hoist_ordered` in `compiler/src/codegen.c`): spawns, widgets and calls that draw, calls to C, and calls that write (a `mut` or an `out` argument, a `mut` method, a list's, map's or set's change), with the functions, methods and operators that make them. In a statement with a call that writes, a value worked out before it that it could change is read in its turn too, into a temporary of its own (`tide_read<n>`, with its lists copied), a compound assignment's target among them, and a value worked out after it has the call run before the statement. What's written out several times in C (a vector's parts, a swizzle, a compound assignment's index) runs once, from a temporary. A statement with none of these generates the C it always did. `compiler/tests/e2e/evaluation_order` checks the results, the same natively and on the web, whose compilers pick different orders.
- A plain name means what's nearest, as in C# (agreed 2026-10-05; `docs/spec.md`, Namespaces): the file's namespace, then the namespaces around it out to the global one, then the `using` namespaces, where two that both have the name are ambiguous (`lookup` in `compiler/src/check.c`). So what a game declares itself wins over what a namespace it imports has by that name. It was the other way round, `using` before the global namespace, until a game with a `Body` of its own said `using Box2D;` and got the package's, with no error. `compiler/tests/e2e/using_own` checks it, a file in a namespace of the game's own included; no other game in the repo generates other C for it (old and new tidec over every source list).
- Default parameter values, named arguments and overloads follow C# (agreed; `docs/spec.md`, Default values, named arguments and overloads). What's built, and what code relies on:
  - A function's or method's last parameters can have defaults, constants like a field's (`param.default_value`, checked in `check_param_default`). A call passes arguments by name with `:` (`expr.arg_names`), unnamed ones first. Functions can share a name, and so can a type's methods, and systems, views and handlers, and frags and verts, when their parameters' types differ, a system's filters and a view's `verified` among them (`decl.shares_name`, `same_param_lists`): names, `mut` and defaults tell nothing apart.
  - Where nothing calls (`[Before]`, `[After]`, a mesh's vert and frag), a shared name is written with its parameters' types, `Move(Position, Velocity, with Player)` (agreed: explicit, never just enough to tell them apart, and it has to be exactly one declaration's; anything else is an error that lists them). A name alone stays fine while one declaration has it. `named_decl` in `compiler/src/check.c` resolves both; the parser reads the list in `parse_signature`, and a mesh's as a call's arguments (`named_shader`).
  - A call's arguments are bound in order, then by name (`bind_args`), and the checker then makes `expr.args` what each parameter gets, in the parameters' order, with the defaults of those left out (`settle_args`): the default is the parameter's own expression, the same at every call. So codegen and the shader writer pass arguments as they always did. What the call wrote stays in `expr.written` (`expr.settled`), which the language server walks, and names out of the parameters' order leave `expr.arg_order`, the order they're worked out in (`arg_in_turn` in `compiler/src/codegen.c`): as written, like everything else (see Evaluation order).
  - A call of a shared name picks as C# does (`check_overloaded_args`): its arguments are checked once, without a type to take (`default`, `null`, `[a, b]` wait for the one picked), each candidate that binds and fits is compared by `better_candidate`, and none or a tie is an error listing them. A name that isn't shared goes through the code it always did (`check_method_args`).
  - In generated C, a declaration that shares its name goes on with its parameters' types (`decl.c_suffix`: `tide_function_Damage_float_Weapon`), and tools show it with them (`decl.signature`: the schedule, the profiler's rows). One alone keeps its name, so a game that shares none generates the C it did, byte for byte: checked by running old and new tidec over every game's source list. `extern` functions that share a name each need a `[NativeName]`.
  - The engine's functions use the same things: a parameter a call can leave out is a default in the signature table (`signature.defaults` in `compiler/src/builtins.c`: `bool overwrite = false`, `Filter filter = Filter.Bilinear`, `string message = ""`), which editors show, and the rest are overloads (the shapes with a rotation or a width in the middle, `Math.Dot`). Their arguments take names where their parameters have them: the table's through `bind`, and the ones the checker takes by hand (`Session`, `Scene`, `Wait`, `Clipboard.Copy`, `Sample`) through `order_named_args`. Constructors, `Spawn`, `Send`, lists', maps' and the `World`'s methods, the component-wise `Math` functions and `Mesh` and `Instanced` take theirs in order (`refuse_arg_names`).
  - Provisional, awaiting the owner: what a default can be and which parameters take one; `default` as an argument staying the type's default; `[NativeName]` on externs that share a name; the names in generated C; a handler's trigger not being among the parameters that tell handlers apart.
- `out` parameters follow C# (agreed 2026-10-05: "if it's like C#'s", for the pattern of returning a bool and giving a result or the default; `docs/spec.md`, Out parameters). What's built, and what code relies on:
  - Functions, methods and extern functions declare them (`param.is_out`, with `mode` `PARAM_MUT`, so generated C, the schedule and evaluation order take one as the `mut` parameter it is underneath: a pointer to the caller's variable). What the engine calls itself (systems, views, handlers, frags, verts) is refused where it's parsed (`parse_query_params`), and operators, async functions, the devices, an `Action` and a default where signatures are checked (`check_signature`, `check_async_decl`, `check_param_default`).
  - The call says `out` (`parse_out_arg`, from `parse_args`: the word then a name, `var` or `mut` is no expression, so `out` stays a name everywhere else). The argument is an ordinary expression with `expr.is_out`: the variable itself for `out health`, and for `out var health`, `out Health health` and `out mut var health` an `E_NAME` of the local it declares (`expr.out_local`, an `S_VAR` with no value and `stmt.out_decl`), which the checker binds like any local (`begin_out_arg`, `finish_out_arg`). So everything that takes a `mut` argument by address takes these with no code of its own. `out _`, where nothing is named `_`, is a local nothing names (`stmt.discard`), called `tide_out_<line>_<column>` in generated C. An `S_VAR` with no value used to mean the name after `is`: `out_decl` tells them apart.
  - An argument and its parameter have to agree about the word (`check_out_param`, `out_mismatch`), for an extern's `out List<T>` too, which took none before. The argument's type is the parameter's exactly, a copy can't be one (a list's element, and a swizzle of several components, which a `mut` parameter refuses too since then: `through_swizzle`; it used to compile and change a temporary), and an existing variable is checked as a `mut` argument's is (`check_writable`), which is what makes a system need `mut`, keeps views off the match and keeps a parallel loop's step and a sort's comparison to their own variables. `out` where no `out` parameter takes it is refused where the argument is checked (`refuse_out_arg`, from `check_expr_any`, by `checker.out_arg`).
  - A local an `out` argument declares is the enclosing block's, as in C#. The checker's scopes are what they were, but an `if`'s own, which hands its condition's to the block around it (`pop_scope_keeping_out`); a `while`'s and a `for`'s keep theirs. Generated C declares each before its statement, with its type's default (`declare_outs` at the top of `gen_stmt`; a loop's condition's in a block around the loop), and a task keeps them while it waits like any local (`task_declare`). `settled` in `codegen.c` counts such a local as one that changes, though it isn't `mut`, so reading it beside the call that makes it keeps its turn. A parallel loop's step and a sort's comparison count one declared inside them as their own (`declared_in_expr`).
  - Definite assignment is `compiler/src/assigned.c` (`check_assigned`), a pass over a body once it's checked with no error, and only for code that has `out` parameters or arguments (`checker.outs`): a byte per variable, set where it's assigned on every path there, with C#'s rules for `&&`, `||`, `!`, `?:`, `??`, constant conditions, loops, breaks, continues, switches and returns. Assignments only add, so a loop's start is what's before it and one pass is enough. `out` parameters are assigned before they're read and at every `return` and a void function's end; locals `out` arguments declare are read only where their call ran. A block written after a call counts as code that may not run.
  - `fail` owes an `out` parameter nothing (a pick: C# has no equivalent). A function that `fails` assigns each its type's default as it starts, in generated C alone (`gen_routine`), so a failed call leaves what was assigned before it failed, or the default, and never what the variable held.

- **No Tide code can corrupt memory.** It's the language's promise to every game (the owner, 2026-10-05: "a Tide issue, not a mod issue"), which mods will rest on, and it's tested as one. Tide alone, that is: a game's C is trusted, as ever. What it rests on, and what code that touches a game's values has to keep:
  - **Nothing a game says is trusted to be a place.** An index into a list, a grid, a map or text is checked where it's used, against what's there then: past it, a read gives the zero value and a write does nothing (`tide_list_at`, `tide_grid_peek`, `tide_map_find`, `tide_text_*`), through the caches too, which only hold while their heap hasn't moved and below a list's count as it is now. An entity's handle is looked up by its generation each time (`tide_entity_alive`), so one that's stale, default or temporary is nobody's. Counts a game picks are added and multiplied 64 bits wide before anything is allocated, and one past what there's memory for stops the program with the engine's own message (`tide_out_of_memory`).
  - **Ints never do what C leaves undefined.** Generated code goes through `tide/math.h` for everything C doesn't define: overflow wraps, division and remainder by zero give 0, shifts use their count's low bits, and a float becomes an int through `tide_i_from_f`, which saturates and makes NaN 0. Runtime code that takes a game's numbers does the same: a float is kept to what an int holds before it's made one (`clamp_pixel` and `whole_pixels` in `platform/src/platform.c`, `tide_font_pixels`, the int slider), and what's summed over a game's data is 64 bits wide (a line's width in pixels).
  - **Places at the ints' edge are worked out 64 bits wide** (`engine/src/grid.c`). A parallel loop's offset is any int and its cells are anywhere an int can say, so its geometry is in `int64_t` until a place is known to be a cell's: an offset is first what's left of it by its block's size (`tide_par_begin`, `tide_par_list_begin`), a task's blocks are numbered from its own first one (`tide_par_tile`'s `origin`), so block k's place is a cell's and never past an int, and a window is where it starts and how many cells it is across (`extent`), never where it ends. Along an open axis a block that would go past the last int is left out, and a cell a step reads past it is the one its own arithmetic wraps to (`place_past`). A foreach's runs end past their last cell, which can be the last int: the end and what counts up to it are `int64_t` in generated code too (`gen_grid_foreach`).
  - **A stack that runs out ends at its guard page** on Linux and Android: generated code and the engine compile with `-fstack-clash-protection` there (`cmake/TideFlags.cmake`, `config_flags` in `compiler/cli/build.c`), so a function with locals bigger than a page touches each page as it makes room. Windows' targets check big frames by themselves. Without it, a frame of 64 KiB (a struct of matrices is enough) steps over a thread's 4 KiB guard and writes in whatever is below: measured, `subq $65544, %rsp` and then a `memcpy`. What recursion with no end does beyond that isn't decided: it crashes, with no message of the engine's, and on the web's threads other than the page's own there's no guard at all (see `docs/spec.md`, Open, at the end). macOS wasn't checked: Apple's clang is said to check big frames by default.
  - **`compiler/tests/safety/`** is the tests: each `.tide` file there is a game that tries a way in, and says in its first lines what it expects: `// expect: <text>` for a line it prints with `Debug.Log` (one or more), `// stops: <text>` for the engine's own stop, `// ticks: <n>`, and `// draws` for one whose frames also go through the renderer in a second test (`_gpu`, label `gpu`). A new file is picked up by the next build. `safety/host.c` runs it as a session would: snapshots that share the world's pages before every tick, views twice a tick with a snapshot as the confirmed world, local events, the world as bytes and back and a tick more on both, on the platform layer's threads, with a hand made up frame by frame that presses the middle of the screen, drags far off it, tabs, steps and types more than a field holds. `safety/expect_safety.cmake` checks how it ended, and fails on anything a sanitizer says. They run in every suite (label `safety`), where they pin what each case gives, the same on every platform, and they mean the most in the `sanitize` preset.
  - **The `sanitize` preset** (Linux and macOS) is the whole build, optimized, with AddressSanitizer and UndefinedBehaviorSanitizer (`TIDE_SANITIZE`): `cmake --workflow --preset sanitize`. On Windows it's a WSL build. Leaks aren't looked for (tidec and the tests end with what they hold). Box2D's and Box3D's own sources have one check off there (`nonnull-attribute`: they clear arrays they haven't got). ASan sees a read or write outside an allocation, and a world's heap, the scratch area and an archetype's pages are each big allocations of the engine's own, so a mistake inside one isn't seen: there, the tests rest on what they print, and on the world coming back from its bytes with the same hash.
  - What the tests found the first time (2026-10-05), all fixed: a parallel loop with an offset or cells near an int's limit overflowed its geometry and crashed; a foreach over an open grid never reached the cells at the top of an int's range; text of a size no int holds, a clip's corner and a render target's pixel count were made ints before they were clamped; an int slider across all the ints made its value from a float that didn't hold it. ## ECS and simulation state

- Read-only entity queries are parameters of systems, views and local handlers: `query (Body body, with Fighter, without Shield) fighters`, iterated with `foreach (var fighter in fighters)`. Their nested component bindings and filters select a second set, never the code's outer entity. Each row exposes its `entity` handle and named read-only component values. In ordinary control flow outside parallel loops and callback blocks; no writable bindings, storing or passing queries or whole rows, nested query parameters or singletons. The match's event handlers, command handlers and tasks take none yet. Component values can be copied or passed on. Traversal is normal deterministic ECS order, including sparse presence checks, with no Entity-ID or nearest-hit ordering promise. In a system, query bindings count as global component reads in access analysis, scheduling and tooling, and reuse the `World` reads-own-writes rule when the outer system writes one of them. Structural changes and events remain deferred.
- **Queries in views and local handlers** (agreed 2026-10-05; `docs/spec.md`, Read-only entity queries, and its Provisional picks under Views and drawing): local code reads the match, so its queries do too, as that code sees it.
  - A view's rows are what the view sees: blended between ticks like its own parameters, with corrections smoothed, over the entities of the world it draws. `verified` in a query follows the rule for views: all of it `verified`, the confirmed world's entities (`param.query_verified_entities`); some of it, the drawn world's that are the same entity in the confirmed one (`param.query_verified_join`, by `tide_born_same`), filters included. A query is all the match's or all local: a local one reads the local world as it is, through the code a system's query generates.
  - A local handler's rows are the match as the tick that sent its event left it, once the tick is done (Provisional: not as each event's turn left things), and a query of local entities the local world as it is. A handler of a local event takes only those.
  - Read-only (Provisional): no `mut`, and a row has the match's fields, never an entity's local fields. A view with a query over the match doesn't run outside a match (`reads_match` in `compiler/src/codegen.c`).
  - **Going through a lot stays cheap:** a view's or a local handler's query over the match (`param.query_rows`, set in `check_params`) is handed its rows, an array made before the code runs, which `gen_query_foreach` loops over: a generated `tide_row_<view|handler>_<Name>_<i>` each, the entity and the bound components. A view's are made once for its run in a frame, in the scratch area (`gen_query_fill`: `tide_query_<View>_<i>`, called when the view first runs for an entity, so one no entity matches makes none; the run function moves its `tide_mark` past them and lets them go at its end). So a view that runs for each of N entities and goes through M others blends the M once, not N times. Measured in a release build, 2,048 bodies each going through all 2,048: about 2 ms a frame, against about 13 ms for a list a view fills by hand each frame, and about 80 ms when the rows are made again for each entity.
  - A tick records a listener's rows after its events, once for the tick, when it recorded an event with a handler that reads them: `tide_hear_<Event>` sets `tide_rows_wanted` and the event's `TIDE_HEARD_READS_ROWS`, and `tide_world_tick_events` calls `tide_hear_rows` (`gen_hear_rows`) once the tick is done, which pushes a `TIDE_HEARD_ROWS` record for each (`tide/events.h`: `handlers` says which rows, `same` how many, the rows follow, and `tide_event_log_trim` gives back what the sparse filters left unused). Queries with the same entities and components share one (`collect_heard_rows`, `same_rows`), and their layout is part of `TIDE_HEARD_BUILD`. A client's hearing sends a run's rows out with the first of its events that reads rows and went out (`tide_hearing_end`), and keeps them with the run for `verified` handlers. The frame finds an event's rows after it in the log (`tide_event_log_rows`: the first with its tick and `as`, which are its run's). Text, lists, maps, sets and grids aren't in them.
  - The language server says what a view's and a listener's queries read on hover and in the lens above them (`put_world_lens`), from the same `world_uses` a system's are in.
  - `compiler/tests/e2e/view_queries` checks it: rows blended between two ticks, an entity that came and one that went, filters, a local query, `verified` against a world that went otherwise and on a client that predicted wrong, and handlers' rows from their tick, once, with the confirmed tick's for a `verified` one.
- The transpiler generates C specific to each game: component structs, archetype storage, per-system dispatch, and the tick. There is no runtime type registry.
- Archetypes derive from the spawn sites and from the Adds and Removes that can reach each one (`change_site` in `compiler/src/ast.h`, `derive_archetypes` in `check.c`): `this.Add` reaches what its system's filters admit, an Add on a local a Spawn in the same code set reaches that archetype, and an Add on an entity from a field or parameter reaches every archetype of its world. From an archetype, every combination of the components of the sites reaching it is reachable (their changes apply in any order at the tick's end), and the archetypes derived from it inherit what it could still apply this tick. Components are bits of a 256-bit mask (`comp_mask`), and a game has at most 1024 archetypes. Generated code for an Add or Remove that reaches no archetype stops the program (`tide_unreachable_change`) rather than leaving the entity as it was.
- Sparse components (`decl.is_sparse`: `[Sparse]`, or a tag any Add or Remove names) are no part of an archetype's mask: each archetype whose entities can have one (`program.possible`, inherited both ways along the moves between archetypes) stores a presence byte column and then its lanes, Add and Remove of it change the row in place (`apply_add`, `apply_remove` in the generated C), and loops, handlers and views skip the rows without it (`gen_row_filter`). Their filters admit an archetype by the components that aren't sparse (`filters_admit`), and the scheduler counts two systems as never meeting the same entity when one needs a sparse component the other excludes (`can_meet` in `parallel.c`). The layout marks them (`tide_layout_place.sparse`), and migration carries the presence byte with the value.
- Singletons hold state for the whole world, such as time, RNG and game rules (other ECSs call them resources). There is one of each per world, stored inside it, and systems declare them the same way as components.
- The world is always passed as a pointer, never stored in a global. Several worlds can exist at once, for example predicted and verified copies, several matches on one server, or snapshots.
- The world owns all simulation memory. Components hold offsets into world memory, never pointers. The allocator's state lives in the world too, so a snapshot captures everything.
- Text, lists, maps and sets in fields live in the world's heap (`tide/heap.h`): blocks handed out and reused in a fixed order, so every machine gets the same offsets. Freed memory is zeroed. Generated code says where each text, list or map it writes is (`where`: the match's, the local world's, or no world's), never the address. A map (`Map<K, V>`, `Set<K>`, `tide/map.h`) is two lists: its entries in the order their keys were added, each a live flag, the key and the value, with removed ones left dead in place until more than half are, and an index of entry numbers by the key's hash, a power of two of slots under half full; tidec generates each map type's entry struct, hash and comparison (`gen_map_helpers`), so the engine's part is generic.
- A world's list whose elements take more than a page keeps them in chunks, heap blocks of a page each, listed in its own block (`tide/list.h`): changing an element copies and hashes its chunk, never the whole list, and growing adds chunks without moving elements. Reading and writing elements is inline, and code reads them through a run cache per list type in each function (`tide_list_cache`, `tide_lc`), so a loop finds each chunk once; it holds while the heap's `moves` count is what it was, and only below the list's count as it is then. C, which takes a list as its elements side by side, gets a copy of a list in chunks, written back after a `mut` call (`tide_list_flatten`), chunk by chunk and only where the bytes differ (`put_elements` in `engine/src/list.c`). A chunk that differs and that a snapshot shares is made the list's own without what was in it (`tide_heap_write_over`), as all of it is written again. The copy is megabytes for a big list, so the last one is kept for the next call (`flat_take`, `flat_give`), each saying how much room it has in the bytes before it, as two can be out at once (a mesh's vertices and indices) and the one that's kept isn't always the last one made.
- `list.Resize(count)` sizes a list in one call (`tide_list_resize`; Provisional in `docs/spec.md`, Lists). Growing writes nothing but the count in a world: a heap's blocks start zeroed and whatever takes elements out of a list zeroes where they were (a page's hash covers them), so the room past a list's count is zeros. A list in the scratch area, whose memory is whatever was there, zeroes what it grows by. Shrinking a world's list zeroes the end of the last chunk it keeps and gives the chunks past it back to the heap (`cut`), where `Clear` keeps them all, zeroed; a list in chunks that's left with none gives its block back too, so there's never a list of no chunks. Elements that hold text let go of it first, in generated code, as `Clear`'s do. A list type's helper (`tide_list<n>_resize`) is only in the C of a game that calls it (`decl.resized`), so the others generate what they did.
- Grids (`Grid2<T>`, `Grid3<T>`, `tide/grid.h`) keep their cells in chunks of 4096 cells (fewer for cells over 4 bytes, so a chunk is never more than a page), a heap block each (its header is cells too, until it's released), listed in the grid's directory: a table by chunk position (by index for a grid sized on every axis with 65,536 chunks at most, else hashed) and each chunk's record (its position and block). A chunk only exists once a cell in it is set to something other than zero. Grids are fields of components, singletons and scenes only, never copied: tidec keeps them out of locals, structs, events, inputs and functions. Generated code reads and writes cells through a chunk cache per grid type in each function (`tide_grid_cache`, `tide_gc`), so a loop looks each chunk up once rather than at every cell; it holds while the heap's `moves` count (a page copied to be changed, or blocks released) is what it was, so whatever the code calls meanwhile, it never reads stale cells.
- Text and lists that code makes along the way live in a scratch area outside the world, cleared after each system, view and handler runs, and are only ever copied into a world. It's a stack of bytes per thread, addressed by offsets of 30 bits, which grows as it needs in pieces of whole slots of 1 MiB (`tide_scratch_at` in `tide/text.h`), each as big as what it's made for, so a list or text of any size is whole and the same whatever else was made before it; a piece goes when the area goes back to a mark from before it, the biggest (up to 64 MiB) kept as a spare for the next. Running out of memory, or of the offsets, ends the program with a message naming what didn't fit, as `tide_out_of_memory` does for worlds.
- Tasks are state machines tidec makes from async code (`gen_task_resume` in `compiler/src/codegen.c`), as C# does: a resume function per async function or handler and world, which goes on from where its frame says it stopped, until it waits again or ends. A frame is a generated struct: where it stopped, its parameters, its value, the frames of the async functions it awaits (so a task is one frame however deep it awaits, and nothing awaits itself), and a slot for each C local in scope at a wait, which goes in before the task waits and comes back after. No task keeps an address: components and singletons are got again from the task's owner entity each time it goes on. A world keeps its waiting tasks in a `tide_table` (one column: `tide_task`, then the frame) per async function and handler, and goes through them in its task pass, once its tick's changes (or its frame's) are in: those whose time has come go on one at a time, in the order they started, on copies of their frames, as tasks they start may move rows; those whose owner is gone end. A system that starts tasks runs them until they first wait, inside it, so it doesn't split, and waits for systems that start tasks, spawn or change text (`CONFLICT_TASKS`).
- Local state (menus, settings, view state such as particles) belongs to one machine and lives outside every world. It's never sent, rolled back or hashed. The compiler keeps match code from reading it and local code from changing the match (see `docs/spec.md`).
- Local fields (`local List<Vertex3> verts;` in a match component or singleton) are local state for the match's entities, and nothing of them is in the match: its layout, hash, deltas and what a joiner downloads are what they'd be without them. `compiler/tests/e2e/local_fields_same.h` pins that against the same game without them, and a change to how worlds are kept or sent updates its numbers.
  - The checker takes them out of their declaration into a declaration of their own, its local part (`decl.local_part`, `split_local_fields` in `compiler/src/check.c`): a local component or singleton of the same name, in no list of names, whose fields `box.verts` finds (`check_local_field`). So nothing that lays the match out can see them. Its struct is `<Name>_local`.
  - A singleton's local part is a local singleton. A component's is in a table of the local world, `tide_fields_<Component>` (`tide/attached.h`): the entity, the value and what the entity was born as (below), a row for each entity something was written for, found from the entity's index (two generations of one index can each have a row, as the two worlds can each have another entity there). The value is one column, so code reads and writes it where it is.
  - Code reaches them through a parameter that comes with a second pointer, to the local part (`has_fields_ptr`, `tide_lf_<name>` in generated C): a view's, a `Forgotten` handler's, and a function's, which the checker marks (`param.local_use`) and follows through calls (`check_local_field_calls`). A view's wrapper finds each row's (`gen_row_fields`): where there's none, the defaults to read, and for a `mut` parameter a copy of them, which becomes a row if the view changed it. Defaults that need the heap are an entity's own from the first run of a view that takes them as `mut`.
  - They go at the start of `tide_frame` (`tide_local_forget`), when either world's tick changed: an entity's when neither the world views draw nor the verified one has it with the component, born as the row's was, a singleton's (back to its defaults) when there's no match, and all of them after `tide_local_disconnected`. Handlers of `Forgotten` run first, with the fields there; it's never queued.
  - What they hold is in the local world's heap. The match only has a heap for what the match holds (`world_heap` in `compiler/src/codegen.c`).
  - A rollback can give an entity's handle to another entity (a predicted spawn, where the server had another), so a row is kept for the entity, not the handle: by what it was born as, a number of the tick and what it was spawned with (its archetype, its scene and each component's bytes, never the spawn's struct, which has padding: `tide_born` in the generated C, set as the spawn applies). The entity table keeps it beside the slots (`tide_entity_set_born`, `tide_entity_born` in `tide/entity.h`: pages after the slots' in `tide_entities.page`, made when one is first set, which snapshots share and copy when they change). It's beside the world and never in it: not hashed, packed or sent, so a world that came as bytes or as a delta has none, and 0, not known, is the same as anything (`tide_born_same`); rows C sets have 0 too. A game with local fields or correction-tagged fields on a component sets it (`entities_born` in `compiler/src/codegen.c`), so others' spawns and entity tables are as they were. A replay that spawns something else on a handle drops what was kept there, and the same spawn again keeps it; hot reloading carries each row's with it.
- Generated types (components, singletons, the input and structs) have no padding the compiler adds: tidec writes it out as members, which every value sets to zero, and the generated header checks each type's size (`_Static_assert`). Their bytes only depend on their fields, so snapshots and state hashes can compare memory directly. Input from outside gets its padding cleared along with its other repairs.
- Worlds grow as they need, with no limits but memory (no engine limit stands in for checking inputs: that's the game's): running out of memory ends the program. A world's heap is the exception: its offsets have 30 bits, so it holds 1 GiB, in blocks of 128 MiB at most (`engine/src/heap.c`), and past either the program ends the same way. The one depth that's checked is a chain of events, each sent or spawned by a handler of the one before: an endless one would never stop, so past `TIDE_MAX_CHAIN` (100,000) in one tick the program stops, naming the event. Each queued change records how far down its chain it is. Their data is in pages (`tide/page.h`): each archetype's rows in chunks, each chunk's column a page (`tide/table.h`), the entity table's slots and the heap. A snapshot (`tide_world_copy`) shares the world's pages, and whoever changes a shared page first gets a copy of their own, so a world and its snapshots cost the memory of what's different. A page nothing refers to any more is handed out again (`tide_page_give`, `tide_page_take` in `engine/src/page.c`): a client lets go of as many pages every tick as the tick changed, with the snapshot it drops, and takes as many, and a new page of these sizes comes from the system each time, with a page fault as each 4 KiB of it is first written, where one just let go of is still in the CPU's caches. Copying into new ones took five times as long (2,400 Box3D bodies: a tick from 2.5 ms to 1.75, `packages/box3d`'s `box3d_costs`; `bench_gallery`'s client snapshots a quarter less, `bench/results/gallery.jsonl`, `page-spares`). They're kept by size, each thread its own, and what a thread has too many of goes where the others find them, as the thread that drops a snapshot is often not the one whose system writes; a page that comes from there is another thread's, so the web's memory is synced (`tide_memory_sync`). What takes one sets every byte of it: it's whatever it was. A system's loop over a chunk writes the lanes it declares `mut` in place when the table alone has their pages. When a snapshot shares one, as a client's do every tick, it's written into a page of the table's own from the start (`tide_table_lanes_begin`), and once the loop is done, a page with a row that changed is the table's and one with none is let go (`tide_table_lanes_end`, which keeps it for the next: `spares`), so a page that nothing changed stays shared, with its hash good, however many systems declare it `mut`. A loop that writes every row of its chunk (no row left out by a sparse component or by whose it is, and the task has the whole chunk) reads each lane where it is and writes it apart (`apart`, `tide_table_lanes_shared`): nothing is copied first, so a shared page costs the loop no more than its own would. Any other loop gets a copy to read and write. Handlers and spawns, which change one row, make the page their own as they write, and a component put back for one entity (a handler's `mut`, `world.Set`, `tide_set_<Component>`) only where a lane isn't what's there already (`tide_table_scatter`): code that changes one field of a component of forty lanes leaves the other pages shared and their hashes good.
- A component is kept in lanes: columns of 4 bytes of it each (2 or 1 when its size isn't a multiple of 4: `tide_lane_width` in `tide/table.h`), so each of its fields is an array of its own, as C written for speed keeps them. Generated code gathers an entity's components from their lanes into copies (`tide_gather_<Component>`), and puts the `mut` ones back once it's done with the entity (`tide_scatter_<Component>`), so a system's ifs become selects and its loop over entities runs with SIMD. That only holds while the C compiler can tell the lanes' places don't change under the loop:
  - The loop reads them from arrays of its own (`tide_in_<Component>` to read and `tide_col_<Component>` to write, `gen_lanes_places` in `compiler/src/codegen.c`), never from the arrays the table was handed (`tide_was_`, `tide_own_`): those have been given to a function, so any write through a byte pointer could change them as far as the compiler knows, and a loop that read its lanes' places from them read them again at every row and never vectorized. A million particles went from 3.4 times the C written for them to 1.2 on one thread when that was fixed (`bench/results/versus.jsonl`, `system-loops-simd`).
  - The loop is in the generated C twice where it can write apart (`gen_chunk`): once with each lane read and written through one pointer, and once with two. One loop for both would have the compiler check whether they overlap, find that in place they do, and run those rows one at a time.
  - Apart, the compiler has to check that no lane the loop writes overlaps one it reads, and it only does for a component of a few lanes: with a dozen (three `float3` and three floats) it gives up, and that loop runs a row at a time, still without the copy. In place the same component runs as SIMD. What would fix it is the loop in a function of its own with every lane a `restrict` parameter, which says they're apart without a check; nothing less does, as `restrict` on a function called for each row only speaks for that row.
  - `versus_particles --kept 1` keeps each tick's world before the tick, as a client does, which is how the shared case is measured: 3.3 ms a tick before any of this, about 1.3 now, against 0.6 in place. A task's components are copies too, loaded each time it goes on and put back when it waits or ends, and around what it awaits or starts, which may change them (`gen_entity_copies` in `compiler/src/codegen.c`).
- Each page keeps the hash of what's in use in it until it changes, so a world's hash (`tide_world_hash`) only reads what changed since the last one. It covers contents, never addresses or capacity, so it's the same on every machine for the same state. The command queue, empty between ticks, isn't shared.
- A chunk has 2048 rows (`arch_shift`): as many as keep its widest column, the entity's 8 bytes, to a 16 KiB page, so a lane's pages are 8 KiB at most. The first chunk starts with room for 4 rows and grows, so archetypes with a few entities take little memory.
- Structural changes and events wait in the world's queue until the end of the tick (`tide_queue` in `tide/table.h`, `tide_command` in the generated header). Each is queued with the bytes it has, what's before `data` and the member of `data` it carries (`TIDE_COMMAND_SIZE`), so an event costs its own size whatever the game's biggest spawn is: nothing copies or reads a whole `tide_command`. An item starts with its size, which is how the queue goes from one to the next (`tide_queue_next`, from a `tide_queue_place`), and is whole in one page. A task's queue hands its pages to the world's, for the empty ones the world kept (`tide_queue_append`), so merging the tasks' queues copies next to nothing and, after the first ticks, allocates nothing. A world unpacked from bytes checks that each change is as big as its kind needs (`tide_command_fits`), since applying one reads that much.

## Performance

- Performance is a top priority. Weigh design choices by their runtime cost.
- Runtime, compilation and rendering speed are requirements. Compare equivalent work with the best practical handwritten implementation; an unexplained order-of-magnitude gap is a performance bug to investigate and fix. Runtime comparisons keep the same determinism guarantees. Fast iteration matters alongside the speed of the shipped game.
- Internal performance changes are authorized when they preserve observable language behavior, including deterministic results, ordering, snapshots and hot reload. Storage, generated code, scheduling, batching and caching are implementation choices; changes to the language's expectations remain the owner's decision.
- Flexible features are fine even if they cost more, as long as the common, fixed path stays fast.
- Friction between engine code and user code should be minimal or non-existent.
- Snapshotting and restoring the full simulation state must be cheap. Rollback depends on it.

## Networking

- Devices use explicit read-only parameters everywhere they can be read: `Sample(Devices devices)`, views, systems, match handlers and helper functions. Bare `Devices.keyboard` is an error. Sample and views get this machine's devices; match systems and handlers get the entity owner's tick input, or the server's for unowned entities and code that runs once. Only fields match code reads are sent. Frame text and window positions keep their existing restrictions.
- UI actions enter the match as typed `command Name { ... }` payloads, sent by local code with `Send(...)` or `entity.Send(...)`. A command has one void handler, `command(Name value, PlayerID sender) Handler(...)`. The engine supplies the sender from the connection; ordinary guard clauses decide which actions to take. There is no acceptance method, return status or transaction. Match events remain simulation notifications.
- Commands are bounded copied wire payloads, queued independently of tick input and resent until a verified world confirms their per-player sequence. The server chooses the tick and order; handlers join the existing deferred event queue at tick end. Sequence state is part of snapshots, hashes and host migration. Initial limits are 1024 packed bytes per command, 32 pending per player and 16 scheduled per tick. Game-specific validation belongs to the handler.
- The command C contract is agreed: `tide_game.check_command(data, size)`, `command_sequence(world, player)` and `command(world, sender, sequence, data, size)` validate bytes, read the world's sequence and record a received command. `tide_session_send_command` and `tide_client_send_command` copy bytes into the pending queue. Generated `tide_local_command` peeks the local queue and `tide_local_command_sent` removes its first item after a successful send; the host table exposes both. Payloads include a type and target plus copied fields; string bytes, never heap handles, go over the network.

- Rollback netcode with full server authority. The server is the source of truth. Clients predict ahead and roll back when the server disagrees.
- Single-player is a match too: the machine runs the server itself and connects to it through a loopback transport, so there's no separate offline path. The engine assumes nothing about what games do with matches (no built-in pause): it gives them the tools.
- There's one kind of match, so no special case for playing alone: a match starts closed, and whether other machines can join it is a switch on it (`Session.Open` and `Session.Close`), not another way to start one. Single-player is a match nobody else was let into.
- A match takes as many players as the game says: its `maxPlayers` setting (`tide_game.max_players`, `TIDE_GAME_PLAYERS` in the generated header), 16 without one (`TIDE_PLAYERS_DEFAULT`) and 256 at most (`TIDE_PLAYERS_MOST`, `tide/player.h`). The world keeps an input for each and the server's in the slot after them, so the count is part of the layout: builds that differ in it are different games, and a reload that changes it starts the match over (`prepare_server` refuses). The netcode has no smaller limit of its own: a server's arrays by player are allocated for its game's count, sets of players are `tide_player_set` (320 bits: the players and the server's slot) and go on the wire as a varint of as many bits as they have (`write_players` in `engine/src/session.c`), so a match of a few players pays what a 32-bit set did; a tick's count of joins and leaves is a varint; and a handover record goes in parts of a datagram (`HANDOVER_PART`), as 256 digests don't fit one. A scene's `tide_players` is as many 32-bit words as the game's players take (`add_scene_player_words` in `compiler/src/check.c`). `compiler/tests/e2e/players` runs a match of 150 on the loopback network, through a handover.
- Clients have no input delay: they run ahead of the server by about half the round trip plus a small margin, so their inputs arrive in time, and only other players' inputs are guessed. The server says how early their inputs arrive, and clients keep them as early as they have to be by it (below). A client that sends none (a game without an input) ignores it and keeps the lead it joined with.
- How late other players see you is the priority (the owner, 2026-10-05: "the entire point"; a player's own input was never the issue, and a change that made views draw the tick in progress was built by mistake and reverted the same day, as it also made each machine guess the others a tick further). What's between a key read on one machine and another's view showing it, beside the network: the wait for a tick to sample it, how early the client sends its inputs (the server holds each until its tick), the server's frame, and the watcher's.
  - A client sends its inputs as early as they have to be, and no earlier (`keep_early` in `engine/src/session.c`). The server says with everything it sends how many ticks ahead of the one it runs next the newest input is (`margin`); the least of those over a while is what counts, as being early is for the input that's nearly late. The client keeps that least at its lead (`tide_client_desc.lead`: 1 over a network, 0 on the server's machine), watching a while at a time. Under it, its clock goes ahead at once by what was missing. Over it for the whole while, its clock loses the difference, a tenth of the time that passes (`CLOCK_SLOW`, in `update_client`), so no tick stands still. The while is 2 seconds (`EARLY_LOOK`), and 10 after an input was nearly late (`EARLY_KEEP`): what made it so may come again, and has to stay away that long. One that was nearly late in the client's first second in the match (`EARLY_START`) doesn't count for that, as a machine starting up stutters, and that doesn't come again. Each change takes a round trip to show, so it watches again from then.
  - Before, inputs were kept 2 to 6 ticks early, wherever in that the clock started. Measured in made-up time, frames of a 60th of a second from a key read to another player's view showing it, on a network with no delay and one 30 ms each way: 3 and 6 frames at 60 ticks a second, 6.5 and 9.5 at 30, 8 and 12 at 20. Now 2 and 5, 4.5 and 7.5, 5 and 9, with no input late.
  - Every tick less early is also a tick less that a machine runs ahead of the server, guessing the others: what it puts right when a guess was wrong is that much smaller.
  - What's left is in whole ticks: the lead is one tick, which at 20 ticks a second is 50 ms. Keeping inputs a frame early instead (the server saying how long before its tick each arrived, which it knows since transports say when datagrams arrive) is the next step, not built.
  - `tide_client_status.early_ticks` is what the server last said, and `late_ticks` how many ticks it ran without this machine's input. `compiler/tests/e2e/seen` pins the frames above as the most they may be, with none late, and checks that on a network that delays some datagrams 40 ms more than others the inputs go as early as that needs.
- Running predicted ticks again is prediction's cost, and a client keeps it within a budget by delaying its input (`tide_prediction`, the `prediction` setting): it samples inputs as far ahead as ever (`sampled`), so they arrive in time, but runs ticks `delay` short of them. Predicting (`Prediction.Rollback`, the default), it starts with none and adds a tick when the ticks it would run again cost more than `tide_client_desc.resim_budget` a frame (4 ms unless the host says), measured with the host's clock (`now_ns`, which `tide/host.h` sets to `tide_time_now_ns`); without a clock, as in tests and benchmarks, there's no delay and a run is the same on every machine. With `Prediction.Delay`, clients never predict: the delay starts at the lead and round trip plus half a round trip and two ticks, grows when a frame hadn't come by its tick, and shrinks once frames have come three ticks early for five seconds. Either way a frame whose tick the clock hasn't reached waits (`play`), so ticks run at the match's pace however early frames come, and views blend up to the clock less the delay. One change per round trip (`adjust_delay`).
- Matches go over WebRTC data channels, unordered and unreliable, on the web and on desktop alike, so web and desktop players meet in the same rooms: they're the only way a browser can reach another player's machine directly, so browsers host matches as well as join them. Desktop hosts also take players on a UDP port, our own thin layer, which `Session.Connect` reaches by address. The protocol above the transport stays the same.
- Desktop WebRTC is our own (`platform/src/rtc/`): P-256, ChaCha20-Poly1305 and the hashes, ICE with STUN and TURN, DTLS 1.2 and SCTP, only as much of each as a data channel needs, written from the RFCs with no third-party code, so games carry no license terms for it. Browsers are its check: it has to work against Chrome's and Firefox's (`platform/tests/rooms.mjs`). Desktop games reach the relay at `wss://` with the system's TLS (`src/rtc/tls.c`): SChannel on Windows (`secur32`), Secure Transport on macOS (the Security framework), and OpenSSL's libssl on Linux, loaded at run time rather than linked, so nothing ships with games; without it, Linux games can't reach the relay. Android apps can load no OpenSSL, so there it's Java's `SSLEngine`, through JNI. Browsers hide their local address behind `.local` names, which desktop games don't look up (hearing mDNS answers means listening on port 5353, which Windows' firewall asks players about): browsers' checks still reach the desktop side, which learns their address from them.
- Direct connections come first, since they cost the relay nothing. Players find each other in rooms, by a code the host picks itself (`Session.room`), so there's nothing to wait for; a code already taken gets another before anyone could read it. The relay we host (`relay/`) introduces players in a room, passing along what WebRTC needs to connect them, and nothing else goes through it. Players whose networks can't connect directly go through Cloudflare's TURN: the relay makes short-lived credentials with the key in its Fly secrets, and hands them to players. Dedicated servers stay.
- A ping is the network's round trip, and nothing else (agreed 2026-10-05: two players at one desk read 14 ms, two frames of waiting, where the owner expected 0 to 2; "logic depend on latency has other ways to use it"). `Session.ping`, the stats' ping and `tide_client_status.ping_ms` are from when this machine sent to when the answer arrived, less what the server held it. What an answer takes to be read, the waits for an update on both machines in it, is `answer_ms` (the client's `rtt_ms`), which is what the netcode still goes by: when to send again, how far ahead to run, how long to wait for a change to show. How:
  - A transport says when a datagram arrived, not when it was read: `tide_transport.clock`, its own clock in seconds, and `arrived`, when the datagram `receive` last gave arrived by it. Both NULL where it can't say (a wrapper in a test): datagrams then arrive as they're read, by the session's time, and a ping counts the waits (`clock_of`, `arrived_of` in `engine/src/session.c`).
  - The server notes when the datagram that said the time it echoes arrived (`connection.their_arrived`), and says how long it held it with every echo: `held_ms`, a varint of milliseconds after the echo in a SERVER (a byte, while it's under 128 ms) and 16 bits in a WELCOME. `PROTOCOL` went to 9 with it.
  - A client remembers when it sent each of its last 256 times, by the transport's clock (`said_time`), and `measure` finds the one echoed: the ping is the answer's arrival less that, less the held time. No session time is in it, so neither is the work of an update between reading and sending.
  - The loopback network's clock is its time, and a datagram arrived when its time came (`engine/src/net.c`): a machine's ping to its own server is 0, and tests and benchmarks repeat.
  - Rooms on the web: the page notes `performance.now()` as a datagram comes, or as the page lets go of one it held back (`Tide.lag`), which the program's clock is too (`room_arrived` in `platform/web/tide.js`).
  - UDP and desktop WebRTC read their sockets through `platform/src/arrivals.c`, which says when each datagram arrived, by `tide_time_now_ns`. Linux, macOS and Android stamp datagrams themselves (`SO_TIMESTAMP`, read with `recvmsg`; by the wall's clock, so it's how long ago that was, never longer than since the socket last had nothing). Windows only does from Windows 11 on, so there the system calls when the socket has something (`WSAEventSelect` on an event the thread pool waits on, `RegisterWaitForSingleObject`), and the call reads it and notes the time into a buffer the frame takes from (up to 256 KiB for sessions' UDP, 64 KiB for a WebRTC peer: what a socket held by itself); no thread of ours. WebRTC carries it up: the ICE socket's (`rtc_ice.arrived`), to the message it came in (`rtc_peer.arrived`), to the room (`backend_arrived` in `platform/src/rooms.c`). A host on UDP and in a room at once says each datagram's by the transport it came on.
  - `net_a_ping_is_the_networks_round_trip` (`compiler/tests/e2e/net_test.c`) checks it in made-up time: 80 ms on a network 40 ms each way with updates 11 and 22 ms apart, 0 on one that takes no time, and through a transport with no clock, the waits counted. `udp_a_ping_counts_no_wait_for_a_frame` (`platform/tests/udp.c`) checks real sockets with frames 60 ms apart: the least of 20 pings, as a busy machine can note one late (measured on Windows: 0 ms, with answers taking 120). In the docs' match on one machine it went from 13.9 ms to 0.6.
- How it works now (`tide/session.h`): the server ticks the one true world and sends each player every tick: who joined or left, the inputs that changed, and a hash of the world after it. Inputs that didn't change or arrive keep the last one, on every machine. A client keeps a snapshot of every tick from the last one the server confirmed (the verified world) to the one it predicted. A tick that arrives as the client guessed only has its hash checked against its snapshot; one that went otherwise runs on the snapshot before it, and the ticks after it run again. Worlds go as deltas (`tide/delta.h`), each a numbered transfer in chunks. A region that goes is XOR'd byte by byte with the one a stride before it where that packs it shorter: the writer tries none, 1, 2, 4, 8 and the size of the region's rows or cells, counting the bytes each leaves that aren't zeros in a sample of it, 8 at a time, and the region says which. Joining players get the world, and a cookie that gets them their `PlayerID` back when they join again. In a game with a seed (`tide_game.seeded`), the server picks the match's as it starts it, and the world carries it. A hello alone gets a welcome: the join and the world wait for the player's first message back (`greet`), so a hello from a spoofed address costs a datagram, never a player in the match or megabytes sent there, and one that never writes back gives its slot up in two seconds with its cookie. A whole world is packed once a tick, however many players join in it (`pack`). A join or leave for the next tick is never dropped: a player who joins and leaves before the tick never was in the match, so the two cancel. The server keeps every tick since a world it sent until that player catches up, however long the world took to arrive (`keep_needed`), up to eight times its four seconds; a player that falls behind otherwise, or further than that, gets the world again. A player with a world to build it from (its own, when its hash differs; its last one, coming back to a match that changed hands; or, joining, the match as it started, which it starts itself when starting calls no C: `tide_game.pure_start`) gets the hashes of the server's pages first, after how the match started, says which its world lacks, and gets those; one that doesn't come out as the hash says is asked for again, whole. Worlds that go in one update anyway go whole. Inputs go as what changed (`write_input_delta`): in frames, from the slot's input as the world keeps it before the tick; from players, each from the tick before. In an input, ints, int enums, players and entities go as varints in bits (7 bits a group and a bit for whether more follow, `tide_bits_put_varint`), signed ones zig-zagged first, so small numbers take a byte; floats keep their 32 bits, and byte and ushort enums their 8 and 16. As a delta, an int or int enum that changed goes as by how much (`tide_bits_put_changed_difference`, wrapping), and a float as its bits' XOR with what it was, the run of bits that differ and where it starts (`tide_bits_put_changed_xor`, as Gorilla packs floats), or its own 32 bits where that's shorter. Packing never changes a value: every one comes back bit for bit, NaNs and -0 too, and `tests/test_bits.c` checks it. Datagrams keep times to 16 bits and small numbers as varints, and a tick where nothing happened is its hash and a byte. `net_a_match_costs_little_to_keep_going` pins what a match costs to keep going: a change that makes it cost more updates the test on purpose. A client sets its clock from the server's tick as it sent the world, not the world's own tick, which a transfer leaves behind. Everything is resent until acknowledged; nothing waits on a reliable stream. A machine that runs the server and stops for a while (a breakpoint, a browser that freezes the page) stops its server and its player with it: its session drops the time beyond what the server can run in one update, so the two never time each other out and nothing runs ahead to catch up. A client of another machine keeps to the real time.
- Host migration is a game's choice, off by default: the `hostMigration` setting (see `docs/spec.md`, Sessions). When a room's host leaves or times out, another player's machine goes on from its verified world, which is bit for bit the server's at that tick, and the others join it again with their cookies. The server sends its players a handover record (`MSG_HANDOVER` in `engine/src/session.c`): its room's code and key, its own player, whether it's open, and who's in the match with their cookies' SHA-256. The relay decides who hosts (`{migrate: code, key}`, in `relay/relay.mjs`): it pings the room's host, and gives the room to the first player there when the host is gone. `tide/host.h` drives it (`tide_run_migrate`), with `tide_platform_room_migrate` on both platforms. A goodbye can be lost, so a match that ends (`Session.End()`, or its last scene) also tells its transports (`tide_transport.end`), and a room tells the relay (`{end}`), which keeps it as ended for five minutes: a player who comes back to take it over hears it ended. The room keeps its relay connection (or makes one) until the relay has read it (on desktop, the relay's answer to the WebSocket close that follows says so: `rtc_ws_finish`, as a socket closed at once can be reset before the relay reads it), and asks for the room first on one that hadn't, since the relay may not know it yet: a room's code shows before the relay hears of it, and a host that lost the relay is reaching it again. Nothing about it is timed on the server. So in a match with host migration on, the server keeps nothing beside the world that the players don't also have: what it keeps of its own (each player's cookie, as a hash, and whether the match is open) goes to every player. A feature that keeps more on the server has to send it too, or not work in those matches. Once visibility hides them (below), private scenes the new host wasn't in are lost, which is the game's to know; a match on an address (no relay to meet at again) ends as it does today.
- Sync relies on determinism as much as possible. The main thing sent over the network is inputs.
- Inputs come from clients, so they're attack points. The engine is forgiving with them and makes bad values hard to turn into broken math or a broken game: NaN and infinite floats in an input become the field's default before the game's `Sanitize` runs, and math functions avoid spreading NaN where they can (`Math.Clamp` always returns a value in range; `Math.Min` and `Math.Max` with one NaN return the other argument; `Math.Normalize` gives zero for a vector too short to normalize, and the identity for a quaternion, so there's no `NormalizeSafe`: `tide_normalize_*` in `tide/math.h`).
- State corrections are supported. Divergence is detected through state hashing.
- **Provisional:** `[Position]` and `[Rotation]` describe match fields for view interpolation and smooth prediction corrections. `[Position]` on a float or floating-point vector keeps linear tick interpolation and accumulates additive presentation error. `[Rotation]` on a float in radians or a quaternion uses shortest-path angular or relative-quaternion interpolation and correction error. Error is local to presentation and decays exponentially with frame time, with a provisional 75 ms half-life; later corrections accumulate, while ordinary movement follows the corrected simulation without being low-passed. Untagged fields keep ordinary tick interpolation. `entity.Snap()` and `singleton.Snap()` remain immediate and clear accumulated error. These attributes never change simulation writes, collisions, world hashes or network state. Ordinary structs can contain annotated built-in fields; correction smoothing through a type's custom `Interpolate` is deferred, with no new custom-type contract or rate setting agreed. Tags take no arguments and cannot combine with each other or `[Snap]` on one field. They do not belong on local state, inputs or events. A new match, hot reload or replacement without comparable presentation history clears the error; migration retains it while drawing the frozen world, then clears it on adoption of the new network timeline. See `docs/spec.md`, Provisional correction smoothing.
- Clients can be denied specific state through a visibility system, for example other players' cards in a poker game. Not built yet: a scene says who's in it (`SceneVisibility.Private`, `Scene.AddPlayer`), but every player is still sent the whole world.
- Visibility is dynamic. The server decides at runtime what each player can see, through an API.
- Each client tracks a **verified tick**. It is the latest tick for which any state the client lacked but should have has arrived, and any divergence has been corrected by the server. Ticks after it are predicted and may be wrong for a while.
- Game code tells verified state from predicted state with one word, `verified`, a parameter's modifier like `mut` (agreed 2026-10-05; `docs/spec.md`, Views and drawing, and Events). For example, a player death visual can wait until the death is verified.
  - In a view, `verified Health health` and `with verified Dead` read the world the server has confirmed, the session's verified world, which `tide_frame` is handed. A view with components of both worlds runs for the drawn world's entities that are the same entity in the confirmed one (`decl.verified_join`: each row looks the entity up there, `gen_row_join` in `compiler/src/codegen.c`, by handle and by what each was born as); one whose components are all `verified` runs for the confirmed world's entities (`decl.verified_entities`, whose `need_mask` is theirs). A view that takes any is handed the confirmed world (`decl.takes_verified`: `tide_run_view_<View>` gets `tide_verified`, which is `w` where the host gave no verified world). Values aren't blended. Showing other players from confirmed state, blended between confirmed ticks, is open, and may belong at another level.
  - A `verified` value is whole (owner, 2026-10-05: `verified` is valid wherever it makes sense): what the confirmed world keeps in its heap is read there, beside the heap of the world the frame draws. A handle's two `where` bits have a fourth value for it, `TIDE_IN_VERIFIED` (`tide/text.h`), which is only ever in a handle, never a `where` a write is given: `tide_frame` says which heap it is (`tide_text_use_verified`), reads find a handle's heap with `tide_heap_read`, and everything that changes a block still finds its heap with `tide_heap_of`, which the confirmed world's never is, so nothing writes there. Where a view's wrapper copies a `verified` component or singleton out of the confirmed world, it retags the copy's text, lists, maps, sets and grids (`tide_confirmed`, `gen_confirmed_copy` in `compiler/src/codegen.c`), so nothing of them is copied and functions the value is passed to read it by what it says. A list's elements and a map's entries are in the heap with their own handles, which still say the drawn world's, so a list or map whose elements hold text is copied to the scratch area with that text retagged (text is all elements can hold); the wrapper frees those when it's done (`tide_confirmed_mark`). A read path that's added to the runtime resolves a handle's heap with `tide_heap_read`, or it reads a `verified` value as empty. `compiler/tests/e2e/verified_heap` reads every kind from two worlds that ticked differently, and from a snapshot that shares the drawn world's pages, and checks the confirmed world's bytes are as they were.
  - In match code it's an error: the match is the same on every machine and has no "confirmed".
  - `compiler/tests/e2e/verified_views` checks views on one world, on two worlds that disagree about a handle, and on a client that predicts wrong for a while.
- **Local handlers of match events** (agreed 2026-10-05; `docs/spec.md`, Events): `local event(Hit hit) ShowHit(Body body, mut Fighter fighter, mut Fx fx)` hears the match's `Hit` on each machine, at the start of a frame, before the views, for each tick simulated since the last frame, in order. It takes the event, the target entity's components (read-only, `mut` reaching only their local fields, as in views), match singletons (read-only) and local singletons (`mut`), all of the match's as the event's turn left them, even if the entity is gone by the frame. The engine's own events have them too. `local event(verified Died died)` runs once, when the server confirmed the tick that sent the event.
  - **Once, under rollback:** each tick remembers which events it delivered locally. Run again, the same event (tick, event, entity and fields) stays silent; one only the corrected tick has is heard then, late; one the correction removed isn't taken back.
  - **Events only local code handles** cost the match nothing: its bytes, hash, snapshots and traffic are the same without them, and a machine with nobody to show it to does no work for them. `compiler/tests/e2e/local_events_same.h` pins that against the same game without them (`local_events_same`, `local_events_plain`), as `local_fields_same.h` does for local fields: a change to how worlds are kept or sent updates its numbers too.
  - In the compiler, such a handler is a listener: `decl.listens` (`check_listener` in `compiler/src/check.c`), kept in its event's `listeners`, never in its `handlers`, which the tick runs. Nothing of it is in the world. A tick records what listeners take only when it's given a log: generated `tide_world_tick_events` sets the log for the thread that runs the tick (a thread-local of the generated `.c`, `tide_listening`), and as each event's turn comes, after the match's handlers of it, `tide_hear_<Event>` (`gen_hear`) pushes a `tide_heard` (`tide/events.h`) and then a `tide_heard_<Event>`: the event, and the components and singletons its listeners take, gathered then, with a bit for each listener that runs for the entity. `Spawned` is recorded as the spawn applies and `Destroyed` before the row goes. An event with listeners and no match handler isn't even queued while no tick records (`tide_listeners`), unless it holds text, whose heap blocks every machine has to take the same way.
  - The frame runs them from the records (`tide_local_hear`, `gen_heard`), before `tide_local_forget`, so a handler still finds the local fields of an entity that's gone since; a row kept for another entity that had the handle goes first (`tide_let_go_<Component>_local`, by what each was born as). Games with listeners of entity events keep what entities are born as (`entities_born`).
  - Text, lists, maps, sets and grids of the match aren't recorded yet: a listener that names one is an error, and the copies have them empty. `World`, `Devices`, the input, `with ownership` and `async` are errors there too.
- The contract for what local handlers hear (Claude's first version, proposed 2026-10-05, for the owner to confirm; `tide/events.h`):
  - `tide_event_log` is a growing run of records, each a `tide_heard` (its size, tick, event, `wants` and `as` (`TIDE_HEARD_PREDICTED`, `TIDE_HEARD_VERIFIED`), target and what it was born as, the bits of the listeners that run, and `same`, a hash of the event's fields) and then what the game's build lays out after it. A log says whose build its records are (`build`), and another build takes none of them. A record whose event is `TIDE_HEARD_ROWS` is no event: the rows a tick recorded for its events' handlers' queries, after the tick's events (see Queries in views and local handlers, under ECS and simulation state), which an event says it reads with `TIDE_HEARD_READS_ROWS` in its `wants`.
  - `tide_game.tick_events(world, jobs, events)` is `tide_game.tick` recording into `events`; NULL in a game with no listeners. Generated `tide_world_tick_events(w, jobs, events)` is always there, and `tide_world_tick` and `tide_world_tick_on` record nothing.
  - `tide_client_desc.events` is the log a client's host takes from, once it's `taken`; `tide_session_events(session)` gives a session's, and marks it taken, so a session records from the first call on. A client keeps a `tide_hearing`: for each tick it ran and hasn't had confirmed, what the tick delivered (`tide_heard_mark`) and what its last run sent (`run_tick` in `engine/src/session.c`: `tide_hearing_begin`, `tide_hearing_end`). A tick's new events go out as `TIDE_HEARD_PREDICTED`; once the server confirms the tick, its last run's go out as `TIDE_HEARD_VERIFIED` (`tide_hearing_confirm`). A world the server sends again drops the ticks before it unheard (`tide_hearing_skip_to`); a host that stopped taking for `TIDE_HEARD_TICKS` ticks is recorded nothing more until it asks again. The server's own world records nothing.
  - Generated `tide_local_events(local, events)` moves a log's records into the local state and leaves it empty; the next `tide_frame` runs them first. Records with no `as` come straight from a tick, with no session between, and run both kinds of handler: a C host that ticks a world itself passes a log to `tide_world_tick_events` and hands it over, and what it ticks is all there is. `tide_host_game.events` is `tide_local_events`, which the standard host calls before `frame` with `tide_session_events`, asked for before the session's update.
  - Hot reloading drops what's recorded (`tide_hearing_rebuilt` in `tide_session_set_game` and `tide_session_migrate`): what each tick delivered is kept, so ticks run again stay silent, and ticks confirmed as the old build ran them tell `verified` handlers nothing. A match that changes hands starts a new client, which hears the ticks after the new host's confirmed one again.
  - `compiler/tests/e2e/local_events` checks all of it: a C host with one world, a match on the loopback network where a client predicts wrong (heard once through replays, late for what only the correction has, never taken back, `verified` only what the server had), and one machine through a session.
- Secrets such as RNG seeds are ordinary state behind visibility, for example an entity the client can't see. They need no special mechanism.
- Clients don't have to simulate the whole world. LOD borders and culling are resolved through state sync. Not built yet: every client ticks the whole world.
- Hosting (not built yet): Tide will host games for people, and hosted matches will run as WebAssembly in a sandbox (a runtime like wasmtime), with a time budget per tick. Owning the language doesn't make hosted code safe by itself: games can call C, and even pure Tide can loop forever. In the sandbox, C only reaches the game's own memory and what the host gives it, so `extern` stays allowed. A hosted game's match code, and the C it calls, has to build for the web; a server build can leave out views and local code.

## Modding

What's agreed (2026-10-05); the design proposed for the rest, and its open questions, are in `docs/spec.md`, Mods. Two parts are built: `virtual` and `override`, in the language for any package (see Language), and the service's first slice, for web games (The build service, below). The rest isn't: tidec's rules for what a mod may be, games that load builds, the prompt before joining, the sandbox.

- Mods are a service we run, the third beside the relay and hosting: remote compilation. A mod is a package that someone other than the game's developer adds to it, and the service builds the game with its mods, whole, natively, for each set of them. So mod code is game code, with its storage, schedule and speed: nothing is interpreted (the owner: the modding community is big, and limiting it is rough), no game carries a runtime for mods, and the engine gains no dynamic path for them.
- Every machine of a match runs the same build, local code included, fetched from the service, never from the host: mods never differ between a match's players, not even ones that only change views, which can show a player what gives them an advantage. Before a game joins a match of another build, local code is told its mods and has to say yes, so the game can ask its player, who then knows code from outside is about to be downloaded; nothing is fetched before that. The prompt is the game's own, and the engine draws none and enforces none (decided over a prompt of the host's that no game could skip: it would be our look and language in their game, and the sandbox is what protects players, not the prompt). A game whose code never says yes joins no such match; for mods a developer listed, asking is the game's choice; for mods from anyone, telling the player is a condition of the service, which turns them off for a game that doesn't. A build's mods are a set, whatever order they're listed in. Builds are signed with a key per game, and can be revoked.
- A mod is Tide alone: no `extern`, C, C++ or libraries. Its files are virtual, as a web page's are, and its code calls nothing that reaches outside the game (`Session.Connect` and `Clipboard.Copy` first; the list is part of the sandbox's work).
- A mod replaces a game's declaration with an explicit `override`, and only one the game marked `virtual`: what can be replaced is the developer's choice. An override matches by name and by parameters, both, filters among them: systems can have the same filters under different names. It's a substitution while compiling, and the override takes the replaced declaration's place in the schedule; nothing calls what was replaced for now (a `base()` may come later). Two mods replacing one declaration are an error that names both.
- `mods` is a setting, false by default: with it, what `tide build` makes can run the builds the service signed for the game, and a game without it has none of this.
- A closed game's source is seen by the service alone; its modders get its declarations without their bodies.
- That Tide code can't corrupt memory is Tide's own promise, for every game (the owner: "a Tide issue, not a mod issue"): mods rest on it, and it has to be tested as one.
- On desktop, a modded build runs in the OS's sandbox as a second layer, since the compiler was never a security boundary. The web has the browser's. WebAssembly isn't that layer on desktop: mod code compiles with the game, so it would put the whole game in a runtime. A system that can't sandbox a build runs no mods; making the sandbox work wherever games ship is our job.
- Stores that forbid downloaded code (iOS, consoles) have the mods a developer built in, and no others.

### The build service

The first slice (the owner, 2026-10-05: "for now let's just use fly Io to get something going", with storage to move later): `builds/`, Node with no dependencies, as the relay is. A mod is a package, so a build with mods needed nothing new of the compiler: it's the game's published source with the mods' lines added to its `tide.packages`, built by `tide build --web --release`. What was agreed for the slice is here; what was picked along the way is Provisional in `docs/spec.md`, Mods.

- **What it does** (`builds/builds.mjs`, whose first comment lists its addresses): a developer publishes a version of a game's source (`tide publish`); whoever has the game's key asks for a build of that version with a set of mods, each a package line pinned to its commit; the service builds it in a machine made for that one build, signs it, keeps it, and serves the page at `/b/<build>/`, cross-origin isolated, so it runs on threads. Players of one link run one build, so they share rooms (`?host`, `?join=<code>`: see Web builds).
- **No accounts.** A game is an id and a key, made with the admin secret (`node builds/admin.mjs game <id>`, with `TIDE_BUILDS_ADMIN` set). Everything that writes (publishing, asking for a build, revoking) takes the game's key, of which the service keeps a hash; getting what was built takes none. Revoking takes the game's key or the admin secret. `authorized` in `builds.mjs` is all that says who may write, which is where accounts and billing go.
- **A build's name** is a SHA-256 of the game's id, the version (the SHA-256 of what was published), tide's version and the mods, sorted (`buildName`, `parseMods`): the same mods in any order are the same build, and asking twice builds once (`alone`, which lets one thing at a time happen to a build). The target isn't in the name: a build's files are named by it (`web.html`, `web.json`), which is where other platforms go.
- **Builds are signed** with a key per game: ECDSA on P-256 over SHA-256, as r then s (64 bytes), with the public key as 65 bytes uncompressed, which is what the engine's own verifier takes (`rtc_p256_verify` in `platform/src/rtc/p256.c`; `tide_platform_rtc_vectors` already checks it against Node's signatures). What's signed is a small manifest (the build's name, its target, the page's SHA-256), served beside the page with its signature, and the game's public key has an address of its own. Nothing verifies them yet: the shipped game will. Private keys are kept encrypted (AES-256-GCM) with a master key from the app's secrets, sign in the service's own process, and never reach a machine that builds.
- **A revoked build** is deleted, and its link answers that it's gone (410). It's never built again.
- **Storage** is the app's volume for now, behind `builds/store.mjs` (named bytes: get, put, list, and uploads that get their name once they're whole), which is all that knows: object storage takes its place without the rest changing. In the folder, one thing at a time happens to a name, as Windows replaces no file while it's being read.
- **The service never unpacks or reads what's uploaded.** It keeps a version's bytes and hands them to the builder, and it signs for a page's hash as the bytes arrived.
- **Each build has a builder** (`builds/builder.mjs`) in a machine of its own (`builds/machines.mjs`): on Fly a Machine made through the Machines API and destroyed by Fly when its program ends, with no service on it, so no address; in tests, a process. It's given one thing, a token for that one build, with which it asks the service what to build, gets the version's bytes, and hands back the page or why there's none, with what tide said. The token stops working once the build is settled.
  - tide runs none of the game's code while it builds (it's tidec, clang and the linker), so the risks are those programs' own bugs and a build that takes everything. The builder unpacks the version itself, into a folder made for it, and only as files (`unpack`: no links, no path that leaves the folder, no name twice, limits on how many and how much).
  - Packages are fetched first, by commit (`tide fetch`), then the build runs with no network: in a network namespace with nothing in it (`unshare --net`), as a user that isn't root (`setpriv`), since root could get back out of it, with a limit on each file it writes (`prlimit`). tide's environment is made for it (`tideEnvironment`): nothing of the builder's is in it.
  - Limits: a time for the whole build, after which tide is stopped; the machine's memory; no file, packages or page over a size; so many builds at once. A build that failed says why to whoever asked. A builder that goes without an answer (out of memory) is found gone the next time its build is asked about (`settle`), and one still there past its time is stopped: nothing polls.
- **The builder's image has an installed tide for Linux**, pinned (`builds/tide.version`, `builds/Dockerfile.builder`: the release's package, checked against its checksums, as `install.sh` installs it). That version is in every build's name, and the builder refuses a job for another. The image also has the engine's objects for a web build, made once as it's built: they're the same for every game (tide keeps them by its version, compiler and flags, never by the game's folder), so each build's `.tide` starts as a copy of them (`TIDE_BUILD_WARM`) and compiles the game alone.
- **On Fly** (`builds/fly.toml`, `builds/fly.builder.toml`): the service is the app `tide-builds`, one `shared-cpu-1x` machine with 256 MB in `fra` that stops when nobody asks it anything, with the volume `builds_data` (1 GB). Builders are Machines of a second app, `tide-builders` (1 shared CPU and 1 GB, which `fly.toml` says), which has no machine of its own, no secret, and a private network of its own: Fly gives an app's secrets to every machine in it, so a machine that builds can't be in the service's app. The service has a token for that app alone. A builder reaches the service at its public address, which starts the service's machine when it had stopped.
  - Deploying: when `builds/tide.version` changes, the builders' image first (`fly deploy -c fly.builder.toml --build-only --push --image-label "tide-$(cat tide.version)"`), then `fly deploy --ha=false`, both from `builds/`. The secrets and what each is for are listed in `builds/fly.toml`.
- **A closed game's source is seen by the service alone** (decided). In this slice whoever asks for a build has the game's key, so the whole log goes back, which names the game's files and quotes its lines (`told` in `builds.mjs`). That changes when modders without the key can ask: they get what a build says of their own files, never the game's code.
- **`tide publish`** (`compiler/cli/publish.c`) sends what a build reads from the game's folder (`tide_game_sources` in `build.c`, from the same lists a build compiles: not `.tide/` or `build/`) as a tar it writes itself, with curl. **`tide fetch`** (`tide_fetch` in `packages_cmd.c`) downloads the game's packages and adds the lines of what they need, building nothing.
- Tests:
  - `builds` (`node --test builds/builds.test.mjs`, in every preset's tests where there's Node, as `relay` is): the service with builders that are processes on this machine and a tide that only stands in for one (`builds/stand-ins/tide.mjs`), so it needs no compiler: keys, publishing, a build's name, one build for two requests, signatures checked with Node, revoking, limits, writes refused without the key, what a builder's token reaches, unpacking, and the Machines API through a stand-in. `TIDE_BUILDS_TEST_LOUD=1` shows what its builders say, and how one that went wrong ended. It was run 8 at once, hundreds of times, to find what rested on the machine's speed: a build's time running out in any of its steps says the same thing, and a builder answers before it clears up after itself.
  - `tide_cli_publish` (`compiler/cli/tests/publish_test.mjs`): `tide publish` against the service on this machine, with no network: what's sent and what isn't, the same bytes each time, and what tide says when it can't.
  - `builds/page.test.mjs`, with `TIDE` set to a tide that builds web games: the example game (`builds/example/game`) published, built with the example mod (`builds/example/mod`) from a git host that's a folder, and its page opened in headless Chrome, where the game has to draw a frame with the mod's system in its match. CI runs it on Linux with the package it made. With `TIDE_BUILDS_URL`, `TIDE_GAME_KEY` and `TIDE_BUILDS_MOD` it checks a deployed service instead, as `TIDE_RELAY` does for rooms.

## Determinism

Given the same build and the same inputs, simulation results must be bit-identical on every supported platform.

### Floats

- Only the IEEE 754 basic operations (`+ - * /` and `sqrt`) can be trusted to give identical results across platforms. Build everything else from them.
- No FMA contraction. The compiler must never fuse `a*b + c` into a single instruction.
- No fast-math. No reassociation or reordering of float operations.
- Simulation code must not use the platform math library (`sin`, `cos`, `atan2`, `exp`, `pow`, and so on). Use the engine's own math library, which is built only from the basic operations.
- Vector math (vectors, matrices, quaternions) is written in-house: it only needs the basic operations, and third-party vector libraries often use approximate instructions or the platform math library.
- Transcendental functions may come from a third-party library, but only as source vendored into the engine and compiled with its flags. Prefer correctly rounded implementations, such as CORE-MATH: they return the same bits on every platform by definition.
- No approximate instructions such as `rsqrtps` or `rcpps`. Their results differ between Intel and AMD.
- Denormals stay enabled (no FTZ/DAZ) on every thread and every platform. WebAssembly can't flush denormals, so no other platform may either.
- Web builds use WebAssembly's SIMD (`-msimd128`, in `CMakeLists.txt` and `tide build --web`), whose operations give the same results on every machine, so the C compiler's vector loops run there too. No relaxed SIMD: its fused multiply-add gives different results on different machines.
- No x87 floating point.
- NaN in simulation state is a bug. NaN bit patterns are not portable.

### Parallelism

- Running in parallel must never change results. Thread timing must not decide the order of anything observable. That includes system order, command playback, reductions, and entity ID allocation.

### Systems that touch the same data

- It is not an error for two systems to write the same component. It's normal.
- Those systems run one after the other, in a deterministic order.
- Tooling tells the user why they didn't run in parallel. Example: "`MoveSystem` runs after `GravitySystem`: both write `Position`."
- Two systems conflict when one writes a component or singleton the other reads or writes, unless they can never touch the same entity: the compiler proves that from the archetypes (`with Player` against `with Enemy`). What code reaches through its `World` parameter (`world.Get<Health>(e)`, `Has`, `TryGet` and, with `mut World`, `Set`) is access to every entity's component, so it conflicts regardless; the checker takes it from the calls in the body (`decl.world_uses`, `check_world_call` in `check.c`) and in the functions the code passes its World to (`check_world_passing`: see Language), as the signature doesn't name the components, and `tidec --schedule` and the language server's hover and lens say it. A system that calls `Set`, or that reads through its `World` a component it also changes through a parameter, runs on one thread, and the latter writes its rows in place so what it reads of the rows it changed is the same on every machine (`world_reads_own_writes`). `Set<T>` in code that takes `T` as a parameter is an error, as the parameter would put this entity's back, but for `world.Set<T>(this, value)` beside a `T` that's only read (agreed 2026-10-05; `check_world_call`): nothing puts a read parameter back, the code goes on reading the chunk's other rows where they were, which a `Set` of this row doesn't change, so it's the same whether a snapshot shares the pages or not, and another entity's is still refused, as rows not yet reached would be read changed or not by that. It's how code that looks at every entity and writes a few avoids `mut`, which copies and compares a component's lanes for every row once a snapshot shares them (`compiler/tests/e2e/world_set_own`). Two systems that change the match's text or lists conflict too, as they share its heap. `Add`, `Remove`, `Destroy` and `Send` never conflict, because they're recorded and applied at the end of the tick in order. `Spawn` is recorded too, and only makes a spawning system that runs on one thread wait for those that spawn before it (below). Event handlers run at the end of the tick too, as each event's turn comes, so they aren't part of the tick's schedule. Input and `Time` are only read.
- Conflicting systems keep their order in the tick, and `[Before]`/`[After]` order systems too. A system starts as soon as everything it waits for is done; there are no barriers between stages. A system's stage is only how deep it is in that chain.
- A system splitting its entities across threads is the other kind of parallelism, and it doesn't change results either.
- The tick runs on threads (`tide/jobs.h`): the schedule (`analyze_parallelism` in `compiler/src/parallel.c`) becomes a task graph, a task per system, or per chunk for a system that splits its entities. A system with fewer chunks than threads runs each chunk in pieces (`pieces_for` in `engine/src/jobs.c`: about two tasks a thread, each worth a few microseconds, up to 16 a chunk), its rows in order piece by piece, so a few heavy chunks keep every thread busy with the same results; before that, its `own` function makes the pages it changes the world's own, as pieces of one chunk write the same pages at once. The platform layer has the threads (`tide_platform_jobs`, one per physical core: two threads of a tick on one core share its units and slow each other; on the web, one for each processor the browser counts, which is all it says: see Web builds); sessions take them in their desc and pass them to `tide_game.tick`. Each task records into a queue of its own, merged in the order one thread would have recorded it; the thread that runs ticks keeps the tasks' queues, pages and all, for the next tick. A tick with little work runs on one thread: tidec reckons each system's cost per entity (`stmt_cost`, counting a `for` from one number to another as many times as it runs, other loops as 8), and a parallel loop's steps as the world is now when its grid or list is a singleton's (`tide_grid_cells_about`, times 4 for what cells cost to read and write), and threads only start past about half a millisecond's work (one and a half on the web), as waking them and then reading on one thread what they changed in their caches costs more than they'd save below that. A worker with nothing to do looks for work 256 times in a row (`IDLE_LOOKS`, with the CPU's pause between looks where there's one), then leaves the tick and sleeps until there's work for it, which whatever makes the work asks it back for (`tide_jobs.more`: see Web builds, where it was first built, for what asks and why no call is lost). Desktop's pool sleeps its workers on a condition variable (`worker_loop` and `more` in `platform/src/jobs.c`), since 2026-10-05: before, a worker stayed in the tick until it was over, looking for work and yielding its core, and that slowed the threads that had work, most in ticks that mostly run on one. Measured on desktop (a release build on Windows, 12 cores, the least of runs taken in turn with the build before; saved as `desktop-idle-threads` and `desktop-idle-threads-before`): with 2,400 crates, Box3D's tick on 12 threads went from 1.62 ms to 1.32 and Box2D's from 0.84 to 0.74, which is what it takes on one thread; `bench_sand`'s clients simulate for 29 ms a second where it was 50 (191 where it was 236 at 1024 cells a side); `versus_life`'s tick went from 0.31 to 0.24 and `versus_sand`'s from 0.27 to 0.24; `bench_gallery` and the other versus benchmarks are as they were. More looks before sleeping were tried: 2,048 were no quicker, and 16,384 slower. The caller's thread can't leave a tick, which is its to finish: with nothing to do it yields its core after as many looks (`tide_yield`), so that a thread the system pushed aside doesn't hold the tick up for a time slice while this one spins. Web pages run on threads when they're cross-origin isolated. `platform/tests/jobs.tide` checks threads against one thread, tick by tick, natively and under Node.
- Besides components and singletons, systems wait for each other over what's the whole match's: changing text or lists (its heap; reading it alongside is safe, as the heap's page table is read atomically and replaced ones are freed once systems are done, `tide_heap_settle`), and spawning by a system that runs on one thread (entity IDs are handed out in order, and it hands them out as it runs). C is trusted and counts for neither. A system only splits its entities across threads when it changes no text, list, grid or singleton (`system_splits`).
- A parallel loop (`parallel (var at in cells by 2 offset o)` over a grid or `parallel (var i in items)` over a list, and a foreach over a grid whose steps only touch their own cell, `own_cell_only` in `compiler/src/check.c`) runs inside its system, a fork and join (`tide_parallel_for`): its steps go to a function of their own after the system's, with what they read of the code around them copied into a struct, and the pool's threads that have nothing else to do help (`help_loop` in `engine/src/jobs.c`) unless it's next to no work, as they're awake already and tidec can't tell how long the loops inside a step go on; outside a threaded tick, or for a small loop, the system's thread runs them alone. A loop's steps count as its tick's work where they can be told (a singleton's grid or list, above); a tick with a loop whose steps can't runs on threads. Its tasks are tiles, the blocks that start in one chunk's place (`tide_par_tile`): every place a sized grid's blocks start in, or for a grid with an open axis, the places of the chunks it has and of those before them whose blocks get into them, where a block that takes in none of its chunks is skipped (`tide_par_live`). A step writes into a copy of its chunk (`tide_par_buffer`, made with a compare-and-swap, the first one's for all, from a pool kept across loops), and reads the grid itself, which doesn't change while the steps run; the loop's end puts the copies into the grid in chunk order (`tide_par_end`). Where it can (`plan_window` in `compiler/src/check.c`), a task reads the cells its blocks reach at their place plus constants once, into a window (`tide_par_window`), and its steps read and write a copy of it as plain memory, which the C compiler can run with SIMD; the rows that changed go into their chunks' copies (`tide_par_window_put`). A task's blocks are numbered from its own first one, and a window is where it starts and how many cells it is across, so nothing in a step's setup goes past an int wherever the loop's offset and cells are (see Language: no Tide code can corrupt memory). A parallel loop over a list (`parallel (var i in items)`, `tide/list.h`) gives each task a copy of its blocks' elements, which its steps write while they read the list itself, and the loop's end puts the runs that changed into the list, chunk by chunk (`tide_par_list_end`). A foreach over a grid that goes in order goes row by row (`tide_grid_rows`), over a grid with an open axis through the chunks it has, sorted, in the scratch area (`tide_scratch_memory`, freed with the area's mark).
- A system that splits and spawns gives temporary handles (`TIDE_ENTITY_TEMPORARY` in the generation, with its task's number; `tide_new_entity`). Once its tasks are done, it settles them (`tide_settled`): its entities get IDs in the order one thread would have given them, and its tasks' queues (`tide_settle_item`) and the entity fields of its `mut` components (`tide_settle_<system>`) get the real handles. Settling keeps the tick's order among spawning systems (each settles after the one before it that spawns is done) and comes before anything waiting for the system starts, so the IDs are the same as on one thread. Systems look entities up while one makes them, so the entity table's page table is read atomically like the heap's (`tide_entities_settle`). Text shows a temporary handle as `Entity(new)`, and C tells with `tide_entity_is_temporary`.
- The language server shows each system's stage and waits above it and on hover, and `tidec --schedule` (or the `<game>_schedule` build target) prints it as text for CI and agents. `compiler/tests/schedule/` pins its output.
- The analysis keeps who runs after whom as bits, a row a system, and whether two systems conflict as a yes or no; it only works out what a wait is over for the waits it lists. Those are every wait that's a system's own and the first 32 that go through another system, and it lists the first 32 systems each runs alongside, counting the rest (`decl.waits_unlisted`, `decl.alongside_count`): a game with thousands of systems has millions of pairs. Generated code names only a system's own waits (`tide_waits_<system>`), as one that goes through another system is done by the time that system is.
- Declared access that isn't used is a warning, since it makes other systems wait for nothing: a `mut` parameter that's never written, or a parameter that's never used (a component only needed as a filter belongs in `with`). The language server offers quick fixes, as it does for adding a missing `mut`.
